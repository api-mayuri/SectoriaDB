# Этап 01 — безопасность движка (C1–C5)

Ветка `01-engine-safety`. Формат блоба на диске **не менялся**: заголовок метаданных — 9 байт на слот
(8 байт ключа + 1 байт состояния), раскладка `META | таблица A | таблица B`. Уже созданные блобы читаются как раньше.

## 1. Что было сломано

| # | Проблема | Последствие |
|---|----------|-------------|
| C1 | `insert` перезаписывал слоты на диске прямо во время цепочки вытеснений; на `maxEvictions` бросал `IOException`, а вытесненный чанк оставался только в локальной переменной. | Неудачный PUT уничтожал **чужой, ранее записанный** чанк. |
| C2 | Ни одной блокировки. | Два PUT выбирали один свободный слот, терялись вытесненные чанки, рвались массивы метаданных. |
| C3 | `Math.abs(key) % n`. | Для `Long.MIN_VALUE` получался отрицательный индекс корзины. |
| C4 | Один вызов `read`/`write` без цикла. | Короткое чтение/запись молча обрезало данные, слот всё равно становился ACTIVE. |
| C5 | Канал открывался на каждый вызов, `force()` не вызывался. | Дорого; после сбоя питания метаданные и данные расходились. |

## 2. Новый алгоритм вставки (C1)

`CuckooHashTable.insert` теперь состоит из трёх фаз.

1. **Поиск пути — только в памяти.** Обход в ширину (BFS) по корзинам. Корни — две корзины-кандидата нового ключа
   (в таблице A и в таблице B). Из корзины ребро ведёт в альтернативную корзину каждого ACTIVE-чанка (в другой таблице).
   Первая найденная корзина со свободным слотом (`FREE`/`DELETED`) завершает поиск, глубина ограничена `maxEvictions`.
   Результат — кратчайший путь слотов `p[0], p[1], …, p[n]`: новый чанк должен лечь в `p[0]`, чанк из `p[i-1]` переезжает
   в `p[i]`, а `p[n]` — свободный слот (при `n = 0` ничего двигать не нужно).
2. **Нет пути → `TableFullException`** (наследник `IOException`). К этому моменту на диск и в память не записано
   ни байта, таблица остаётся прежней.
3. **Есть путь → перемещения с конца.** Для `i = n … 1`:

| Шаг | Действие | Состояние сразу после |
|-----|----------|-----------------------|
| 1 | записать данные чанка из `p[i-1]` в область данных `p[i]` | `p[i]` ещё FREE/RESERVED — данные никому не видны |
| 2 | `force` | данные долговечны |
| 3 | метаданные `p[i]` := ACTIVE(ключ чанка) + `force` | чанк ACTIVE в **двух** слотах (`p[i-1]` и `p[i]`) |
| 4 | метаданные `p[i-1]` := RESERVED + `force` | чанк ACTIVE ровно в одном слоте `p[i]`; `p[i-1]` можно перезаписывать |

После всех перемещений: данные нового чанка → `p[0]`, `force`, метаданные `p[0]` := ACTIVE, `force`.
Порядок везде один: **данные → force → метаданные → force**.

### Почему это безопасно при сбое

В любой момент (и между любыми двумя записями) каждый ранее сохранённый чанк лежит хотя бы в одном ACTIVE-слоте
с корректными данными:

* до шага 3 чанк ещё только в `p[i-1]`; запись в `p[i]` (FREE или RESERVED) ничего не ломает;
* между шагами 3 и 4 чанк в двух слотах — безвредный дубликат;
* шаг 4 выполняется (и сбрасывается на диск) **до** того, как следующая итерация перезапишет данные `p[i-1]`;
  поэтому перезапись происходит только в слоте, чей чанк уже живёт в другом ACTIVE-слоте;
* новый чанк становится видимым только после того, как его данные сброшены на диск.

Дубликаты и RESERVED-слоты могут остаться только после сбоя. `loadMetadataFromDisk` их чинит: RESERVED → FREE
(такой слот всегда уже скопирован в другой ACTIVE), а если ключ ACTIVE и в таблице A, и в таблице B — остаётся копия A.
`lookup` принимает любой из двух ACTIVE-слотов. В штатной работе дубликатов нет вообще: пока идёт вставка, читатели
исключены блокировкой, а повторная вставка существующего ключа возвращает старое положение.

Тест `crashAtAnyPointDuringMove_neverLosesStoredChunks` имитирует сбой перед каждой записью многошаговой вставки,
перезагружает таблицу с диска и проверяет, что все чанки целы, а дубликаты/RESERVED устранены.

## 3. Модель блокировок (C2)

* В `CuckooHashTable` — один `ReentrantReadWriteLock` на таблицу.
* **Write lock:** `insert`, `loadMetadataFromDisk` (включая восстановление), `close`.
* **Read lock:** `lookup`, `readChunk`, `readChunkByKey`, `getBucket`, `getFillStats`, `forEachActiveChunk`.
* `lockForWrite()` возвращает `WriteGuard` (`AutoCloseable` без проверяемых исключений) — для операции из нескольких
  шагов; замок реентерабелен, внутри можно вызывать `insert`/`lookup`. Из read-секции (например из `ChunkConsumer`)
  его вызывать нельзя: повышение read → write даёт взаимоблокировку.
* **`ChunkLocation` живёт только пока удерживается замок:** следующая вставка может переместить чанк в альтернативный слот.
  Поэтому добавлен `readChunkByKey(key, size)` — поиск и чтение под одним read lock. Все места в `FileStorageService` и
  `BlobFileRestoreService` переведены на него; `lookup` + `readChunk(loc)` остаются только для обратной совместимости.
* `forEachActiveChunk` держит read lock на весь обход: записи в эту таблицу на это время блокируются (частично
  смягчает C6, но не решает его).

## 4. Хэш-функции (C3)

`bucketA/bucketB` считают `Math.floorMod(Math.abs(x), (long) numBuckets)`. Для всех значений, которые старая формула
`Math.abs(x) % n` обрабатывала корректно, результат **идентичен** — существующие блобы остаются читаемыми
(чистый `floorMod(x, n)` без `abs` дал бы другие корзины для всех отрицательных ключей, т.е. для ~половины чанков).
Меняется только `Long.MIN_VALUE` (у него `abs` остаётся отрицательным): индекс теперь всегда в `[0, numBuckets)`.
Тесты: `Long.MIN_VALUE` и прочие крайние ключи, а также проверка совместимости отображения `-5 → корзина 5`.

## 5. Ввод-вывод и долговечность (C4, C5)

* `FileChannelStorageIOEngine` держит **один** `FileChannel` на блоб, открывает его лениво и закрывает в `close()`.
  Используются позиционные `read(buf, pos)` / `write(buf, pos)` — потокобезопасны, положение канала не меняют.
* Чтение/запись идут в цикле до заполнения буфера (`readFully` / `writeFully`).
  **EOF до заполнения буфера → `IOException`.** Блоб заранее выделен целиком (sparse-файл внутри своего размера
  отдаёт нули), поэтому EOF означает обрезанный файл или выход за границы; молчаливое дополнение нулями скрыло бы порчу.
* `StorageIOEngine` теперь `AutoCloseable` и имеет `force(BlobFile)`. `CuckooHashTable` — `AutoCloseable`
  (закрывает движок под write lock, т.е. дожидается текущих операций). `HashTableCache.evict` закрывает таблицу,
  `@PreDestroy closeAll()` закрывает все при остановке. `ResizeService` закрывает временную таблицу нового блоба.
* `force(false)` (данные без лишних метаданных ФС) вызывается по схеме **данные → force → метаданные → force**;
  включается свойством `sectoriadb.fsync` (по умолчанию `true`, `StorageProperties.fsync`). Тесты используют
  `new FileChannelStorageIOEngine(false)`.
* `BlobFileWriteService` читает каждый чанк исходного файла полностью (в цикле) и падает с понятной ошибкой, если
  файл укоротился во время чтения.
* Весь вывод прогресса через `System.out` в core заменён на `log.debug`.
* Убрана бессмысленная обёртка `catch (IOException e) { throw new IOException(e); }`.

## 6. Оставшиеся ограничения

* **Неудачная хэш-функция B (существовала и раньше).** Множитель `0x6c62272e07bb0142` чётный, а младшие биты произведения
  зависят только от младших битов ключа. Для `numBuckets`, кратного степени двух, корзина B почти полностью определяется
  корзиной A, и таблица насыщается при ~40–50 % заполнения (замерено: 1280 корзин → ~5100 из 10240 слотов; степень двойки — ещё хуже).
  Смена функции сломает чтение существующих блобов — нужно делать вместе с форматом v2 (заголовок, версия, CRC32C на слот).
  Это же причина, по которой `TableFullException` реально встречается задолго до 70 % из `ResizeService`.
* Запись 9-байтовой записи метаданных может пересекать границу сектора и теоретически порваться при потере питания;
  защита — CRC на слот в формате v2.
* Перемещение стоит до 3 `fsync` на шаг пути: вставка с длинной цепочкой заметно медленнее. Отключается `sectoriadb.fsync=false`.
* BFS на полной таблице может обойти все корзины (O(numBuckets)) под write lock перед тем, как отказать.
* Прерывание потока (`Thread.interrupt`) в момент IO закрывает общий канал (поведение JDK); последующие операции
  с этой таблицей падают, пока `HashTableCache` не загрузит её заново. Закрытая через `evict` таблица, оставшаяся у
  параллельного читателя, также начнёт бросать `ClosedChannelException`.
* Не решено в этом этапе: C6 (миграция при записи), C7 (дедупликация без сравнения байтов), удаление чанков (H4),
  блокировка на уровне нескольких блобов/менеджера пулов, атомарность «манифест + чанки» (H1/H2).
* Если `TableFullException` произошёл посреди загрузки файла, уже вставленные чанки этого файла остаются в блобе
  (без манифеста) — «осиротевшие» чанки; их вернёт будущий GC со счётчиками ссылок.
