# Этап 03 — целостность чанков (C7)

Ветка `03-chunk-integrity`, растёт из `01-engine-safety`. По решению владельца проекта **обратная совместимость со старыми
блобами не нужна**: legacy-формат (9-байтовые записи без заголовка) удалён целиком, формат один. Старые блобы не открываются:
`loadMetadataFromDisk` падает с `InvalidBlobHeaderException` («bad magic»). Миграции v1→v2 нет.

## 1. Что было сломано

* Дедупликация доверяла 64-битному хэшу: при совпадении ключа байты не сравнивались, контрольной суммы на чтении не было —
  потерянный слот или коллизия молча отдавали чужие данные.
* Хэш корзины B был слабым (чётный множитель, младшие биты зависят только от младших битов ключа): при степени двойки
  корзин таблица насыщалась при 40–50 % заполнения.
* 9-байтовая запись метаданных могла пересекать границу 512-байтового сектора и порваться при потере питания; CRC не было.

## 2. Формат блоба (все числа big-endian)

```
[0 .. 4096)                 заголовок
[4096 .. 4096+M)            метаданные: totalSlots × 32 байта, M = округление вверх totalSlots*32 до 4096
[tableA .. tableA+T)        таблица A: numBuckets × 4 слота × chunkSize
[tableA+T .. tableA+2T)     таблица B: тот же размер;   tableA = 4096 + M (кратно 4096)
```

Заголовок (4096 байт):

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 8 | magic `SDBBLOB1` |
| 8 | 4 | formatVersion = 1 (неизвестная версия отвергается) |
| 12 | 4 | numBuckets (на таблицу) |
| 16 | 4 | chunkSize |
| 20 | 4 | slotsPerBucket = 4 |
| 24 | 4 | hashScheme = 1 (A: finalizer splitmix64, B: fmix64 Murmur3, разные seed) |
| 28 | 4 | зарезервировано |
| 32 | 8 | время создания, epoch millis |
| 40 | 4052 | нули |
| 4092 | 4 | CRC32C байтов [0, 4092) |

Запись метаданных слота (32 байта):

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 8 | ключ чанка |
| 8 | 1 | состояние: 0 FREE, 1 ACTIVE, 2 DELETED, 3 RESERVED |
| 9 | 1 | flags (0) |
| 10 | 2 | зарезервировано |
| 12 | 4 | dataLength — число сохранённых байт (1..chunkSize) |
| 16 | 4 | CRC32C этих dataLength байт данных |
| 20 | 8 | sequence — монотонный счётчик записей таблицы |
| 28 | 4 | CRC32C байтов [0, 28) самой записи |

Полностью нулевая запись (разрежённый файл, слот ни разу не писался) читается как FREE.

### Почему записи по 32 байта и выровнены

512 и 4096 кратны 32, а метаданные начинаются с 4096: запись целиком лежит в одном секторе и не может «разорваться» между
двумя секторами. Это же даёт «атомарность» записи метаданных на уровне сектора, а CRC записи ловит всё остальное
(частичная запись, bit-rot). Данные начинаются с границы 4096.

### Размеры при значениях по умолчанию

`chunkSize = 16384` (корзина из 4 слотов = 64 КиБ), `numBuckets = 65536`: слотов 2·65536·4 = 524 288; данные 8 ГиБ;
секция метаданных 524 288·32 = 16 МиБ (+4 КиБ заголовка); в памяти массивы ключ/состояние/длина/CRC — 17 байт на слот ≈ 8,5 МиБ.
Метаданные читаются при загрузке порциями по 8192 записей (256 КиБ), без одного огромного буфера. Блоб разрежённый.

## 3. Контрольные суммы и политика

* **Запись:** данные (ровно `dataLength` байт, без дополнения нулями) → `force` → запись метаданных с `dataCrc32c` → `force`.
* **Чтение (`readChunkByKey`, `readChunk`, `forEachActiveChunk`):** читается `dataLength` байт, проверяются длина и CRC32C;
  несовпадение → `ChunkCorruptedException extends IOException` (блоб, слот, ключ, причина). Запрос большего размера, чем сохранено, —
  тоже `ChunkCorruptedException`.
* **Перемещения при вытеснении** CRC не пересчитывают: длина и CRC переезжают вместе с чанком, порча остаётся обнаружимой.
* **Заголовок** проверяется при каждой загрузке таблицы (`HashTableCache` → `loadMetadataFromDisk`): magic, версия, CRC и совпадение
  геометрии (numBuckets, chunkSize, slotsPerBucket, hashScheme) с `BlobFileEntity` — иначе ошибка.

### Карантин (QUARANTINED)

Запись с неверным CRC (или неизвестным состоянием/длиной) при загрузке получает **только в памяти** состояние `QUARANTINED`:

* `lookup`/`readChunkByKey` её не возвращают; данные слота не читаются как чанк;
* слот **не считается свободным**: `insert` и BFS его не используют, поэтому его данные не затираются вслепую;
* на диске запись не переписывается — повреждение обнаруживается при каждой загрузке (ERROR в логе) и не «лечится» молча;
* считается в `FillStats.quarantinedSlots`, виден в `blob` и `scrub`; `ResizeService` отказывается расширять блоб с карантином
  (иначе чанки тихо потерялись бы).

Если при сбое питания оборвалась запись ACTIVE-копии при перемещении, исходный слот ещё ACTIVE, чанк не потерян; потерян
лишь один слот ёмкости. Освобождение слотов карантина оператором пока не реализовано.

## 4. Коллизии и дедупликация

`insert(key, data)` под write lock: если ключ уже есть, сравниваются длина и CRC (дёшево, без IO), затем **полные байты**
(один дополнительный read на каждое попадание дедупа — принято). Совпали — дедуп, ничего не пишется. Не совпали — настоящая
коллизия: чанк получает ключ `hasher.hash64(data, seed = attempt)`, `attempt = 1..7` (всего до `MAX_KEY_ATTEMPTS = 8` ключей), и вставляется
под первым свободным/идентичным ключом; после 8 попыток — `IOException`, ничего не портится. `insert` возвращает
`InsertResult(key, location, deduplicated)`, `BlobFileWriteService` пишет в манифест **итоговый** ключ, поэтому чтение работает
как обычно. Если сохранённые байты повреждены, а входящие совпадают с записанным CRC — чанк «лечится» перезаписью.
`insertPreservingKey` (для миграции при `resize`) ключ менять не разрешает. Тест использует хэшер-заглушку, у которой ключ при seed 0 константа.

Код не предполагает, что у любого объекта есть хотя бы один чанк (пустой список `chunkKeys` обрабатывается), — под будущие «малые объекты».

## 5. Хэши

### XXH64 вместо урезанного Murmur3

Раньше ключ — `h1` из Murmur3-x64-128 (половина 128-битного результата, ровно 64 бита, но с нестандартной обработкой хвоста и
фиксированным seed). Теперь `XxHash64BytesHasher` — стандартный XXH64 с seed: стандартизованная, широко проверенная функция,
быстрая (>10 ГБ/с на современных CPU, обрабатывает по 32 байта 4 независимыми потоками), с поддержкой seed — он нужен для пересчёта
ключа при коллизии. Корректность проверена официальными векторами (пустая строка = `EF46DB3751D8E999`, `a`, `abc`,
`Nobody inspects the spammish repetition`) и сверкой длинного входа/seed с независимой реализацией (Python). Ключ остаётся
64-битным: коллизия вероятна ~n²/2⁶⁵ — но теперь она обнаруживается и обрабатывается, а не молча портит данные.

### Хэши корзин

`bucketA = floorMod(splitmix64(key ^ SEED_A), n)`, `bucketB = floorMod(fmix64(key ^ SEED_B), n)` — два независимых миксера с разными
seed, без `Math.abs` (поэтому `Long.MIN_VALUE` не проблема). Допустимы любые `numBuckets`, включая степени двойки.

### Замеры заполнения до `TableFullException`

`maxEvictions = 32`, 4 слота в корзине, случайные ключи (тест `ChunkIntegrityTest.fillFactor_*`):

| numBuckets | слотов | заполнение (v1, этап 01) | заполнение (сейчас) |
|---|---|---|---|
| 1000 | 8000 | — | 98,31 % |
| 1024 | 8192 | степень двойки — хуже 40–50 % | 98,10 % |
| 1280 | 10240 | ≈ 5100 слотов (~50 %) | 97,88 % |
| 8192 | 65536 | — | 98,05 % |

Тест требует ≥ 95 %. Порог `ResizeService` (70 % после миграции) и автоматического расширения (80 %) оставлены как запас: вблизи
предела длина BFS-пути (и число `fsync`) растёт, а не потому, что таблица раньше отказывает.

## 6. Resize

Resize создаёт новый блоб и переносит чанки через `insertPreservingKey` с **теми же ключами** (манифесты на них ссылаются),
проверяя CRC каждого чанка (`forEachActiveChunk` бросает `ChunkCorruptedException` → resize прерывается, временный файл
удаляется). Блоб с карантином расширять нельзя. Миграции со старого формата нет — он больше не поддерживается.

## 7. Новые команды shell

* `scrub --id BLOB_ID` — проходит все слоты, проверяет CRC32C данных; печатает `active / ok / corrupt / quarantined`, список проблем
  (до 100) и `RESULT: clean|DAMAGED`.
* `verify --id FILE_ID` — перечитывает объект, считает MD5 и сравнивает с сохранённым ETag. Применимо только к обычному ETag
  (без `-`, т.е. не multipart); для остальных печатает «Not applicable». Ошибка CRC чанка выводится как `CORRUPT: …`.
* `blob` дополнительно показывает число слотов в карантине.

## 8. Настройки по умолчанию

`sectoriadb.default-chunk-size = 16384`, `sectoriadb.default-num-buckets = 65536` (`StorageProperties`, `application.properties`, README).

## 9. Оставшиеся ограничения

* Слоты карантина не освобождаются автоматически; нет «ремонта» блоба.
* Полное сравнение байтов при дедупе — лишний read на каждое попадание.
* `scrub` держит read lock на весь проход.
* Не решено: C6, H1–H4. Малые объекты решены в этапе `04-small-objects`.
