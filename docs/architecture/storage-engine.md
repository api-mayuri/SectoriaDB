# Движок хранения данных

Модуль `sectoriadb-engine` (форматы, кукушка, журнал малых объектов, ввод-вывод, хэши, размещение) и слой `storage` ядра (пулы, индекс чанков, кэши, рост).
Все числа в файлах — big-endian.

## Кукушкин блоб (`blob_<uuid>.raw`)

Блоб — разрежённый файл, заранее выделенный целиком. Две таблицы (A и B) по `numBuckets` корзин, в корзине 4 слота по `chunkSize` байт. Чанк может лежать
в корзине `bucketA(key)` таблицы A или в корзине `bucketB(key)` таблицы B.

```
[0 .. 4096)             заголовок
[4096 .. 4096+M)        метаданные слотов: totalSlots × 32 байта, M = totalSlots*32, округлённое вверх до 4096
[tableA .. tableA+T)    таблица A: numBuckets × 4 слота × chunkSize     (tableA = 4096 + M, кратно 4096)
[tableA+T .. +2T)       таблица B: тот же размер
```

Заголовок (4096 байт): `0` magic `SDBBLOB1` · `8` версия формата (1) · `12` numBuckets · `16` chunkSize · `20` слотов в корзине (4) · `24` схема хэшей (1) · `32` время создания ·
`4092` CRC32C байтов `[0, 4092)`. Неверный magic, версия, CRC или геометрия, не совпавшая с реестром, — `InvalidBlobHeaderException`, блоб не открывается.

Запись метаданных слота (32 байта; 4096 и 512 кратны 32, поэтому запись не пересекает границу сектора):

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 8 | ключ чанка |
| 8 | 1 | состояние: 0 FREE, 1 ACTIVE, 2 DELETED, 3 RESERVED |
| 12 | 4 | `dataLength` — сохранённых байт (1…chunkSize) |
| 16 | 4 | CRC32C этих байт данных |
| 20 | 8 | sequence — монотонный счётчик записей таблицы |
| 28 | 4 | CRC32C байтов `[0, 28)` записи |

Полностью нулевая запись (слот ни разу не писался) читается как FREE. Данные слота начинаются с границы 4096 и хранят ровно `dataLength` байт без дополнения.

**Размеры по умолчанию.** `chunkSize = 16384`, `numBuckets = 65536`: слотов 2·65536·4 = 524 288, данных 8 ГиБ (логически), метаданных 16 МиБ (+4 КиБ заголовка).
В памяти таблица держит массивы ключ/состояние/длина/CRC — 17 байт на слот ≈ 8,5 МиБ (≈9 МиБ). Метаданные загружаются порциями по 8192 записи.

**Хэши корзин.** `bucketA = floorMod(splitmix64(key ^ SEED_A), n)`, `bucketB = floorMod(fmix64(key ^ SEED_B), n)` — два независимых миксера, допустимы любые `numBuckets`.
Ключ чанка — XXH64 содержимого (стандартная реализация с seed, проверена официальными векторами). Таблица отказывает во вставке при заполнении около 98 %
(в тестах ≥ 95 % при `maxEvictions = 32`), поэтому пороги роста пула (75 %) и расширения (≤ 70 % после переноса) оставляют запас: у предела растёт длина пути вытеснений и число `fsync`.

### Вставка (`CuckooHashTable.insert`)

1. **Поиск пути — только в памяти** (`EvictionPlanner`). Обход в ширину по корзинам: корни — две корзины нового ключа, ребро ведёт в альтернативную корзину каждого ACTIVE-чанка.
   Первая корзина со свободным слотом (`FREE`/`DELETED`) завершает поиск; глубина ограничена `max-evictions` (32). Результат — кратчайший путь слотов `p[0]…p[n]`.
2. **Нет пути — `TableFullException`**; на диск и в память не записано ни байта.
3. **Есть путь — перемещения с конца.** Для `i = n … 1`: данные чанка из `p[i-1]` пишутся в `p[i]`, `fsync`; метаданные `p[i]` := ACTIVE, `fsync`; метаданные `p[i-1]` := RESERVED, `fsync`.
   Затем данные нового чанка в `p[0]`, метаданные ACTIVE. Порядок везде: **данные → force → метаданные → force**.

Безопасность при сбое: в любой момент каждый закоммиченный чанк лежит хотя бы в одном ACTIVE-слоте с верными данными (до шага метаданных чанк только в `p[i-1]`; между шагами в двух
слотах — безвредный дубликат; источник перезаписывается лишь после того, как его чанк стал ACTIVE в приёмнике). При загрузке таблицы RESERVED → FREE, а дубликат ACTIVE в обеих таблицах
сводится к копии из A.

**Новая вставка без `fsync` под блокировкой.** Запись в свободный слот (данные, затем метаданные ACTIVE) идёт без `fsync` и только под блокировкой таблицы; долговечность обеспечивает
**барьер** (`CuckooHashTable.barrier`): ведущий/ведомые, как у группового коммита — один `fsync` файла покрывает все записи, сделанные до него (`writeSeq`/`forcedSeq`).
Загрузка вызывает барьер для каждого блоба своих размещений **перед** коммитом метахранилища, который впервые называет её чанки; поэтому для закоммиченного объекта все чанки уже долговечны.
Ходы цепочки вытеснений сохраняют упорядоченные `fsync` — они защищают уже закоммиченные чанки. Незакоммиченная запись, потерянная при сбое, оставляет бродячий слот (ACTIVE с неверным CRC
данных или без ссылок): его освобождает обход сборщика или лечит повторная загрузка тех же байт.

### Блокировки

Один `ReentrantReadWriteLock` на таблицу: пишущая часть — вставка, загрузка метаданных, закрытие, освобождение слота; читающая — `readChunkByKey`, `contains`, статистика, пакетный обход.
Чтение чанка по ключу — поиск и чтение под одной блокировкой (положение слота живёт только пока держится блокировка: следующая вставка может переместить чанк).
Счётчик заполнения ведётся самой таблицей (O(1)).

### Контрольные суммы, карантин, дедупликация

- **Запись:** данные → `force` → метаданные с `dataCrc32c` → `force` (при вставке в свободный слот `force` откладывается до барьера).
- **Чтение:** читается `dataLength` байт, проверяются длина и CRC32C; несовпадение — `ChunkCorruptedException`. Перемещения вытеснения не пересчитывают CRC — порча остаётся обнаружимой.
- **Карантин.** Запись метаданных с неверным CRC (или неизвестным состоянием/длиной) при загрузке получает **только в памяти** состояние QUARANTINED: не читается, не считается
  свободной и не перезаписывается; на диске не исправляется; при каждой загрузке — `ERROR` в логе; видна в `blob`, `scrub`, метрике `sectoriadb_cuckoo_slots_quarantined`.
  `resize` блоба с карантином отказывает. Освобождения карантина оператором нет.
- **Дедупликация и коллизии** (уровень таблицы): если ключ уже есть, сравниваются длина и CRC, затем **полные байты** (одно дополнительное чтение на попадание). Совпали — ничего не пишется.
  Не совпали — настоящая коллизия 64-битного хэша: ключ пересчитывается `XXH64(данные, seed = попытка)`, всего до `MAX_KEY_ATTEMPTS = 8` ключей, иначе ошибка без порчи данных.
  Если сохранённые байты повреждены, а входящие согласуются с записанным CRC, чанк лечится перезаписью. `insertPreservingKey` (перенос при `resize`) ключ менять не позволяет.
- `freeSlot(key)` переводит ACTIVE → DELETED с `force` и уменьшает счётчик (используется только сборщиком); `activeKeys` постранично отдаёт ключи без чтения данных (обход блоба).

## Журнал малых объектов (`small_<uuid>.sob`)

Объект меньше `default-chunk-size` не режется и не попадает в кукушку: он хранится целиком одной записью в append-only файле пула.

```
[0 .. 4096)        заголовок
[4096 .. tail)     записи, каждая начинается с границы 8 байт
```

Заголовок: `0` magic `SDBSMOB1` · `8` версия (1) · `16` время создания · `64` и `96` два слота контрольной точки по 32 байта · `4092` CRC32C статической части `[0, 64)`.
Слот контрольной точки: `checkpointTail` (8) · generation (8; побеждает валидный слот с большим) · CRC32C `[0, 28)`. Контрольная точка живёт вне CRC всего заголовка и в двух слотах внутри
одного сектора, чтобы рваная запись подсказки не делала файл неоткрываемым; оба слота повреждены — данные проверяются с начала (медленнее, но верно).

Запись: `0` recordMagic `0x53524543` · `4` state (1 ACTIVE, 2 DELETED) · `8` dataLength · `12` CRC32C данных · `16` sequence · `24` ownerTag (информативно) · `28` CRC32C заголовка записи
по `[0, 28)` **кроме байта state**; затем данные и нули до кратности 8. Минимальная запись — 40 байт. Байт state исключён из CRC, чтобы удаление было записью одного байта
(`DELETED`) по смещению `offset + 4`: однобайтовая запись атомарна, а перезапись 32 байт могла бы порваться на границе сектора и выглядеть как оборванный хвост.

**Добавление.** Под короткой блокировкой файла: зарезервировать смещение и записать запись в page cache (`at = writeEnd; write; writeEnd = at + span`). Затем — групповой `fsync`: ведущий делает один
`force` за всех ожидающих, снова берёт блокировку и **публикует `tail`** только после `force`; читатель не видит запись, пока она не на диске. Контрольную точку пишет ведущий каждые `checkpoint-interval-bytes`.
Сбой `force` отбрасывает все недолговечные записи: у ожидающих `IOException`, файл усекается до `tail`, блоб становится **только для чтения** (после ошибки `fsync` содержимое страниц не определено);
пул выбирает или создаёт другой файл. Файл закрывается для дозаписи по достижении `small-object.max-file-bytes` (1 ГиБ); пустой файл принимает одну запись любого размера.

**Чтение** без блокировок: смещение выровнено и внутри `[4096, tail)`, magic, CRC заголовка, state ACTIVE, длина и CRC равны значениям манифеста, CRC данных; иначе `SmallObjectCorruptedException`.
`Range` — срез одной проверенной записи.

**Восстановление при открытии.** Проверить заголовок и слоты контрольной точки; пройти записи от 4096: у всех проверяется CRC заголовка, пересчитываются живые/мёртвые записи и `nextSequence`; у записей
после контрольной точки — ещё и CRC данных. Первая невалидная запись, после которой нет валидных, — оборванный хвост: логический `tail` = её начало, файл усекается. Если после невалидного места найдена
валидная запись — повреждение в середине: блоб открывается **только для чтения** (остальные записи читаются, проблема в логе и в `scrub`), запись идёт в другой файл.
Всё, что отрезается, — не более одной ещё не подтверждённой клиенту записи.

Удаление: байт state ← DELETED (выполняет сборщик через G). Место не освобождается сразу: файл считает живые/мёртвые записи и байты, а [компакция](garbage-collection.md) переписывает живое в новый файл.
Каталог синхронизируется после создания файла, чтобы имя блоба, названного метаданными, не пропало при потере питания.

## Ввод-вывод (`engine.io`)

- Один `FileChannel` на блоб, открывается лениво, позиционные `read(buf, pos)`/`write(buf, pos)` — потокобезопасны, положение канала не меняют.
- Чтение и запись идут циклом до заполнения буфера (`PositionalIo.readFully`/`writeFully`). **EOF до заполнения буфера — `IOException`**: блоб выделен целиком, EOF означает обрезанный файл.
- `force(false)` после данных и после метаданных (при `sectoriadb.fsync=true`).
- Прерывание потока во время ввода-вывода закрывает канал (поведение JDK): движок переоткрывает канал и повторяет операцию один раз.
- Новые файлы создаются с `CREATE_NEW` и именем из полного UUID (коллизия не обнулит живой блоб); длина файла проверяется при загрузке; каталог синхронизируется после создания.
- Таблица закрывается только когда ею никто не пользуется (ссылочные счётчики, см. ниже), поэтому читатель не получает `ClosedChannelException` от вытеснения.

## Пулы: несколько блобов и размещение

Бакет — пул из нескольких кукушкиных блобов и нескольких файлов малых объектов. Два разных вопроса:

| Вопрос | Кто отвечает |
|---|---|
| Куда положить **новый** чанк? | HRW по весам блобов — детерминированно, без состояния |
| Где чанк **лежит**? | индекс чанков `chunks` в метахранилище: `(pool, chunkKey) → {blob, длина, CRC32C, refcount}` — [metadata-model.md](metadata-model.md) |

### Взвешенное rendezvous-хэширование

Для ключа `k` и блобов `b` с весами `w_b`: `u_b = ((mix64(k ^ seed_b) >>> 11) + 0.5) / 2^53`, `score_b = -w_b / ln(u_b)`; чанк идёт в блоб с наибольшим score, остальные в убывающем порядке — детерминированный fallback.
`seed_b = mix64(FNV-1a(blobId))`. Вероятность выигрыша блоба точно `w_b / Σw`; при добавлении блоба переезжает в него ~`1/N` ключей и никто не переходит между старыми блобами; состояния нет. Данные при изменении весов
не переезжают — место записано в индекс. По сравнению с `hash % N`, кольцом и jump hash HRW единственный допускает произвольные веса, меняющиеся на лету, без перестройки.

**Вес** блоба = свободные байты × k(заполнение), где `k = 1` при заполнении ≤ 0,70; `k = ((0,95 − f) / 0,25)²` при 0,70 < f < 0,95; `k = 0` при f ≥ 0,95
(0,36 при 80 %, 0,16 при 85 %, 0,04 при 90 %). Слоты в карантине считаются занятыми. Блоб с нулевым весом (заполнен, заморожен для `resize`, много карантина) ставится **последним**, а не исключается.
Если блоб ответил `TableFullException`, закрыт или заменён, берётся следующий (`sectoriadb_pool_placement_fallbacks_total`).

### Путь записи чанков

`ChunkStore.stage`: создаёт начальные блобы (`pool.initial-blobs`) и растит пул по порогу; читает файл окнами по 256 чанков (4 МиБ), считает XXH64 и CRC32C, ищет ключи окна в индексе одной
читающей транзакцией. Ключ найден (или занят чанком этой же загрузки): сравниваются длина и CRC, затем **читаются и сравниваются байты** — дедупликация по пулу, `sectoriadb_pool_dedup_hits_total`;
повреждённая копия при совпадающих байтах лечится на месте. Иначе — вставка по HRW. Коллизия ключа с чужим чанком пересчитывает ключ (до 8 попыток) уже на уровне пула.
Все блобы пула используют один размер чанка.

### Рост пула

Блоб добавляется (под одной блокировкой на пул, условие проверяется заново), когда суммарное заполнение достигает `pool.grow-threshold-percent` (75), когда ни один блоб не принял чанк, и фоновой проверкой
раз в минуту; не более `pool.max-blobs` (16). Достигнут предел — `TableFullException` («Pool is full»), загрузка отклоняется без следов. Замороженный на `resize` блоб в предел не засчитывается.

### Расширение блоба на месте (`resize`)

Ручная команда `resize --id --buckets N`. Протокол: создать новый файл (отмечается «строится», чистильщики его не трогают) → **заморозить** блоб (дождаться вставок в полёте; новые вставки идут в другие блобы;
при единственном блобе пул растёт блобом) → перенести активные чанки порциями по 512 слотов (ключи сохраняются, читатели старой таблицы не стоят в очереди) и один `fsync` нового файла →
транзакция `replaceBlob` переносит записи индекса и сирот на новый блоб (манифесты не меняются) → перенаправление «старый → новый» в памяти для загрузок и читателей со старым снимком индекса →
старый файл удаляется через G. После сбоя: недостроенный новый файл и старый файл после коммита неучтённые и удаляются при старте. Отказ при блобе с карантином или заполнении после переноса > 70 %.
Два `resize` одного блоба одновременно исключены.

### Память: кэши с подсчётом ссылок

`HashTableCache` держит таблицы блобов в памяти (≈9 МиБ), `SmallBlobCache` — открытые файлы малых объектов. Пользователи берут ручку (`acquire`); таблица закрывается, только когда она вышла из кэша и ручек нет.
Вытесняется по LRU самая давняя таблица без ручек при превышении `cache.max-resident-tables` (64) или бюджета байт (пределы мягкие). Таблица с неподтверждёнными записями и запечатанный файл компакции не вытесняются.
Статистика заполнения вытесненной таблицы запоминается (веса размещения не перечитывают 9 МиБ). Подсказки «чанк → блоб» (`pool.location-cache-entries`) — LRU, не источник истины: чанк проверяется CRC, неверная подсказка стоит одного поиска в индексе.

## Известные ограничения

- Блобы не уменьшаются: освобождённые слоты переиспользуются, файл остаётся того же размера.
- Слоты карантина не освобождаются автоматически; автоматического ремонта блоба нет.
- Дедупликация сравнивает байты — одно дополнительное чтение на попадание.
- `replaceBlob` переносит все записи индекса блоба одной транзакцией (десятки-сотни миллисекунд для блоба на сотни тысяч чанков).
- Нет сжатия; малые объекты не дедуплицируются.
