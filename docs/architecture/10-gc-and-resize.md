## Проблема

До этапа 10 удаление и перезапись объекта освобождали только счётчики ссылок (`refcount`, этап 09): чанки с нулём ссылок
оставались в блобе и в индексе, строки очередей `chunk_gc`, `chunk_orphans` и `deleted_manifests` только росли, записи малых
объектов помечались `DELETED`, но файл `.sob` не сжимался. Место не возвращалось никогда. Кроме того, у такого «мусора» было
два неочевидных источника, которые не попадают ни в одну очередь:

* **оборванные загрузки**: чанки записаны в блоб до транзакции коммита (правило «данные до метаданных», doc 07), а коммита нет
  (сбой процесса, ошибка проверки ACL, `TableFull` посередине файла): копия лежит в слоте, индекс о ней не знает;
* **параллельные загрузки одного содержимого**: вторая физическая копия в другом блобе (сирота, doc 09).

Часть A возвращает место во всех этих случаях и не нарушает ни один из инвариантов doc 09.

## Что собирается: очереди

| Очередь / признак | Источник | Что делает сборщик | Условие |
|---|---|---|---|
| `chunk_gc` `(пул, ключ, txId) → время` | `refcount` дошёл до нуля (удаление, перезапись) | освобождает слот в блобе, удаляет `chunks`, `chunks_by_blob`, строки `chunk_gc` | строка старше периода ожидания G; запись по-прежнему с `refcount = 0` |
| `chunk_orphans` `(блоб, ключ) → время` | коммит нашёл запись индекса на другой блоб | освобождает слот копии в блобе, удаляет строку | под затвором загрузок; запись индекса не указывает на этот блоб |
| активный слот без записи индекса | оборванная загрузка, сбой между записью данных и коммитом | освобождает слот | обход блоба (`gc sweep`), под затвором загрузок |
| `deleted_manifests` `(txId, манифест) → время` | замещённая или удалённая версия | для SMALL: `markDeleted` записи; затем удаляет манифест и строку очереди | строка старше G |
| `small_*.sob` с мёртвыми байтами | пометки `DELETED` сборщиком | переписывает живые записи в новый файл, переключает манифесты одной транзакцией | доля мёртвых байтов не меньше порога, блоб не является целью добавления |
| записи `.sob`, на которые не указывает ни один манифест | оборванная загрузка малого объекта, упавшая компакция | то же: переписывание блоба (при обходе) | таких записей не меньше порога |

Значение строки `deleted_manifests` теперь время постановки (8 байт; пустое значение старого формата читается как «давно»).

## Период ожидания G

`sectoriadb.gc.grace` (по умолчанию 15 минут). Сборщик не трогает мусор моложе G. Зачем:

1. **Загрузка, нашедшая чанк в индексе, ещё не закоммитила.** Загрузка видит запись `refcount = 0`, сравнивает байты и считает,
   что писать не нужно. Если сборщик освободит слот до её коммита, коммит создал бы ссылку на несуществующий чанк. Протокол
   doc 09 закрывает это двумя средствами: период G (загрузка успевает закоммитить за секунды-минуты) и проверка при коммите
   `COLLECTED` (записи уже нет, а загрузка нашла её в индексе): коммит отклоняется, S3 отвечает `503 ServiceUnavailable` с
   `Retry-After: 1`, клиент повторяет запрос, и повтор пишет чанки заново. Данные не теряются, медленная загрузка только
   повторяется.
2. **Читатель старой версии.** Читатель берёт манифест из снимка и затем идёт по нему чанк за чанком. Пока G не истёк, чанки
   версии, которую только что заменили, на месте, а запись малого объекта ещё `ACTIVE` (до этапа 10 её помечал
   `DELETED` сам коммит, и читатель, державший старую версию, получал ошибку: это гонка, отмеченная в doc 07, теперь закрыта).
3. **Файл после компакции** остаётся до конца G по той же причине.

С `--grace 0s` (команда `gc run`) читатель старой версии получит `ChunkNotFoundException` / «record is marked DELETED»: это
документированное поведение режима для администратора и тестов.

## Освобождение чанка: одна эксклюзивная транзакция

`GarbageCollector.collectChunks` берёт из `chunk_gc` ключи, чья **самая новая** строка старше G (`GcRepository.dueChunks`; чанк,
который снова прошёл через ноль, не собирается раньше времени), и отдаёт их пачками в `GcRepository.collectChunks`. Одна пачка это
одна эксклюзивная write-транзакция (`beginWrite`: слот единственного писателя, исключает все коммиты, `replaceBlob` и другие шаги
сборщика). Внутри для каждого чанка:

1. строк `chunk_gc` уже нет: пропустить (его обработал предыдущий шаг пачки);
2. записи `chunks[(пул, ключ)]` нет: удалить строки `chunk_gc`;
3. `refcount != 0` (оживлена): удалить строки `chunk_gc`, запись оставить;
4. самая новая строка моложе границы (прошёл через ноль заново после выборки): не трогать;
5. иначе **освободить слот** в таблице блоба, названного записью (`SlotFreer`: блоб заморожен `resize` или заменён: отложить;
   блоба нет: считать слот отсутствующим; иначе `writerGate.lock()`, `CuckooHashTable.freeSlot(key)`, то есть слот `ACTIVE` →
   `DELETED`, `fsync`, счётчик `activeCount` уменьшен; в `FillStats` и весах размещения место видно сразу), затем удалить `chunks`,
   `chunks_by_blob`, строки `chunk_gc`.

После фиксации вызывается `ChunkStore.forget(пул, ключ)` (подсказка расположения не нужна, но занимает место). Сбой освобождения слота
(`IOException`) завершает пачку: то, что сделано до него, фиксируется, неудавшийся чанк не тронут, проход помечает ошибку и идёт
дальше при следующем запуске.

**Почему пачка, а не транзакция на чанк.** Контракт doc 09 говорит «одна транзакция на чанк». Две `fsync` фиксации на каждый
чанк (плюс `fsync` слота) дали бы около 100 чанков в секунду, и каждая такая транзакция блокирует всех писателей. Пачка из
`sectoriadb.gc.batch-size` чанков (16) выполняет **то же самое перечитывание записи внутри эксклюзивной транзакции для каждого
чанка**, поэтому корректность не меняется: между перечиткой и освобождением коммит вклиниться не может ни в пачке, ни в одиночной
транзакции. Цена: писатели ждут до 16 освобождений слота, а не одно. `batch-size=1` включает строгое «на чанк».

**Освобождение слота перед правкой индекса, не после.** Порядок контракта: слот, потом записи, потом фиксация. Если освобождение
слота бросает `IOException`, правок индекса для этого чанка ещё нет, и пачка фиксируется без него; правки дерева это операции
в памяти, они не бросают. Сбой самой фиксации отравляет метахранилище (как любой неудачный коммит), и перезапуск оставляет записи с
`refcount = 0` без слота: см. таблицу сбоев.

**Лимит скорости.** За проход освобождается не больше `sectoriadb.gc.max-chunks-per-run` чанков (10 000); остальное ждёт следующего
прохода (раз в `sectoriadb.gc.interval`, 1 минута).

## Затвор загрузок

### Почему он нужен

Копию без записи индекса нельзя освободить «просто так». Загрузка могла **получить** её дедупликацией внутри таблицы
(`insertPreservingKey` вернул «уже есть», потому что чанк лежит в слоте с тем же ключом) и ещё не закоммититься: запись индекса на
неё появится позже. Освободить такой слот значит создать объект, чьи чанки существуют только в индексе (контракт doc 09, «копии без
записи индекса»). Отличить копию мёртвой загрузки от копии живой снаружи нельзя.

### Устройство

`UploadGate` (по одному состоянию на пул). Не `ReentrantReadWriteLock`: загрузка берёт «читающую» часть на одном шаге запроса
(`stageStream`) и отпускает на другом (`commitObject`), оба могут идти не в одном потоке, а брошенная загрузка не должна навсегда
остановить сборщик.

* **Загрузка** (`ChunkStore.stage`, а для малых объектов `FileStorageService.stageSmall`) берёт `Hold` **до** записи первого байта и
  держит его до конца коммита: `FileStorageService.commitObject` / `store` отпускают его в `finally` при любом исходе, контроллеры S3
  вызывают `abortStaged` при отказе между стадиями (проверка ACL, ошибка сборки multipart). Новая загрузка ждёт только пока сборщик
  осушает или держит затвор (миллисекунды).
* **Сборщик** (`tryBegin`) для каждой пачки копий: запрещает новые `Hold`, ждёт до `sectoriadb.gc.sweep-gate-wait` (2 с), пока
  существующие не завершатся, и только когда их нет, освобождает пачку в **эксклюзивной write-транзакции с повторной проверкой
  каждого ключа** по закоммиченному индексу. Закончив, открывает затвор. Если загрузки не успели, пачка откладывается (метрика
  `gc_deferred{reason="uploads_in_flight"}`), обход этого пула прекращается: он не будет по очереди блокировать новые загрузки.
* **Отзыв.** `Hold` старше `sectoriadb.gc.upload-ticket-ttl` (30 минут) сборщик **отзывает**, чтобы забытая загрузка не останавливала
  обход навсегда. Отозванная загрузка не может закоммититься: `commitObject` вызывает `beginCommit()`, который возвращает `false`
  для отозванного `Hold`, и коммит отклоняется тем же `COLLECTED` (503, повтор). `Hold`, начавший коммит, не отзывается: сборщик
  ждёт его.

### Почему это корректно

Пока затвор у сборщика, ни одна загрузка не находится между «записала» и «закоммитила» и ни одна не может начаться. Значит слот,
для ключа которого в закоммиченном индексе нет записи, указывающей на этот блоб, не принадлежит никому. Повторная проверка
внутри эксклюзивной транзакции нужна потому, что кандидатов выбирают до затвора: загрузка, закоммитившая за время ожидания, уже
создала запись, и ключ остаётся (`notStray` в отчёте).

Рассмотрены и отвергнуты: (а) **эпохи** (запоминать начало каждой загрузки и освобождать только слоты, записанные до самой старой
из них): слоты не хранят время записи, а переиспользование слота внутри блоба вперемешку с эпохами потребовало бы нового формата;
(б) **тихое окно** (освобождать только когда загрузок нет вообще): при постоянной нагрузке окна нет; (в) **блокировка чтения-записи**
из подсказки контракта: см. выше. Затвор по пулу, а не по блобу, потому что загрузка ставит чанки в любые блобы пула.

Затвор не нужен очереди `chunk_gc`: у её записей есть строка индекса, загрузка, которая на неё опирается, защищена периодом G и
проверкой `COLLECTED`.

## Сироты и копии-бродяги: обход блобов

**Сироты** (`chunk_orphans`) обрабатываются тем же путём, что копии-бродяги: `GcRepository.freeStrays(блоб, ключи)` под затвором
пула. Запись индекса, указывающая на этот блоб (сирота стал настоящим чанком, когда запись создали на него), строку сироты просто
снимает; иначе слот освобождается, строка снимается. Освобождать копию «без затвора», пока запись индекса есть на другой блоб,
было бы безопасно только пока эта запись жива: если её соберут и создадут заново, указывая на освобождённую копию, получится
битая ссылка. Поэтому затвор берётся всегда; цена: пачка сирот осушает загрузки пула на миллисекунды.

**Обход** (`gc sweep --pool P`, раз в `sectoriadb.gc.sweep-interval`, 6 часов): для каждого кукушкиного блоба пула (не
замороженного и не заменённого) страницами по 512 слотов читаются **только ключи** активных слотов (`CuckooHashTable.activeKeys`,
метаданные в памяти, данные не читаются), одной read-транзакцией находятся ключи без записи индекса на этот блоб (кандидаты) и
те, что нашлись, освобождаются под затвором, как выше. Обход ограничен: страница, затвор на пачку, прекращение при первой
невозможности осушить загрузки. Бродяги малых объектов (записи `.sob` без манифеста) освобождаются переписыванием блоба
(`strayHeavy`, ниже). В конце обхода удаляются неучтённые файлы `small_*.sob` (см. компакцию).

## Надгробия и малые объекты

Выведенный из обращения манифест остаётся надгробием в `manifests` и `deleted_manifests` (doc 09). Сборщик, по строкам старше G:

1. для SMALL читает манифест (с разрешённым блобом) и вызывает `markDeleted(smallOffset)` записи (идемпотентно, один байт и
   `fsync`). Блоб исчез (компакция, удаление бакета): нечего помечать. Повреждённая запись: ошибка в лог, надгробие удаляется
   (читать там нечего). Другой сбой ввода-вывода: надгробие остаётся до следующего прохода;
2. **потом** одной эксклюзивной транзакцией удаляет записи манифестов и строки очереди (манифест, снова ставший живым, теряет
   только строку очереди).

Пометка до удаления манифеста: сбой между ними повторит идемпотентную пометку, а не оставит запись `ACTIVE`, которую никто не
найдёт. Для CHUNKED и EMPTY дополнительных действий нет.

**Что изменилось в пути записи.** `commitObject` и `deleteObject` больше не помечают запись малого объекта `DELETED` (удалён
`releaseData`). Тест `smallRecordsAreMarkedDeletedOnlyByTheCollectorAfterTheGracePeriod`: читатель держит старый манифест,
объект перезаписывают и удаляют, статистика блоба остаётся `live=2 dead=0`, чтение старой версии работает; после прохода с G = 0
`live=0 dead=2`, чтение старой версии даёт `SmallObjectCorruptedException`.

## Компакция малых блобов

`SmallBlobCompactor`; блоб с долей мёртвых байтов не меньше `sectoriadb.gc.small-compact-dead-percent` (50) и не меньше
`small-compact-min-dead-bytes` (1 МиБ), **не являющийся целью добавления** (`BlobService.smallAppendTarget`: самый новый блоб с
местом, куда сейчас идут записи пула). Шаги:

1. **Запечатать и осушить.** Старый блоб закрывается для обычного добавления (`SmallObjectBlob.seal`: `append` возвращает `null`,
   писатели выбирают другой блоб) и один раз берётся затвор пула (`tryBegin`, сразу `close`): малая загрузка держит `Hold` от
   добавления до коммита (`stageSmall`), поэтому после осушения множество записей блоба конечно: каждая принадлежит закоммиченному
   манифесту или никому, и новых нет.
2. **Снимок живых манифестов** блоба (`manifests_by_blob`, `deleted = false`), по смещению.
3. **Копирование.** Новый блоб создаётся уже запечатанным (до регистрации, писатели его не видят; зарегистрирован сразу, чтобы упавший
   процесс оставил учтённый, а не потерянный файл). Каждая живая запись читается с проверкой CRC32C (повреждённая запись прерывает
   компакцию: ничего не теряется) и дописывается; копируют 8 потоков, чтобы добавления делили групповой `fsync`. Чтения и записи
   идут своим чередом: старый файл не меняется.
4. **Обмен: одна транзакция** (`swapSmallBlob`): каждый живой манифест блоба должен быть в карте перемещений и стоять на старом
   смещении (иначе обмен отклонён, компакция прервана, новый блоб удаляется), его `smallBlobId`/`smallOffset` указывают на новый
   блоб (`manifests_by_blob` следует за ними), надгробия, всё ещё называющие старый блоб, удаляются с их строками очереди, запись
   старого блоба удаляется. Манифест, ставший надгробием между снимком и обменом, не переключается; его копия в новом блобе
   помечается `DELETED` после обмена.
5. **Освобождение.** Новый блоб открывается для обычных добавлений (`unseal`). Старый файл остаётся открытым в кэше и удаляется в
   проходе сборщика после G (`releaseOldFiles`); читатель, державший старый манифест, читает старый файл. Читатель старше G
   получит ошибку (документировано). Неучтённые `small_*.sob` (упавший процесс до удаления, оставшийся новый файл без записи реестра)
   удаляет `deleteUnregisteredFiles`: не открытые, без записи реестра, старше `max(G, 60 с)`. После перезапуска читателей нет,
   поэтому ждать нечего.

Загрузка, ожидающая коммита, задерживает компакцию (затвор не осушился: `deferred`), а не теряет запись.

| Момент сбоя | Что остаётся на диске | Чем кончается |
|---|---|---|
| после записи чанков загрузки, до коммита | копии без записи индекса, манифеста нет | обход (`gc sweep`) освобождает слоты под затвором |
| оборванная загрузка (ошибка ACL, `TableFull` посередине файла) | то же | отпускается `Hold` (`abortStaged` / `stage`), обход освобождает копии |
| забытая загрузка (поток не вернулся) | `Hold` в памяти | отзыв по `upload-ticket-ttl`; поздний коммит получает `COLLECTED` (503) |
| освобождён слот, транзакция сборщика не зафиксирована (процесс упал) | запись `refcount = 0` и строки `chunk_gc` на месте, слота нет | следующий проход: слота нет (`absent`), записи удаляются. Загрузка, пришедшая раньше, при проверке байтов не находит чанк и **переписывает** его на месте (`verifyExisting`), `refcount` растёт, коммит нормален |
| то же, но процесс жив, загрузка проверила байты до освобождения и коммитит после | запись удалена или осталась | запись удалена: `COLLECTED`, 503, повтор. Запись осталась только если транзакция не зафиксировалась, это отравление хранилища: коммиты загрузок тоже падают |
| сбой записи метаданных слота (`IOException`) | слот в памяти не изменён | пачка фиксирует то, что сделано до чанка; чанк остаётся в очереди |
| пометка `markDeleted` сделана, надгробие не удалено | запись `DELETED`, манифест на месте | повтор: пометка идемпотентна, надгробие удаляется |
| компакция упала до обмена | старый блоб авторитетен, новый блоб с неучтёнными копиями | новый блоб обычный и накапливает записи; обход находит в нём записи без манифестов (`strayHeavy`) и переписывает |
| процесс упал после обмена, до удаления старого файла | старый файл без записи реестра | `deleteUnregisteredFiles` (старше G и 60 с, не открыт) |
| `resize` замораживает блоб во время прохода | блоб `frozen` | чанки блоба откладываются (`gc_deferred{blob_busy}`), следующий проход |
| бакет удалён при очередях | записи индекса удалены вместе с бакетом | проход не находит строк, ошибок нет |

## Настройки

| Свойство | По умолчанию | Смысл |
|---|---:|---|
| `sectoriadb.gc.enabled` | `true` в `application.properties` (`false` по умолчанию в `StorageProperties` и в CLI-режиме) | фоновый планировщик; команды консоли работают всегда |
| `sectoriadb.gc.grace` | `15m` | период ожидания G |
| `sectoriadb.gc.interval` | `1m` | пауза между проходами (очередь чанков, сироты, надгробия) |
| `sectoriadb.gc.max-chunks-per-run` | `10000` | лимит скорости: слотов за проход |
| `sectoriadb.gc.batch-size` | `16` | чанков (или копий) на одну эксклюзивную транзакцию; `1` это строгое «на чанк» |
| `sectoriadb.gc.sweep-interval` | `6h` | пауза между обходами пулов |
| `sectoriadb.gc.sweep-gate-wait` | `2s` | сколько сборщик ждёт осушения загрузок пула |
| `sectoriadb.gc.upload-ticket-ttl` | `30m` | возраст `Hold`, после которого сборщик может его отозвать |
| `sectoriadb.gc.compact-interval` | `10m` | пауза между проверками блобов малых объектов |
| `sectoriadb.gc.small-compact-dead-percent` | `50` | порог доли мёртвых байтов |
| `sectoriadb.gc.small-compact-min-dead-bytes` | `1 MiB` | и не меньше стольких мёртвых байтов |

Периоды задаются в формате `Duration` (`15m`, `PT15M`, `6h`); планировщик читает их при старте.

## Команды консоли

| Команда | Что делает |
|---|---|
| `gc status` | длины очередей (чанки без ссылок и сколько из них старше G, сироты, надгробия), загрузки в полёте, ждущие удаления старые файлы, результат последнего прохода, обхода, компакции |
| `gc run [--pool P] [--grace 15m] [--max N]` | один проход; G учитывается, если `--grace` не задан явно (`--grace 0s` для тестов и администратора: не ждёт ничего и удаляет ждущие старые файлы сразу) |
| `gc sweep --pool P` | обход блобов пула; сообщает, если загрузки помешали (`deferred`) |
| `gc compact --pool P [--force]` | компакция подходящих блобов малых объектов; `--force` игнорирует порог, но не цель добавления |

`config` показывает настройки `gc.*`.

## Принятые решения и ограничения

* **Затвор по пулу.** Загрузки одного пула коротко ждут друг друга только при осушении (миллисекунды раз в обход).
* **Пачка вместо транзакции на чанк** (см. выше). Один писатель метахранилища занят на время пачки, пропорционально
  `batch-size`; при задержках PUT на пике уменьшайте `batch-size`.
* **Выборка `chunk_gc` сканирует очередь**: строки упорядочены по `(пул, ключ, txId)`, а не по времени, поэтому каждый проход
  читает очередь целиком (быстро, миллионы строк за секунды). Если очередь станет узким местом, нужен индекс по времени.
* **Компакция одним обменом**: все живые манифесты блоба переписываются в одной транзакции. При размере `.sob` 1 ГиБ и записях
  по 1 КиБ это около миллиона манифестов в одной транзакции; для таких профилей уменьшите `small-object.max-file-bytes`.
* **Таблицы блобов не уменьшаются**: освобождённые слоты переиспользуются вставками, но файл остаётся своего размера.
* **Читатель старше G** может получить ошибку (чанки освобождены, файл `.sob` удалён). Просроченное чтение «одного GET» дольше 15
  минут настраивается `sectoriadb.gc.grace`.
* **Нет пометки записей малых объектов `DELETED` при удалении**: статистика `small_dead_bytes` растёт только после прохода
  сборщика, а не при удалении.
* **Не освобождается** то, что держит `quarantined` слот (повреждённые метаданные) и данные блоба, которого нет в реестре.
