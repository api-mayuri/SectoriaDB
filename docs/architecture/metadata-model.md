# Модель метаданных

Всё состояние, кроме байтов объектов, лежит в `sectoria.db` ([metastore.md](metastore.md)); исключения — `credentials.json` (ключи доступа, атомарная замена файла с `fsync`) и `oplogs.jsonl` (журнал операций).
Кодировка ключей — `Keys` метахранилища: строки UTF-8 с терминатором (порядок байтов = порядок строк, строка не префикс другой), числа `u64` big-endian; поэтому ключи объектов сравниваются побайтно в UTF-8, как в S3.

## Деревья и индексы

| Дерево | Ключ | Значение | Назначение |
|---|---|---|---|
| `pools` | `poolId` | JSON пула (имя, путь, ACL, политика, время создания) | бакеты |
| `pools_by_name` | `name` | `poolId` | уникальность имени, поиск по имени |
| `blobs` | `blobId` | JSON блоба (вид `CUCKOO`/`SMALL`, путь, геометрия) | реестр блоб-файлов |
| `blobs_by_pool` | `(poolId, blobId)` | — | блобы пула |
| `manifests` | `manifestId` | кодек манифеста (ниже) | все версии объектов, живые и надгробия, скрытые манифесты частей |
| `objects` | `(bucket, objectKey)` | `manifestId` текущей версии | S3-пространство имён, листинг, поиск |
| `manifests_by_blob` | `(blobId, manifestId)` | — | какие манифесты ссылаются на файл малых объектов (компакция, удаление блоба) |
| `manifests_by_pool` | `(poolId, manifestId)` | — | манифесты, не являющиеся S3-объектами (файлы консоли, скрытые части multipart): чтобы `DeleteBucket` их находил |
| `deleted_manifests` | `(txId u64, manifestId)` | время постановки | очередь сборщика: замещённые и удалённые версии |
| `chunks` | `(poolId, chunkKey u64)` | `u16 len + blobId, u32 dataLength, u32 crc32c, u64 refcount` (≈56 байт) | авторитетное место чанка, дедупликация по пулу, счётчик ссылок |
| `chunks_by_blob` | `(blobId, chunkKey)` | — | чанки блоба (`resize`, удаление блоба, счётчики в консоли) |
| `chunk_gc` | `(poolId, chunkKey, txId)` | время постановки, мс | чанки с `refcount = 0` для сборщика |
| `chunk_orphans` | `(blobId, chunkKey)` | время записи, мс | физические копии, на которые индекс не указывает |
| `stats` | `"totals"`, `"chunk_refs"` | `(объектов u64, байт u64)`; сумма всех `refcount` | число и размер текущих версий (метрики без сканирования), счётчик ссылок; меняются в тех же транзакциях |
| `mpu_uploads` | `uploadId` | JSON загрузки (бакет, ключ, пул, заголовки, метаданные, ACL, алгоритм и тип суммы, состояние, результат) | загрузка в любом состоянии |
| `mpu_by_bucket` | `(bucket, key, initiatedAt u64, uploadId)` | — | только `OPEN`; порядок «по ключу, затем по времени» для `ListMultipartUploads` |
| `mpu_parts` | `(uploadId, partNumber u64)` | JSON (`manifestId`, размер, ETag, CRC32C, алгоритм и сумма части, время) | части |

Блоб в записи индекса хранится строкой, а не номером: блобы создаются, заменяются `resize` и удаляются, второй реестр номеров пришлось бы согласовывать. Цена — ≈0,3 % размера чанка на запись.

## Манифест

Запись `manifests`: `u8 версия (2) | u32 длина JSON | JSON скалярных полей | u32 число чанков | u64[] ключи чанков | u32 число сегментов | сегменты`. Версия 1 читается как версия 2 без сегментов. Листинг декодирует манифест
без массива ключей. Скалярные поля: id, имя файла, `storageKind`, `poolId`, `totalBytes`, `totalChunks`, `chunkSize`, `lastChunkSize`, время, флаг `deleted`, `bucketName`, `objectKey`, `contentType`, `etag`, `crc32c`
(CRC32C всего объекта, base64), `checksumAlgorithm`/`checksumValue`/`checksumType`, `acl`, пользовательские метаданные, `Cache-Control`, `Content-Disposition`, `Content-Encoding`, `Content-Language`,
для малых: `smallBlobId`, `smallOffset`, `smallLength`, `smallCrc32c`; для скрытой части: `multipartUploadId`, `partNumber`.

### Раскладки `storageKind`

| Вид | Что хранит манифест |
|---|---|
| `EMPTY` | только `poolId` и атрибуты |
| `SMALL` | `smallBlobId`, `smallOffset`, `smallLength`, `smallCrc32c` — одна запись `.sob`; индекс `manifests_by_blob` |
| `CHUNKED` | `poolId` и упорядоченный массив ключей чанков (8 байт на чанк); где лежат чанки, говорит индекс `chunks` |
| `MULTIPART` | массив ключей чанков всех `CHUNKED`-сегментов подряд + упорядоченные сегменты частей |

Сегмент `PartSegment`: `partNumber`, `length`, вид (`CHUNKED`/`SMALL`/`EMPTY`), `chunkSize`, `lastChunkSize`, `chunkCount` (сегмент владеет `chunkCount` ключами начиная с суммы `chunkCount` предыдущих
`CHUNKED`-сегментов), для `SMALL` — `smallBlobId`/`smallOffset`/`smallLength`/`smallCrc32c`. Последний чанк каждой части обычно короче, поэтому одного списка ключей недостаточно; у разных сегментов может быть разный
`chunkSize`. `totalBytes` — сумма длин. Сегменты нужны для диапазонов через границы частей и для `GET`/`HEAD ?partNumber`.

Манифест-надгробие (`deleted = true`) хранит только то, что нужно сборщику: для `SMALL` — положение записи, для `MULTIPART` — только малые сегменты; список чанков уже освобождён транзакцией удаления.

## Транзакции операций S3

Блобы (данные) пишутся до коммита и вне транзакции — загрузка может идти минуты, а писатель один. В каждой операции, меняющей метаданные, ровно одна короткая транзакция (групповой коммит).

| Операция | Транзакция |
|---|---|
| PutObject / CopyObject | `commitObject`: проверка пула и условия (`If-Match`/`If-None-Match`), ссылки на чанки (создание или `refcount += встречаемость`, оживление нулевой записи), манифест, `objects`, **затем** прежняя версия выводится из обращения (общие чанки старой и новой версий не проходят через ноль), `stats` |
| DeleteObject / DeleteObjects | одна транзакция на ключ: `objects.delete`, манифест `deleted`, ссылки освобождены, строка в `deleted_manifests`; отсутствующий ключ — идемпотентный `204` |
| CreateBucket | `pools` + `pools_by_name`; гонка двух создателей оставляет один пул |
| DeleteBucket | в одной транзакции: нет ключей в `objects` (иначе `BucketNotEmpty`), удалены все загрузки бакета, их части и скрытые манифесты, блобы пула, индекс чанков пула, пул; файлы удаляются после коммита |
| ACL, политика | read-modify-write одной транзакцией (`updateByName`/`updateCurrent`): параллельные изменения не затирают друг друга |
| GET / HEAD / листинг | читающие транзакции на снимке |
| `resize`, коммит | `replaceBlob`: запись нового блоба, перенос записей `chunks`, `chunks_by_blob`, сирот, удаление старой записи |

Указатель `objects` меняется атомарно с манифестом: двух «живых» версий ключа быть не может; при параллельных `PUT` одного ключа побеждает зафиксированный последним, остальные версии уходят в `deleted_manifests`.
`GET` — два поиска (`objects`, `manifests`), O(log n), без чтения чужих манифестов.

### Размещение и коммит чанков

Коммит принимает решение по индексу на момент коммита: запись уже есть (параллельная загрузка успела раньше) — `refcount` растёт, а своя копия в другом блобе записывается в `chunk_orphans`;
записи нет, а загрузка нашла её при начале (`indexed = true`) и её успел собрать сборщик — коммит отклоняется (`ChunkPlacementException COLLECTED`, клиент получает `503` с `Retry-After: 1`);
блоб размещения заменён `resize` — коммит повторяется с подстановкой замены (`BLOB_GONE`); у записи другие длина или CRC (`COLLISION`) — отклонение и пересчёт ключа при повторе.

## Листинг

`ListObjects` v1/v2 — диапазонный проход по `objects` от `max(prefix, after)` до `prefixEnd(prefix)`. `StartAfter`, `Marker`, `ContinuationToken` исключающие; общие префиксы считаются в `MaxKeys` вместе с ключами; при
`delimiter` курсор после найденного общего префикса перепрыгивает на `prefixEnd(commonPrefix)` — стоимость страницы зависит от числа возвращаемых записей, а не от размера «папок»; `NextMarker` — последний ключ или общий префикс.

## Multipart

Состояние загрузки — деревья `mpu_*`; части — обычные данные, а не отдельные файлы.

| Состояние | Когда | Что хранится |
|---|---|---|
| `OPEN` | после `Create` | принимает части; есть в `mpu_by_bucket` |
| `COMPLETED` | после `Complete` | `resultEtag`, `resultManifestId`, сумма, отпечаток списка частей (`md5` строки `номер:ETag;…`), `completedAt`; живёт `completed-retention` (24 ч) |
| `ABORTED` | после `Abort` или истечения | `abortedAt`; живёт столько же — запоздавшие запросы получают `NoSuchUpload` |

- **Часть.** Тело проходит тот же путь, что объект (спул, MD5+CRC32C+сумма клиента, проверка до записи в блобы, чанки или малая запись, барьер) и фиксируется одной транзакцией как **скрытый манифест** (без бакета и ключа,
  в `manifests_by_pool`) + строка `mpu_parts` + ссылки на чанки. Повтор номера освобождает прежнюю часть в той же транзакции; одновременные повторы сериализуются, побеждает последний.
  Если загрузку отменили между записью данных и коммитом — `NoSuchUpload`, данные становятся мусором для сборщика.
- **Complete — одна транзакция, ни одного байта данных не читается и не пишется.** Проверяет загрузку (бакет, ключ), для каждой части запроса: строка есть, ETag совпадает, суммы совпадают, у части есть сумма алгоритма загрузки,
  манифест жив; порядок номеров строго по возрастанию проверен до транзакции (`InvalidPartOrder`); **каждая часть списка, кроме последней, не меньше `min-part-size` (5 МиБ)** — иначе `400 EntityTooSmall`
  (проверка внутри транзакции, загрузка остаётся `OPEN`). Затем: суммы объекта из **хранимых** значений частей, манифест `MULTIPART`, **передача ссылок** (записи манифестов частей удаляются без освобождения ссылок и без надгробия —
  `refcount` каждого чанка не меняется), не перечисленные части отбрасываются (`retire`), общий код коммита объекта (условие записи, `objects`, прежняя версия, `stats`), состояние `COMPLETED`. Любая ошибка откатывает всё.
- **Суммы без чтения данных.** ETag — `md5(md5₁‖…‖md5ₙ)-N`. `COMPOSITE` — алгоритм от конкатенации двоичных сумм частей (CRC32, CRC32C, SHA-1, SHA-256), base64 и `-N`. `FULL_OBJECT` (CRC32, CRC32C, CRC64NVME) и CRC32C всего
  объекта получаются склейкой сумм частей по их длинам: `crc(A‖B) = M^len(B)·crc(A) ⊕ crc(B)` над GF(2) (`CrcCombine`, не больше 48 умножений матрицы на вектор, не зависит от длины данных).
- **Идемпотентность.** Повтор после успеха с тем же отпечатком списка частей возвращает сохранённый результат; другой список — `404 NoSuchUpload`. Одновременные `Complete` сериализуются: объект создаёт один.
- **Abort и срок жизни.** Одна транзакция освобождает ссылки частей (чанки освобождает сборщик через G), снимает запись с `mpu_by_bucket`. Фоновая очистка раз в `cleanup-interval-ms` отменяет `OPEN`-загрузки без новых частей дольше
  `stale-after` (7 суток; повторная проверка `updatedAt` в транзакции) и удаляет записи `COMPLETED`/`ABORTED` старше `completed-retention`.
- **`GET`/`HEAD ?partNumber=N`** читают сегмент `N` (номер — клиентский); `ListParts` — страница `mpu_parts` (`NextPartNumberMarker` — последний выданный номер); `ListMultipartUploads` — диапазон `mpu_by_bucket` с `delimiter` и маркерами.
- Каталог `<data-dir>/.multipart` формата до перехода на метахранилище не читается и удаляется при старте.

## Целостность метаданных

CRC32C каждой страницы (проверка при каждом чтении), атомарная мета-страница; инварианты проверяются в тестах после каждого сценария: `refcount` против живых манифестов, `refcount = 0` ⇔ строка `chunk_gc`,
`chunks` ↔ `chunks_by_blob`, сегменты сходятся с `totalBytes` и длиной массива ключей, `mpu_parts` указывают на живые скрытые манифесты, `mpu_by_bucket` равно множеству `OPEN`-загрузок.
