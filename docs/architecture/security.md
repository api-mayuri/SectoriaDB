# Безопасность

## Модель

Один владелец (один «аккаунт»), но у каждого ключа доступа может быть своя **IAM-политика** — стандартный документ AWS (`Version`, `Statement` с `Effect`, `Action`, `Resource`, `Condition`), без своего формата прав. Аутентификация — AWS Signature Version 4;
авторизация подписанного запроса — политика ключа вместе с политикой бакета (раздел «Авторизация»). **Ключ без политики сохраняет полный доступ** (так работали все прежние установки): политики нужно подключить, см. [recommendations.md](../guide/recommendations.md#один-ключ-на-приложение-или-арендатора).
Пользователей, групп, ролей, STS и OIDC нет; владельца объекта/бакета нет — арендаторов разделяют ключи с политиками, каждый на свои бакеты. Сервер не терминирует TLS: шифрование на пути обеспечивает nginx перед ним (раздел «Защита канала»).

## Аутентификация (SigV4)

| Правило | Поведение |
|---|---|
| Включение | `sectoriadb.s3.auth.enabled` (по умолчанию `true`); `false` отключает проверки полностью — только для разработки |
| Нет ключей | при включённой авторизации и пустом списке ключей — `403 AccessDenied` на всё; «открытый режим» только явным `allow-open-setup=true` |
| Форма | заголовок `Authorization: AWS4-HMAC-SHA256 Credential=…/дата/регион/s3/aws4_request, SignedHeaders=…, Signature=…` или presigned (`X-Amz-Signature` в запросе, определяется по имени параметра) |
| Область ключа | сервис `s3`, окончание `aws4_request`, дата в области = дате `x-amz-date`; регион должен равняться `sectoriadb.s3.region` (`enforce-region`) |
| Подписанные заголовки | `host` и все `x-amz-*` обязаны входить в `SignedHeaders` (`require-signed-headers`); повторные заголовки склеиваются через запятую |
| Канонический запрос | значения хэшируются в ISO-8859-1 (так Tomcat декодирует заголовки: подпись не-ASCII метаданных сходится); URI кодирует кодовые точки, а не суррогатные половины (эмодзи в ключах); `+` — не пробел; строгий разбор query |
| Сдвиг часов | ±15 минут (`403 RequestTimeTooSkewed`); presigned «из будущего» более чем на 15 минут — то же; истёк `X-Amz-Expires` — `403 ExpiredToken`; `X-Amz-Expires` 1…604800 с |
| Сравнение подписей | `MessageDigest.isEqual` (постоянное время); ожидаемые подпись и ключ подписи не логируются никогда, секреты тоже |
| Хэш тела | `x-amz-content-sha256`: 64 hex проверяются потоково; `UNSIGNED-PAYLOAD`/`STREAMING-UNSIGNED-PAYLOAD-TRAILER` — при `allow-unsigned-payload=true` (иначе `400 InvalidRequest`); `STREAMING-AWS4-HMAC-SHA256-PAYLOAD[-TRAILER]` — подписи фрагментов; прочее `STREAMING-*` — `501`; мусор — `400` |
| Ключи | `credentials.json`, снимок публикуется только после надёжной атомарной записи; ключ можно выключить/удалить без перезапуска; причины отказов — метрика `sectoriadb_s3_auth_failures_total{reason}` |

## Авторизация подписанных запросов (IAM)

Запрос прошёл проверку подписи, значит известен ключ. Дальше `IamAuthorizer` проверяет **каждое** право, которое нужно операции (для `CopyObject` — два), по правилам AWS для одного аккаунта:

```
 для права (действие, ресурс):

   Deny в политике ключа ИЛИ в политике бакета (Principal совпал с ключом)? ──да──▶ 403 AccessDenied
                         │нет
   Allow в политике ключа ИЛИ в политике бакета? ───────────────────────────да──▶ разрешено
                         │нет
   у ключа нет собственной политики (прежний ключ)? ────────────────────────да──▶ разрешено
                         │нет
                         ▼
                    403 AccessDenied
```

| Вопрос | Как устроено |
|---|---|
| Где хранится политика | в `credentials.json` рядом с ключом, необязательное поле `policy` (обычный JSON-объект). Нет поля — полный доступ. Пишется командой `key-policy` ([admin-shell.md](../guide/admin-shell.md#ключи-доступа-online)), файл общий для консоли и сервера |
| Когда применяется | на следующий же запрос: репозиторий перечитывает `credentials.json` при смене времени или размера файла — тот же механизм, что для `disable-key`; перезапуск не нужен |
| Принципал | в политике ключа неявный (сам ключ), элемент `Principal` там запрещён. В политике бакета ключ задаётся как `"*"`, `{"AWS":"*"}`, `{"AWS":"arn:aws:iam::sectoriadb:user/<accessKeyId>"}` (основная форма) или просто `<accessKeyId>`; можно списком |
| Одно соответствие операция → право | `OperationClassifier` (тот же, что в метриках) даёт операцию, `IamAuthorizer.requirements` — действие и ARN ресурса. Анонимный путь использует те же имена действий и ARN |
| `CopyObject`, `UploadPartCopy` | `s3:GetObject` на источнике **и** `s3:PutObject` на приёмнике |
| `DeleteObjects` | как в AWS, ответ `200`, а каждый запрещённый ключ получает `<Error><Code>AccessDenied</Code>` (проверка `s3:DeleteObject` на каждый ключ в контроллере) |
| `ListBuckets` | `s3:ListAllMyBuckets`; при праве выдаются имена **всех** бакетов (как в AWS); без права — `403` |
| Multipart | `s3:PutObject` на `CreateMultipartUpload`, `UploadPart`, `CompleteMultipartUpload`; `s3:AbortMultipartUpload`; `s3:ListMultipartUploadParts`; `s3:ListBucketMultipartUploads` |
| Условия | `Bool` на `aws:SecureTransport`; `StringEquals` и `StringLike` на `s3:prefix` и `s3:delimiter` (для `s3:ListBucket`; `s3:prefix` без параметра `prefix` равен `""`, `s3:delimiter` без параметра отсутствует и условие не выполняется). Всё остальное — fail closed: `key-policy` такую политику не принимает, а в политике бакета `Allow` не действует, `Deny` действует безусловно |
| Fail closed | неразбираемая политика ключа не даёт ничего; операция, которой нет в таблице действий (`Other`), и неоднозначный запрос (закодированное имя подресурса, смесь `acl` и `uploadId`, путь с пустым первым сегментом) ключу с политикой отказывают; ключу без политики они доходят до контроллера, как раньше |
| Метрика | отказ — `403 AccessDenied` с текстом «User: arn:aws:iam::sectoriadb:user/ID is not authorized to perform: действие on resource: ARN» и причина `policy_denied` в `sectoriadb_s3_auth_failures_total` |
| Что это не даёт | политика ограничивает S3-операции ключа, но не владельца: нет «чужих» и «своих» объектов внутри общего бакета, кроме разделения по префиксам в `Resource`; ACL на подписанные запросы не влияют |

Явный `Deny` в политике бакета теперь действует и на ключи без политики (например, «запретить всё не по HTTPS» заставит и подписанные запросы идти по HTTPS). Пустой список ключей и `allow-open-setup`/`auth.enabled=false` работают как раньше: личности нет, проверок нет.

## Анонимный доступ, ACL, политики

Подробная семантика для пользователей — [s3-usage.md](../guide/s3-usage.md). Реализация (`AccessControlService`, `BucketPolicyEvaluator`):

- Анонимный `GET`/`HEAD` объекта разрешён, если объект сам `public-read(-write)` или политика бакета разрешает `s3:GetObject`, и нет явного `Deny`. Бакетный ACL `public-read` даёт только листинг (ресурс `arn:aws:s3:::bucket`).
  `public-read-write` даёт анонимные `PUT` и `DELETE` ключей (не чтение, не ACL/политики, не multipart).
- Политика: явный `Deny` по совпавшему оператору побеждает любой `Allow` и все ACL; затем `Allow`; иначе решают ACL. **Fail closed:** `Allow` с `Condition` или с `NotAction`/`NotResource`/`NotPrincipal` не применяется;
  `Deny` с `Condition` применяется как безусловный; политика, не разбирающаяся как JSON, игнорируется целиком. Принципалы для анонима: `"*"`, `{"AWS":"*"}`; конкретные ARN и ключи анонимным не соответствуют.
- Анонимные запросы с `x-amz-copy-source`, не-`private` `x-amz-acl` или `x-amz-grant-*` отклоняются (иначе открытый бакет — канал выноса приватных объектов); подресурсы `acl`, `policy`, `uploads`, `uploadId`, `partNumber`, `tagging`,
  `versioning`, `cors`, `lifecycle`, `encryption`, `publicAccessBlock`, `delete`, `location` анонимно недоступны.
- `response-*` для `GET` разрешены только подписанным запросам.

## Защита канала (TLS)

Сервер говорит только по HTTP; TLS терминирует nginx ([deploy/nginx/sectoriadb.conf](../../deploy/nginx/sectoriadb.conf), установка и сертификаты — [operations.md](../guide/operations.md#tls-через-nginx)). Решение принято сознательно: TLS в Java не реализуется,
сертификатами, версиями протокола и шифрами управляет проверенный прокси.

| Вопрос | Как устроено |
|---|---|
| Что шифруется | клиент → nginx (TLS 1.2/1.3, ECDHE + AES-GCM/ChaCha20, HSTS). Участок nginx → сервер идёт открытым текстом по внутренней сети compose; на разных хостах нужен VPN/WireGuard |
| Подпись и прокси | `Host` и путь доходят неизменными, поэтому SigV4 сходится; подпись защищает от подмены запроса, но не скрывает содержимое — это делает TLS |
| Как сервер узнаёт о HTTPS | `server.forward-headers-strategy=native`: `RemoteIpValve` Tomcat берёт схему из `X-Forwarded-Proto` **только от пира из `server.tomcat.remoteip.internal-proxies`** (по умолчанию loopback и частные сети). От других адресов заголовок игнорируется — подделать его снаружи нельзя (`S3SecureTransportSpoofTest`). nginx перезаписывает заголовок, присланный клиентом |
| Обязательный HTTPS | `sectoriadb.s3.require-secure-transport=true`: запрос не по HTTPS получает `403 InsecureTransport` до проверки подписи и до чтения тела (в compose включено; по умолчанию свойство выключено, чтобы голый jar в разработке работал по HTTP) |
| `aws:SecureTransport` | в политиках бакета вычисляется условие `Bool` на `aws:SecureTransport` (единственное поддерживаемое; значение — флаг `request.isSecure()` из строки выше). Остальные условия обрабатываются в режиме fail closed, как раньше |
| Кому доверяется заголовок | в compose — только адресу nginx (`172.31.250.10`, фиксированная подсеть сети compose); подделанный `X-Forwarded-Proto` от другого контейнера получает `403 InsecureTransport`. Без compose сузьте `server.tomcat.remoteip.internal-proxies` до адреса своего прокси: по умолчанию Tomcat доверяет всем частным сетям |
| Порт управления | `9464` через nginx не проксируется, на хосте слушает только loopback |

## Лимиты и защита от злоупотреблений

| Угроза | Мера |
|---|---|
| Медленные клиенты занимают потоки Tomcat | `server.tomcat.connection-timeout=60s`, `keep-alive-timeout=30s`, `max-connections=2048`; минимальная скорость тела 1 КиБ/с после 30 с (`400 RequestTimeout`); лимит одновременных записей (64) и чтений (128) на ключ доступа (`503 SlowDown`) |
| Огромные тела | `PutObject`/`UploadPart`: размер обязателен (`411`), потолок 5 ГиБ (`400 EntityTooLarge`), проверка места под спул до приёма; политика ≤ 20 КиБ, ACL ≤ 64 КиБ, XML ≤ 2 МиБ; `DeleteObjects` ≤ 1000; парсер `aws-chunked` растёт по мере прихода данных, ограничивает строку заголовка и число трейлеров, сверяет длину |
| XXE | все разборщики XML — `XmlSupport.newSecureDocumentBuilder` (DOCTYPE, внешние сущности и DTD, XInclude запрещены); Jackson-XML только для ответов |
| Выход за пределы каталога | ключи объектов в файловую систему не попадают (имена блобов — UUID); ключ `../x` — обычный ключ; имена бакетов валидируются; пул не может иметь общий или вложенный базовый каталог |
| Подмена подресурса | `PUT`/`DELETE` с неизвестным подресурсом — `501`, а не удаление бакета/перезапись объекта |
| Внедрение в логи | управляющие символы и переводы строк из клиентских имён экранируются одним помощником `LogSafe`, длина ограничена; ключи объектов в `INFO` не логируются (только в профиле `debug`), имена бакетов — только в событиях создания и удаления бакета; описание ключа на `INFO` не пишется |
| `;` в пути (path parameter) | запрос с `;` в пути отклоняется `400 InvalidURI` до проверки подписи и политик, для подписанных и анонимных: авторизатор видел бы бакет `secret;x`, а Spring выполнил бы запрос над `secret` и обошёл `Deny`. Ключ с символом `;` клиенты кодируют как `%3B` — это работает |
| ACL через заголовки | `x-amz-acl` (кроме `private`) и `x-amz-grant-*` у `PutObject`, `CopyObject`, `CreateMultipartUpload` требуют ещё и `s3:PutObjectAcl`, у `CreateBucket` — `s3:PutBucketAcl`; `CreateBucket` существующего бакета ACL не меняет |
| Исчерпание потоков | лимиты на ключ 32 записи + 64 чтения (один ключ занимает не больше 96 из 200 потоков), все анонимные запросы вместе — 16; скорость тела запроса и скачивания считается в скользящем окне 30 с (быстрый всплеск не покупает простой); медленный читатель ответа обрывается; nginx: `limit_conn` на адрес, `limit_req` для запросов без подписи, `client_body_timeout`, `send_timeout` |
| Исчерпание диска | заявленные размеры идущих загрузок и копий суммируются (резерв освобождается по окончании запроса); `x-amz-decoded-content-length` учитывается только у aws-chunked; `CopyObject`/`UploadPartCopy` проходят ту же проверку и потолок 5 ГиБ; порог `sectoriadb.storage.min-free-bytes` (1 ГиБ) на томах спула, метаданных и данных даёт `507` заранее, чтобы metastore не остался без места |
| Куча под загрузками | оценка кучи на промежуточные структуры идущих загрузок ограничена долей `upload-heap-fraction` (25 %) максимальной кучи; сверх — `503 SlowDown` |
| Коллизия 64-битного ключа чанка | при коммите чанк, уже проиндексированный другой загрузкой в другом блобе, сравнивается побайтно (длины и CRC32C недостаточно); различие — `503` с повтором, повтор перекладывает чанк с новым ключом |
| Размер multipart-объекта | `Complete` отклоняет объект больше 5 ТиБ и больший, чем помещается в манифест (64 МиБ значения, 8 байт на чанк: около 124 ГиБ при чанке 16 КиБ) — `400 EntityTooLarge` до выделения памяти |
| Вложенный XML | глубина элементов ограничена 32: `400 MalformedXML` вместо `StackOverflowError` |
| Лавина логов отказов | WARN о неудачной аутентификации — не чаще 10 строк за 10 с, остальные считаются в `sectoriadb_s3_auth_failures_total` |
| Идентификаторы | `uploadId` — канонический UUID в нижнем регистре |
| Утечки | ошибки типизированы с фиксированными текстами; текст внутренних исключений клиенту не уходит |

## Модель угроз

| Актор | Может | Не может / замечания |
|---|---|---|
| Аноним | читать публичные объекты и листинг публичных бакетов, писать в `public-read-write` | читать приватное, менять ACL/политики, копировать, multipart |
| Ключ с политикой | то, что разрешает политика (и политики бакетов) | выйти за свои бакеты и действия; изменить свою политику (нет такого API); **исчерпать ресурсы сервера в пределах лимитов на ключ** |
| Ключ без политики | всё (прежнее поведение) | изолироваться от других ключей; подключите политики |
| Атакующий в сети | при HTTP без TLS видит данные и подписанные заголовки; по HTTPS (nginx) — только факт соединения и объём | подделать запрос без секрета, воспроизвести запрос позже окна 15 минут; подмена тела обнаруживается хэшем |
| Доступ к дискам / томам | читает всё: данные, `credentials.json` с секретами в открытом виде | шифрования на диске нет |
| Образы и развёртывание | compose: ротация логов Docker, `no-new-privileges`, `cap_drop: ALL`, `read_only` для сервера и nginx; образы закреплены по digest; журнал nginx без строки запроса (подписи presigned-ссылок), заголовки `Forwarded`/`X-Forwarded-Host`/`X-Forwarded-Port`/`X-Real-IP` от клиента сбрасываются; `error_log` nginx строку запроса печатает; архивы копий (`credentials.json` внутри) создаются с `umask 077`, по умолчанию вне репозитория |
| Порт метрик 9464 | отдаёт метрики без аутентификации | секретов, бакетов и ключей в метриках нет; закройте сетевыми правилами |

## Открытые вопросы

- Нет пользователей, групп, ролей, STS/OIDC и владельца объектов; из `Condition` вычисляются только `Bool` на `aws:SecureTransport` и `StringEquals`/`StringLike` на `s3:prefix`/`s3:delimiter`; нет переменных политик (`${aws:username}`), `NotAction` в `Allow`, версионирования, блокировок объектов, CORS, public access block, POST-формы; ACL — только три готовых значения.
- Ключи без политики по умолчанию имеют полный доступ (совместимость); политика не обязательна, её нужно подключить.
- Секреты ключей хранятся в `credentials.json` в открытом виде (подпись SigV4 требует секрета на сервере).
- Нет шифрования на стороне сервера. Аудит — журнал `oplogs.jsonl`: операции хранилища (запись, чтение, удаление объектов, бакеты, пулы, блобы) с ключом доступа, адресом клиента и `requestId`; отказы в доступе туда не попадают (их видно по метрике `sectoriadb_s3_auth_failures_total` и `WARN` в журнале сервера).
- Не сделано сознательно: фиксированный UID пользователя образа (сломал бы права существующих томов), 128-битный криптографический хэш чанка (формат данных), квоты на число бакетов и открытых multipart-загрузок, ограничение размера работы `DeleteBucket` (это метахранилище, не эта правка).
- Лимиты на ключ не ограничивают число ключей; нет ограничения числа бакетов и открытых multipart-загрузок.
- Эксплуатация: не публикуйте `.env`, `deploy/certs/`, порты 9464, 8080 (без TLS) и 8081 (s3manager с полными правами), не оставляйте `auth.enabled=false` и `allow-open-setup=true` на доступном сервере — [operations.md](../guide/operations.md).
