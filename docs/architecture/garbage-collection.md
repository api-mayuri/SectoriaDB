# Сборка мусора

Удаление и перезапись объекта освобождают только **ссылки** на чанки (`refcount`). Место возвращает сборщик (`maintenance.gc.GarbageCollector`, `SmallBlobCompactor`; планировщик
`GarbageCollectionScheduler` при `sectoriadb.gc.enabled=true`; те же действия вручную командами `gc …`, [admin-shell.md](../guide/admin-shell.md)). Настройки — [configuration.md](../guide/configuration.md).

## Что собирается

| Очередь / признак | Источник | Что делает сборщик | Условие |
|---|---|---|---|
| `chunk_gc` | `refcount` дошёл до нуля | освобождает слот в блобе, удаляет `chunks`, `chunks_by_blob`, строки очереди | строка старше G; запись по-прежнему с `refcount = 0` |
| `chunk_orphans` | коммит нашёл запись индекса на другой блоб | освобождает слот копии | под затвором загрузок; запись не указывает на этот блоб |
| занятый слот без записи индекса | оборванная загрузка (сбой между записью данных и коммитом, ошибка ACL, `TableFull` посреди файла) | освобождает слот | обход блоба (`gc sweep`), под затвором загрузок |
| `deleted_manifests` | замещённая или удалённая версия | для `SMALL` (и малых сегментов `MULTIPART`): `markDeleted` записей, перечисленных в самой строке очереди, затем удаляет строку | строка старше G |
| `small_*.sob` с мёртвыми байтами | пометки `DELETED` | переписывает живые записи в новый файл, переключает манифесты одной транзакцией | доля мёртвых ≥ порога, файл не цель дозаписи |

## Период ожидания G (`gc.grace`, 15 минут)

Мусор моложе G не трогается. Зачем: (1) загрузка, нашедшая чанк с `refcount = 0` в индексе и сравнившая байты, ещё не закоммитила — освобождение слота до её коммита создало бы ссылку на несуществующий чанк;
(2) читатель, идущий по снимку старой версии манифеста, должен дочитать — чанки и запись малого объекта на месте; (3) файл после компакции остаётся до конца G. Загрузка, не уложившаяся в G, не теряет данные:
её коммит получает `COLLECTED` — `503 ServiceUnavailable` с `Retry-After: 1`, клиент повторяет запрос. С `--grace 0s` читатель старой версии получит ошибку (режим администратора и тестов).

## Скорость сборки: сборщик не должен отставать от мусора

Мусор появляется со скоростью удалений и перезаписей (`warp mixed`: около 300 в секунду), а проход идёт раз в `gc.interval`. Любой жёсткий предел на проход — потолок скорости освобождения: выше него очередь, удалённые манифесты за ней
(`manifests`, `manifests_by_blob`) и мёртвые записи файлов малых объектов растут без конца, хотя число объектов постоянно. Именно так `sectoria.db` вырос до 1,2 ГБ за 54 минуты soak-прогона этапа 18:
очередь надгробий (`sectoriadb_gc_queue_length`; в CSV прогона наблюдалась только очередь чанков) не опустошалась, потому что проход брал не больше `max-chunks-per-run` = 10 000 надгробий, тратя около 2,5 мс на `fsync` каждой пометки `DELETED`.
Поэтому:

- **надгробия** собираются все просроченные за один проход, срезами по 2048 строк (префиксный просмотр очереди: ключ `(txId, манифест)` растёт со временем, просмотр кончается на первой строке, которая ещё не просрочена) и транзакциями по `batch-size × 8` строк;
  пометки `DELETED` записей малых объектов не синхронизируются по одной: на пачку — один `fsync` на файл, и только после него удаляются манифесты (порядок «пометка раньше манифеста» сохранён);
- **чанки**: `max-chunks-per-run` остаётся размером прохода, но проход, упёршийся в предел при оставшихся к освобождению чанках, помечает отчёт (`more`), и планировщик сразу запускает следующий (до 20 подряд), не дожидаясь `gc.interval`;
- метрики `sectoriadb_gc_queue_length` (надгробия) и `sectoriadb_chunks_gc_queue_length` в `soak.csv` — столбцы `tombstones` и `gc_queue`: рост любого — сигнал, что сборка отстаёт.

## Освобождение чанка — эксклюзивная транзакция

Кандидаты — ключи, чья **самая новая** строка `chunk_gc` старше G (`dueChunks`); пачками по `gc.batch-size` (16) в одной эксклюзивной write-транзакции (`beginWrite`: исключает все коммиты, `replaceBlob` и другие шаги).
Для каждого чанка внутри транзакции перечитывается состояние: строк очереди нет — пропуск; записи индекса нет — снять строки; `refcount ≠ 0` (оживлён) — снять строки; строка моложе границы — не трогать; иначе
**освободить слот** (`freeSlot`: ACTIVE → DELETED, `fsync`, счётчик заполнения уменьшен — веса размещения видят место сразу), затем удалить `chunks`, `chunks_by_blob`, строки `chunk_gc`.
Замороженный `resize` или заменённый блоб откладывается (`gc_deferred{blob_busy}`). Сбой ввода-вывода слота завершает пачку (сделанное фиксируется), проход повторится. За проход освобождается не больше
`max-chunks-per-run` (10 000). Слот освобождается до правки индекса и фиксации: если фиксация не удалась, остаётся запись с `refcount = 0` без слота — безопасно: загрузка при проверке байт не найдёт чанк и перепишет его на месте.

## Затвор загрузок

Копию без записи индекса нельзя освободить «просто так»: загрузка могла получить её дедупликацией внутри таблицы и ещё не закоммитить. Освобождение слота чанка из очереди `chunk_gc` тоже опирается на затвор: слот освобождается до фиксации метаданных,
и если фиксация не удалась, остаётся запись индекса без слота — загрузка, которая успела проверить байты по этой записи, закоммитила бы ссылку на несуществующую копию. `UploadGate` (по одному состоянию на пул):

- Загрузка берёт `Hold` **до** записи первого байта данных и держит до конца коммита (или `abortStaged` при отказе). Перед тем как опереться на чанк (искать его в индексе, сверять байты, писать в слот), загрузка вызывает `hold.touch(ключ)`;
  `Hold` помнит эти ключи до своего конца.
- Сборщик не осушает пул. Пачка чанков (`gc.batch-size`) **занимает свои ключи** (`tryBeginKeys`): ждёт до `gc.sweep-gate-wait` (2 с) только те загрузки, которые уже трогали один из ключей пачки; ключи, которые загрузка держит и по истечении срока, остаются на следующий проход
  (`gc_deferred{uploads_in_flight}`), остальные освобождаются. Загрузка, которая только собирается тронуть занятый ключ, ждёт конца пачки (миллисекунды), остальные загрузки пачку не замечают и она их.
  Поэтому непрерывные долгие загрузки в один бакет не останавливают сборку: раньше любая загрузка длиннее двух секунд, пересёкшаяся с пачкой, откладывала весь пул, и при непрерывной нагрузке место не возвращалось никогда.
- Тот же порядок для копий без записи индекса (обход блобов, `chunk_orphans`): ключ, тронутый живой загрузкой, ещё не «сирота». Повторная проверка по закоммиченному индексу в эксклюзивной транзакции сохраняется.
- Полное осушение пула (`tryBegin`) осталось у компакции файлов малых объектов: оно нужно один раз на компакцию. Пока идёт пачка с ключами, полное осушение отказывает, и наоборот.
- `Hold` старше `gc.upload-ticket-ttl` (30 минут) сборщик **отзывает**; отозванная загрузка не может закоммититься (`beginCommit()` возвращает `false`, `COLLECTED`/`503`). Начавший коммит `Hold` не отзывается.

## Обход блобов (`gc sweep`, раз в `gc.sweep-interval` = 6 ч)

Для каждого кукушкиного блоба пула (не замороженного и не заменённого) страницами по 512 слотов читаются **только ключи** активных слотов (метаданные в памяти), одной читающей транзакцией находятся ключи без записи индекса
на этот блоб, и они освобождаются под затвором. В конце обхода удаляются неучтённые `small_*.sob` (не открытые, без записи реестра, старше `max(G, 60 с)`). Записи `.sob`, на которые не указывает ни один манифест, освобождаются
переписыванием файла.

## Надгробия и малые объекты

Выведенная из обращения версия **не хранит манифест**: запись в `manifests` (и строки `manifests_by_blob`) удаляется той же транзакцией, что освобождает её чанки. Читателю, уже начавшему старую версию, запись не нужна —
он держит манифест (и снимок MVCC); период G защищает данные (чанки и записи малых объектов), а не запись манифеста. Надгробие — это строка `deleted_manifests`, значение которой несёт всё, что нужно сборщику:
`время(8) 0x01 длинаПула(2) пул n(4) n × [длинаБлоба(2) блоб смещение(8)]` — адреса записей малых объектов (своя запись `SMALL` или малые сегменты `MULTIPART`; для `CHUNKED` и `EMPTY` список пуст).
Раньше манифест-надгробие целиком жил G: под нагрузкой перезаписей это одна запись на каждую версию последних 15 минут (в soak — 250 тыс. записей и 57 тыс. страниц `manifests` при 10 тыс. живых объектов), и каждое дерево, которое копирует коммит, было глубже.
Строки старого формата (`время пул`, без `0x01`; id пула — UUID и с `0x01` не начинается) обрабатываются по-прежнему: сборщик читает оставшийся манифест-надгробие и удаляет его.

Коммит и удаление **не** помечают запись малого объекта `DELETED`: это делает сборщик через G (иначе читатель старой версии получил бы ошибку). Пометка идемпотентна (однобайтовая запись + `fsync`) и выполняется **до**
удаления строки очереди; повреждённая запись — ошибка в лог и удаление надгробия; блоб, которого уже нет (удалён или заменён компакцией), пропускается.

## Компакция малых блобов

Файл с долей мёртвых байтов ≥ `small-compact-dead-percent` (50) и ≥ `small-compact-min-dead-bytes` (1 МиБ), не являющийся целью дозаписи (`smallAppendTarget`):

1. запечатать (дозапись возвращает `null`, писатели выбирают другой файл) и один раз осушить затвор пула — после этого множество записей конечно;
2. снимок живых манифестов файла;
3. копировать 8 потоками в новый, уже запечатанный файл; каждая запись читается с проверкой CRC32C (повреждённая прерывает компакцию);
4. **обмен — одна транзакция** (`swapSmallBlob`): каждый живой манифест (и сегмент `MULTIPART`) должен стоять на старом смещении и перепривязывается к новому файлу; скопированная запись, чья версия выведена из обращения после снимка, — мёртвая копия и помечается `DELETED` в новом файле; запись реестра старого файла удаляется;
5. файл открывается для дозаписи; старый остаётся открытым и удаляется сборщиком через G (читатели старого снимка читают его).

Блоб `.raw` не уменьшается никогда: освобождённые слоты переиспользуются вставками.

## Таблица сбоев

| Момент сбоя | Что остаётся | Чем кончается |
|---|---|---|
| после записи чанков, до коммита | копии без записи индекса | обход освобождает слоты |
| забытая загрузка (поток не вернулся) | `Hold` в памяти | отзыв по TTL; поздний коммит — `503` |
| слот освобождён, транзакция сборщика не зафиксирована | запись `refcount = 0` без слота | следующий проход: слота нет, записи снимаются; опередившая загрузка перепишет чанк на месте |
| `markDeleted` выполнен, надгробие не удалено | запись DELETED, строка очереди на месте | повтор идемпотентен |
| компакция упала до обмена | старый файл авторитетен, новый с неучтёнными копиями | обход находит записи без манифестов и переписывает |
| процесс упал после обмена | старый файл без записи реестра | `deleteUnregistered` (старше G и 60 с, не открыт) |
| `resize` замораживает блоб | блоб `frozen` | чанки откладываются на следующий проход |
| бакет удалён при очередях | записи индекса удалены с бакетом | проход не находит строк |

## Решения и ограничения

- Пачка вместо «транзакции на чанк»: две `fsync` на чанк дали бы около 100 чанков/с и блокировали бы писателей; корректность та же — состояние перечитывается внутри эксклюзивной транзакции (`batch-size=1` — строго по одному).
  При задержках `PUT` на пике уменьшайте `batch-size`.
- Выборка `chunk_gc` читает очередь целиком каждый проход (ключ упорядочен по пулу и ключу, не по времени); выборка надгробий читает только просроченный префикс.
- Удаление бакета и обмен при компакции не читают очередь надгробий целиком: надгробия найдены по индексам (`manifests_by_blob`, `deleted_manifests_by_pool`); строки очереди манифестов, которых уже нет, сборщик снимает сам при очередном проходе.
  `DeleteBucket` убирает пул и записи его блобов одной короткой транзакцией (после неё бакета для клиентов нет), остальное — индекс чанков, надгробия, манифесты пула — пачками по тысяче строк в отдельных транзакциях под записью `pool_purges`;
  оборванное сбоем удаление заканчивает следующий проход сборщика. Записи COMPLETED/ABORTED multipart-загрузок удалённого бакета остаются до обычной очистки по сроку хранения.
- Компакция переключает все живые манифесты файла одной транзакцией: для файла 1 ГиБ из записей по 1 КиБ это около миллиона манифестов; для таких профилей уменьшите `small-object.max-file-bytes`.
- Читатель, держащий старую версию дольше G, может получить ошибку. Слоты карантина и данные блобов, которых нет в реестре, не освобождаются.
- Метрики и алерты — [monitoring.md](../guide/monitoring.md).
