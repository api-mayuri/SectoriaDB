# Этап 02. Безопасность S3-слоя (S1–S5)

Ветка `02-security`, растёт из коммита с `ROADMAP.md`. Затронут только `sectoriadb-server`
(`s3.auth`, `s3.access`, контроллеры); движок хранения (`sectoriadb-core`) не менялся.

## Сводка

| # | Проблема | Исправление | Изменение поведения |
|---|----------|-------------|---------------------|
| S1 | `public-read` бакета открывал анонимное чтение всех объектов | Бакетный ACL даёт только листинг; чтение объекта — по ACL самого объекта или политике бакета | **Да**: анонимный GET объектов в `public-read`-бакете теперь `403` |
| S2 | В политике учитывался только `Allow` | Вычислитель политик в стиле AWS: явный `Deny` побеждает всё | Да: `Deny` начинает действовать; `Allow` с `Condition` перестал действовать |
| S3 | `x-amz-content-sha256` принимался на веру | Хэш тела и подписи фрагментов проверяются при чтении; при несовпадении объект не сохраняется | Да: неверные/обрезанные загрузки отклоняются |
| S4 | Нет ключей — пропускались все запросы | По умолчанию `403`; открытый режим только явным флагом | **Да**: свежий сервер без ключей закрыт |
| S5 | Ожидаемая подпись в debug-логе; ряд мелких проблем | Убрано из логов; проверки области действия, XXE, `uploadId` | Мелкие |

## S1. Бакетный ACL и чтение объектов

**Было.** `AccessControlService.isObjectPublicReadable` возвращал `true`, если бакет `public-read` или
`public-read-write`. В AWS S3 такой ACL разрешает только `ListBucket`; объекты читаются по собственному ACL или
по политике бакета с `s3:GetObject`.

**Стало.** Анонимный `GET`/`HEAD` объекта разрешён, только если (а) объект сам помечен `public-read` /
`public-read-write` либо (б) политика бакета разрешает `s3:GetObject`, и (в) нет явного `Deny`. Листинг
бакета (`GET /bucket`, `HEAD /bucket`) разрешён при `public-read(-write)` либо при `Allow` на `s3:ListBucket`
(ресурс `arn:aws:s3:::bucket`). `public-read-write` по-прежнему даёт анонимную запись и удаление объектов
(`s3:PutObject`, `s3:DeleteObject`), но не чтение.

**Что делать пользователям.** Если вы рассчитывали, что `bucket-acl --acl public-read` отдаёт файлы:
пометьте нужные объекты (`object-acl --acl public-read`) или добавьте политику
`{"Effect":"Allow","Principal":"*","Action":"s3:GetObject","Resource":"arn:aws:s3:::BUCKET/*"}`.
Тесты `S3PublicAccessTest` и тексты `README.md`, `docs/S3-GUIDE.md` обновлены.

## S2. Вычисление политик бакета

Класс `BucketPolicyEvaluator` (`s3.access`). Порядок как в AWS: явный `Deny` по совпавшему оператору
побеждает любой `Allow`; затем `Allow`; иначе «нет решения» (доступ определяют ACL). Явный `Deny` отменяет и
публичные ACL (бакета и объекта).

Поддерживается:

* `Statement` — массив или один объект; `Effect` — `Allow`/`Deny`.
* `Principal`: `"*"`, `{"AWS":"*"}`, `{"AWS":["*", ...]}`. Конкретные ARN анонимным вызовам не соответствуют.
* `Action`, `Resource` — строка или массив; подстановки `*` и `?` (`s3:*`, `s3:Get*`, `arn:aws:s3:::b/docs/*`).
  Имена действий регистронезависимы, ресурсы — нет.
* `NotAction`, `NotResource`, `NotPrincipal` — только в операторах `Deny`.
* Запросы уровня бакета (`ListBucket`) проверяются по ресурсу `arn:aws:s3:::bucket`, а не «по любому ресурсу»
  (раньше `Resource` для листинга не проверялся вовсе).

**Консервативные правила (fail closed):**

| Ситуация | Решение |
|----------|---------|
| `Allow` с блоком `Condition` | не применяется (условия не вычисляются, доступ не выдаётся) |
| `Deny` с блоком `Condition` | **применяется**, как если бы условие выполнялось |
| `Allow` с `NotAction`/`NotResource`/`NotPrincipal` | не применяется |
| Политика не разбирается как JSON | игнорируется целиком (никаких выдач; ACL работают как обычно) |

Последствие для `Deny`: типичный оператор «запретить, если не HTTPS» (`Bool: aws:SecureTransport=false`)
будет запрещать анонимный доступ и по HTTPS. Это осознанная перестраховка.

**Область действия.** Политики вычисляются только для **анонимных** запросов. Запросы с валидной подписью
имеют полный доступ с любым действующим ключом: пользователей/ролей (IAM) в SectoriaDB нет.

## S3. Проверка хэша тела и подписей фрагментов

`SigV4Filter` после проверки подписи заголовков связывает тело с подписанным значением
`x-amz-content-sha256`:

| Значение заголовка | Что делается |
|--------------------|--------------|
| 64 hex-символа | Запрос оборачивается (`VerifiedBodyRequest`): SHA-256 считается во время чтения; на EOF сравнение, при несовпадении `PayloadVerificationException` (наследник `IOException`) → ответ `400 XAmzContentSHA256Mismatch`. Заголовок отсутствует — считается хэш пустого тела. |
| `UNSIGNED-PAYLOAD` | Допускается, если `sectoriadb.s3.auth.allow-unsigned-payload=true` (по умолчанию), иначе `400 InvalidRequest`. |
| `STREAMING-AWS4-HMAC-SHA256-PAYLOAD` | Проверка подписи каждого фрагмента (см. ниже). |
| `STREAMING-AWS4-HMAC-SHA256-PAYLOAD-TRAILER` | То же + подпись трейлера (`x-amz-trailer-signature`). |
| `STREAMING-UNSIGNED-PAYLOAD-TRAILER` | Фрагменты без подписей, трейлер разбирается; подпадает под `allow-unsigned-payload`. |
| другое `STREAMING-*` (например, ECDSA/SigV4a) | `501 NotImplemented` |
| прочее | `400 InvalidArgument` |

**Почему объект не сохраняется.** `S3Support.openBody` читает тело; `FileStorageService.storeStream` копирует
его во временный файл `Files.copy(...)` до EOF и только потом создаёт манифест. Исключение на последнем
`read` (EOF) прерывает копирование до `store(...)`/`manifestRepo.save(...)`; временный файл удаляется в
`finally`. Для загрузки частей multipart (`UploadPart`) аналогично: часть пишется во временный файл и
переименовывается после успешного чтения.

**Подписи фрагментов** (`AwsChunkedInputStream`, контекст `ChunkSigningContext`):

```
sig(N) = HMAC(signingKey, "AWS4-HMAC-SHA256-PAYLOAD\n" + timestamp + "\n" + scope + "\n"
                          + sig(N-1) + "\n" + sha256("") + "\n" + sha256(chunk))
```

`sig(-1)` — подпись самого запроса. Данные фрагмента отдаются читателю только после проверки; поток обязан
закончиться корректным нулевым фрагментом. Раньше разбор был «мягким»: битый размер или обрыв потока молча
считались концом данных (усечённый файл сохранялся). Теперь это `IOException` (`IncompleteBody`, 400).
Подпись трейлера: `HMAC(key, "AWS4-HMAC-SHA256-TRAILER\n" + ts + "\n" + scope + "\n" + sig(последнего) + "\n" +
sha256(канонический трейлер))`.

**Ограничения.** Значение `x-amz-checksum-*` в трейлере с данными не сверяется (подпись трейлера при этом
проверяется). Сигнатуры не проверяются, если авторизация отключена или включён открытый режим. Предпросмотр
(presigned) URL по определению имеют `UNSIGNED-PAYLOAD`. Тело, прочитанное напрямую через `getInputStream()`
(ACL, DeleteObjects), проверяется на уровне запроса так же, как `PutObject`.

## S4. Открытый режим настройки

**Было.** При включённой авторизации и пустом списке ключей пропускались все запросы.

**Стало.** Ответ `403 AccessDenied` с текстом: создайте ключ командой оболочки `mk-key` или задайте
`SECTORIADB_S3_ACCESS_KEY`/`SECTORIADB_S3_SECRET_KEY`. Чтобы вернуть старое поведение — явный флаг
`sectoriadb.s3.auth.allow-open-setup=true`. Оболочка (shell) HTTP не использует, поэтому `mk-key` работает
всегда. `sectoriadb.s3.auth.enabled=false` по-прежнему отключает проверки полностью.

## S5. Прочее

* **Логи.** В debug-лог больше не пишутся ожидаемая и присланная подписи; логируется только идентификатор ключа.
  Тексты, пришедшие от клиента, очищаются от управляющих символов (внедрение строк в лог).
* **Сравнение подписей.** Везде `MessageDigest.isEqual` (постоянное время) с явной кодировкой UTF-8;
  то же для подписей фрагментов.
* **Область действия ключа.** Сервис должен быть `s3`, а область заканчиваться `aws4_request` (иначе 400);
  дата в области должна совпадать с датой `x-amz-date` (и для presigned).
* **Presigned URL.** `X-Amz-Expires` ограничен 1…604800 с (проверка уже была, покрыта тестами); дата из
  будущего более чем на 15 минут → `403 RequestTimeTooSkewed`; истёкший → `403 ExpiredToken`.
* **Сдвиг часов.** ±15 минут для подписи в заголовке (было и раньше; теперь покрыто тестом).
* **`uploadId` в multipart.** Раньше проверялось `UUID.fromString`, который принимает нестрогие формы
  (`1-1-1-1-1`). Теперь только канонический `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx` (строчные hex), и путь
  дополнительно сверяется с каталогом `.multipart`. Ключи объектов в файловую систему не попадают (имена блобов
  и манифестов не зависят от ключа), имена бакетов проверяются при создании.
* **XXE.** Три места создавали `DocumentBuilderFactory` (`DeleteObjects`, `CompleteMultipartUpload`, разбор ACL).
  Все теперь используют `XmlSupport.newSecureDocumentBuilder`: запрещены DOCTYPE, внешние сущности, внешние
  DTD/схемы, XInclude, включена защищённая обработка. `XMLInputFactory`, Jackson-XML и JAXB для разбора запросов
  не используются (Jackson-XML — только для сериализации ответов).

## Открытые вопросы

* Политики не применяются к подписанным запросам (нет IAM); если появятся пользователи с разными правами,
  вычислитель нужно подключить и к ним.
* `Condition` не вычисляются. Для `s3:prefix`-ограничений листинга придётся реализовать операторы условий.
* Сверка `x-amz-checksum-*` с телом не реализована.
