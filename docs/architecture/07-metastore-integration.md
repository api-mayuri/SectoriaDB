# 07. Метаданные в MetaStore: репозитории, индексы, атомарные операции

Этап переносит все метаданные пулов, блобов и манифестов из JSON-файлов в транзакционное хранилище
`org.example.sectoriadb.metastore` (см. [06-btree-metastore.md](06-btree-metastore.md)). Исправляются проблемы
H1–H3 из [ROADMAP.md](ROADMAP.md).

## 1. Spring-бин и жизненный цикл

* `MetaStoreConfig` создаёт бин `MetaStore` по пути `${sectoriadb.meta-dir}/sectoria.db`. Режим `fsync`
  берётся из `sectoriadb.fsync`. Бин имеет `destroyMethod = "close"`: при остановке контекста хранилище закрывается
  и снимает блокировку файла.
* Путь зависит от настроек контекста, поэтому каждый тестовый Spring-контекст с собственным `meta-dir` получает
  своё хранилище и не пересекается с другими. Один файл открывает один процесс: второй сервер на том же каталоге
  завершится с понятным сообщением.
* Репозитории обращаются к хранилищу через `MetaStoreProvider`. Консоль администратора (`sectoriadb.metastore.lazy=true`)
  открывает файл лишь тогда, когда команде он действительно нужен, поэтому команды с ключами доступа работают
  рядом с запущенным сервером.

## 2. Деревья и индексы

Строки в ключах кодируются как `Keys.string`: UTF-8, `0x00` экранируется как `0x00 0xFF`, завершает строку
`0x00 0x01`. Порядок закодированных ключей совпадает с порядком кортежей, а значит, строки сравниваются по байтам
UTF-8, как в S3. Префикс строки без терминатора (`Keys.Builder.stringPrefix`) годится для диапазонного прохода.

| Дерево | Ключ | Значение | Назначение |
|--------|------|----------|------------|
| `pools` | `string(poolId)` | `PoolCodec`: JSON пула | бакеты (пулы) |
| `pools_by_name` | `string(name)` | `poolId` | уникальность имени бакета, поиск по имени |
| `blobs` | `string(blobId)` | `BlobCodec`: JSON блоба | блоб-файлы и файлы малых объектов |
| `blobs_by_pool` | `string(poolId) string(blobId)` | пусто | блобы пула |
| `manifests` | `string(manifestId)` | `ManifestCodec` (ниже) | все версии объектов, живые и удалённые |
| `objects` | `string(bucket) string(objectKey)` | `manifestId` текущей версии | S3-пространство имён, листинг, поиск по ключу |
| `manifests_by_blob` | `string(blobId) string(manifestId)` | пусто | какие манифесты ссылаются на блоб (resize, удаление блоба) |
| `deleted_manifests` | `u64(txId) string(manifestId)` | пусто | очередь сборщика мусора: замещённые и удалённые версии |

`txId` в очереди — номер транзакции, которая вывела манифест из обращения; очередь отсортирована по возрасту.

**Компактные кодеки.** Значение манифеста:
`u8 версия | u32 длина JSON | JSON скалярных полей | u32 число чанков | u64[] ключи чанков (big-endian)`.
Список ключей чанков — бинарный массив (8 байт на чанк вместо 17 в старой hex-строке через запятую); остальные
поля остаются расширяемым JSON. Листинг декодирует манифест без массива ключей (`decode(value, false)`).
Целостность записей обеспечивают CRC32C страниц хранилища и атомарные коммиты, поэтому отдельный CRC метаданных не нужен.

## 3. Границы транзакций по операциям S3

Блобы (данные) пишутся до коммита метаданных и вне транзакции: загрузка может идти минуты, а писатель в
хранилище один. Поэтому в каждой операции, меняющей метаданные, есть ровно одна короткая запись-транзакция.

| Операция | Транзакции |
|----------|-----------|
| PutObject | запись данных в блобы (без транзакции), затем **одна** write-транзакция `commitObject`: проверить, что пул существует; сохранить манифест со всеми полями (ETag, контрольные суммы, ACL, метаданные); записать `manifests_by_blob`; перенаправить `objects[(bucket,key)]`; предыдущую версию пометить `deleted` и поставить в `deleted_manifests`. Контроллеры не удаляют старую версию отдельным шагом, второго `save` нет |
| CopyObject | чтение источника (read-транзакции), затем та же `commitObject` для назначения |
| CompleteMultipartUpload | части склеиваются и пишутся как обычный объект, затем `commitObject` |
| DeleteObject | одна транзакция: `objects.delete`, манифест `deleted`, запись в `deleted_manifests`. Отсутствующий ключ — идемпотентный 204 |
| DeleteObjects | по одной транзакции на ключ; ошибка одного ключа не отменяет остальные (как в S3, где пакет не атомарен) |
| CreateBucket | одна транзакция: `pools` + `pools_by_name`; гонка двух CreateBucket с одним именем заканчивается одним пулом |
| DeleteBucket | одна транзакция: проверить, что в `objects` нет ключей бакета (`BucketNotEmpty`, HTTP 409), удалить блобы пула с `blobs_by_pool`, манифесты блобов, пул и имя. Файлы блобов удаляются после коммита |
| ACL, политика бакета | одна read-modify-write транзакция `updateByName`/`updateCurrent`: параллельные изменения не затирают друг друга |
| Теги | не хранятся (заглушка), транзакций нет |
| Resize, коммит | одна транзакция `replaceBlob`: записать новый блоб, перенаправить все манифесты старого блоба (по `manifests_by_blob`) на новый, обновить индексы, удалить запись старого блоба. Старый файл удаляется после коммита |
| GET, HEAD, листинг, поиск | read-транзакции на снимке; не блокируют писателя |

**Чтение.** `S3Lookup` — два поиска в B+-дереве (`objects`, затем `manifests`), O(log n) и без чтения чужих
манифестов (раньше каждый запрос читал все файлы `manifests/*.json`).

**ListObjects v1/v2.** Диапазонный проход по `objects` от `max(prefix, startAfter)` до `prefixEnd(prefix)`:
* `StartAfter`, `Marker` и `ContinuationToken` исключающие; порядок ключей — UTF-8 побайтовый;
* общие префиксы (`CommonPrefixes`) считаются в `MaxKeys` вместе с ключами;
* `MaxKeys=0` даёт пустой ответ с `IsTruncated=false`;
* при `delimiter` после найденного общего префикса курсор переоткрывается на `prefixEnd(commonPrefix)`: содержимое
  «папки» не обходится, а стоимость страницы зависит от числа возвращаемых записей, а не от размера папок;
* маркер, который сам является общим префиксом (`NextMarker`/токен предыдущей страницы), пропускает весь диапазон
  этого префикса; произвольный `StartAfter`, оканчивающийся не на разделитель, фильтрует по ключам, как в S3;
* `NextMarker` — последний возвращённый ключ или общий префикс.

## 4. Гарантии изоляции

* **Нет грязного чтения.** Читатель работает на снимке (корень дерева на момент начала); незафиксированные страницы
  ему недоступны. Внутри одной read-транзакции индекс `objects` и манифесты согласованы.
* **Нет грязной записи.** Писатель один, транзакции сериализуются; чужие незавершённые изменения не видны и не
  перезаписываются. Откат (`close` без `commit`) не оставляет следов.
* **Нет потерянных обновлений.** Все read-modify-write (PUT, ACL, политика, resize) выполняются в одной
  write-транзакции: чтение предыдущей версии и запись новой не разделены другой записью.
* **Last-writer-wins.** При параллельных PUT одного ключа побеждает транзакция, зафиксированная последней;
  ровно одна версия остаётся живой, все остальные попадают в `deleted_manifests` (требование проверяет тест из
  16 потоков).

## 5. Порядок при сбоях

1. Данные в блобы пишутся **до** коммита метаданных. Блоб без манифеста — безвредный мусор (его уберёт сборщик
   мусора этапа 10); объект не виден, `verify-all` чист.
2. Коммит — переключение мета-страницы хранилища: либо полностью новая версия, либо полностью старая.
3. Побочные действия, зависящие от коммита (пометка записи малого объекта `DELETED`, удаление файла старого блоба
   после resize), выполняются **после** коммита. Сбой между ними оставляет утечку места, но никогда — живой
   объект без данных.

## 6. Каталог `sectoriadb-meta`

До:

```
sectoriadb-meta/
  pools.json          пулы, перезаписывался целиком
  blobs.json          блобы, перезаписывался целиком
  manifests/<id>.json по файлу на каждую версию объекта
  credentials.json
  oplogs.jsonl
```

После:

```
sectoriadb-meta/
  sectoria.db         пулы, блобы, манифесты, индексы, очередь GC
  credentials.json    запись через временный файл, fsync, атомарная замена и fsync каталога
  oplogs.jsonl
```

Миграции со старого формата нет: проект экспериментальный, старые `pools.json`, `blobs.json` и `manifests/`
хранилище игнорирует.

## 7. Как исправлены H1–H3

* **H1** (запись прямо в итоговый файл, битый JSON молча пропускается): метаданные пишутся copy-on-write страницами
  с CRC32C и переключением мета-страницы; JSON-файлы пулов, блобов и манифестов удалены. `credentials.json`
  пишется атомарной заменой с `fsync`.
* **H2** (нет транзакции «новая версия + удаление старой»): `commitObject` меняет указатель `objects` и ставит
  старую версию в очередь GC в одной транзакции; двух живых версий быть не может.
* **H3** (каждый GET и листинг читают все манифесты): поиск и листинг идут по индексам `objects`,
  `manifests_by_blob`, `blobs_by_pool`, `pools_by_name`; полные проходы остались только в административных
  командах (`findAllLive`, `countAndSize`).

## 8. Тесты

* `MetaStoreRepositoriesTest`: каждое дерево и индекс (включая уникальность имени пула), кодеки, `commitObject`,
  удаление, `updateCurrent`, удаление бакета, коммит resize; после операций проверяются кросс-инварианты (`MetaInvariants`).
* `ObjectListingTest`: 4000 ключей с юникодом, суррогатными парами, NUL и символами вокруг `/`; сравнение с наивным
  эталоном для префиксов, разделителей, `startAfter`, страниц разного размера.
* `StorageIntegrationTest`: 16 параллельных PUT одного ключа, перезапуск (закрыть и открыть заново), сбой между
  записью блоба и коммитом (объекта нет, `verify-all` чист).
