# SectoriaDB — архитектурный аудит и план исправлений

Документ ведёт архитектор проекта. Каждый этап — отдельная ветка, растущая из предыдущей:
`01-…` → `02-…` → … → `11-…` Ветку можно смержить в `main` по отдельности, начиная с первой.

## Найденные проблемы (по степени опасности)

### Критические — портят уже сохранённые данные

| # | Где | Проблема | Этап |
|---|-----|----------|------|
| C1 | `CuckooHashTable.insert` | Цикл вытеснений перезаписывает слоты прямо на диске. На последнем шаге бросается `IOException`, а вытесненный чанк остаётся только в локальной переменной: ломается **чужой, ранее записанный** объект. | исправлено в `01-engine-safety` |
| C2 | `CuckooHashTable`, `HashTableCache` | Нет блокировок. Параллельные PUT в один блоб выбирают один и тот же свободный слот, теряют вытесненные чанки, рвут массивы метаданных. | исправлено в `01-engine-safety` |
| C3 | `CuckooHashTable.bucketA/B` | `Math.abs(Long.MIN_VALUE) < 0` → отрицательный индекс корзины → `ArrayIndexOutOfBounds` или запись в чужую корзину. | исправлено в `01-engine-safety` |
| C4 | `FileChannelStorageIOEngine`, `BlobFileWriteService` | Один вызов `read`/`write` без цикла: короткое чтение/запись молча режет байты, слот всё равно помечается ACTIVE. | исправлено в `01-engine-safety` |
| C5 | `FileChannelStorageIOEngine` | Канал открывается на каждый вызов, `force()` нет. После сбоя питания метаданные слота и данные расходятся. | исправлено в `01-engine-safety` |
| C6 | `ResizeService` | Миграция не останавливает запись: чанки, вставленные во время `forEachActiveChunk`, теряются, а манифесты уже переключены на новый блоб. | `10-gc-and-resize` |
| C7 | Дедупликация | Совпадение 64-битного Murmur считается совпадением данных, байты не сравниваются, контрольной суммы на чтении нет. Коллизия → объект молча получает чужой чанк. | исправлено в `03-chunk-integrity` |

### Высокие — потеря метаданных, гонки

| # | Где | Проблема | Этап |
|---|-----|----------|------|
| H1 | `JsonManifestRepository.save` (и pools/blobs) | Запись прямо в конечный файл. Сбой посреди записи → битый JSON → `loadAll` молча пропускает объект. | исправлено в `07-metastore-integration` |

## Целевая архитектура

```
             S3 API (server)
                   │
          ┌────────┴─────────┐
          │  MetaStore (tx)  │  копируемое при записи B+-дерево, один писатель,
          │  B+tree indexes  │  читатели на снимках (MVCC) — нет грязного чтения
          └────────┬─────────┘
                   │ chunkKey → {blobId, crc32c, len, refcount}
          ┌────────┴─────────┐
          │  Pool placement  │  взвешенное rendezvous-хэширование (HRW,
          │  (HRW, weights)  │  «хэш приоритетов») по нескольким блобам пула
          └────────┬─────────┘
        ┌──────────┼──────────┐
     blob_1.raw  blob_2.raw  blob_N.raw   кукушкины таблицы v2: заголовок,
                                          CRC32C на слот, блокировка, fsync
     small_1.sob small_2.sob              журналы малых объектов (< размера чанка): append-only,
                                          CRC32C на запись, восстановление хвоста
```

### Почему copy-on-write B+-дерево, а не WAL + JSON

* Атомарность и стойкость к сбоям даются конструкцией: новые страницы пишутся в свободное место,
  затем `fsync`, затем переключается одна из двух мета-страниц (с номером транзакции и CRC).
  Сбой в любой момент оставляет на диске предыдущий целостный снимок — отдельный журнал не нужен
  (подход LMDB / CouchDB / Btrfs).
* Изоляция: один писатель (сериализуемость), читатели держат корень снимка и никогда не видят
  незафиксированных страниц — защита и от «грязного чтения», и от «грязной записи».
* Индексы — это просто дополнительные деревья в той же транзакции: `(bucket, key) → manifest`,
  `blobId → manifests`, `chunkKey → chunk-запись`. Листинг с префиксом — диапазонный проход по листьям.

### Почему rendezvous-хэширование (HRW) для выбора блоба

Для каждого чанка блоб выбирается как `argmax_b  -w_b / ln(h(chunkKey, b))` — взвешенный HRW.
Свойства:
* при добавлении блоба переезжает только ~1/N чанков (в отличие от `hash % N`);
* веса = свободная ёмкость, поэтому полный блоб естественно получает меньше чанков;
* если первый по приоритету блоб полон, берётся следующий в том же порядке (детерминированный fallback);
* реальное место чанка всё равно записывается в индекс `chunkKey → blobId`, поэтому чтение — один
  поиск в B+-дереве, без перебора блобов; HRW нужен для размещения и дедупликации по пулу.

## Этапы

| Ветка | Содержание |
|-------|------------|
| `01-engine-safety` | C1–C5: атомарная вставка в кукушку (поиск пути вытеснений в памяти, перенос с конца), блокировка на блоб, `floorMod`, полные read/write, постоянный канал и `fsync`. |
| `02-security` | S1–S5. |
| `03-chunk-integrity` | C7: формат блоба v2 (заголовок, CRC32C и длина в слоте), XXH64-ключи чанков, размер чанка 16 КиБ, проверка на чтении, сравнение байт при дедупе, повторный хэш с солью при коллизии. |
| `04-small-objects` | Объекты меньше размера чанка не режутся и не попадают в кукушку: хранятся целиком в `small_*.sob` (append-only журнал с CRC32C, восстановление хвоста, откат по размеру); пустые объекты — только манифест. |
| `05-object-checksums` | Сквозная проверка целостности объекта: S3-контрольные суммы при загрузке (`x-amz-checksum-*`, заголовок и trailer aws-chunked, `Content-MD5`), CRC32C всего объекта в манифесте и проверка при каждом полном чтении, составные суммы multipart, `verify`/`verify-all` в консоли. |
| `06-btree-metastore` | Собственное транзакционное хранилище метаданных: страничное copy-on-write B+-дерево, MVCC-снимки, API транзакций. |
| `07-metastore-integration` | H1–H3: репозитории поверх MetaStore, индексы, атомарная замена версии объекта, листинг диапазонным проходом (CRC метаданных даёт сам MetaStore). |
| `08-observability-bench` | Метрики Prometheus (готово, см. раздел «Метрики»), нагрузочные тесты warp, InfluxDB, дашборды Grafana, тесты отказов и совместимости. |
| `09-multi-blob-pool` | Несколько блобов в пуле, взвешенное rendezvous-хэширование (HRW, «хэш приоритетов»), индекс чанков с refcount. |
| `10-gc-and-resize` | H4, C6: подсчёт ссылок, освобождение слотов, сборка очереди `deleted_manifests`, компакция `small_*.sob` (по счётчикам live/dead байт), безопасное расширение под блокировкой. |
| `11-review-refactor` | Финальное код-ревью и рефакторинг: импорты, чистый код, модульность. |

Подробности каждого этапа — в `docs/architecture/NN-*.md` соответствующей ветки.
