# SectoriaDB — архитектурный аудит и план исправлений

Документ ведёт архитектор проекта. Каждый этап — отдельная ветка, растущая из предыдущей:
`01-…` → `02-…` → `03-…` и т.д. Ветку можно смержить в `main` по отдельности, начиная с первой.

## Найденные проблемы (по степени опасности)

### Критические — портят уже сохранённые данные

| # | Где | Проблема |
|---|-----|----------|
| C1 | `CuckooHashTable.insert` | Цикл вытеснений перезаписывает слоты прямо на диске. На последнем шаге бросается `IOException`, а вытесненный чанк остаётся только в локальной переменной: ломается **чужой, ранее записанный** объект. |
| C2 | `CuckooHashTable`, `HashTableCache` | Нет блокировок. Параллельные PUT в один блоб выбирают один и тот же свободный слот, теряют вытесненные чанки, рвут массивы метаданных. |
| C3 | `CuckooHashTable.bucketA/B` | `Math.abs(Long.MIN_VALUE) < 0` → отрицательный индекс корзины → `ArrayIndexOutOfBounds` или запись в чужую корзину. |
| C4 | `FileChannelStorageIOEngine`, `BlobFileWriteService` | Один вызов `read`/`write` без цикла: короткое чтение/запись молча режет байты, слот всё равно помечается ACTIVE. |
| C5 | `FileChannelStorageIOEngine` | Канал открывается на каждый вызов, `force()` нет. После сбоя питания метаданные слота и данные расходятся. |
| C6 | `ResizeService` | Миграция не останавливает запись: чанки, вставленные во время `forEachActiveChunk`, теряются, а манифесты уже переключены на новый блоб. |
| C7 | Дедупликация | Совпадение 64-битного Murmur считается совпадением данных, байты не сравниваются, контрольной суммы на чтении нет. Коллизия → объект молча получает чужой чанк. |

### Высокие — потеря метаданных, гонки

| # | Где | Проблема |
|---|-----|----------|
| H1 | `JsonManifestRepository.save` (и pools/blobs) | Запись прямо в конечный файл. Сбой посреди записи → битый JSON → `loadAll` молча пропускает объект. |
| H2 | `S3ObjectController`/`FileStorageService` | Нет транзакции «новая версия + удаление старой». Два PUT одного ключа видят одну и ту же старую версию → две «живые» версии. |
| H3 | `JsonManifestRepository.findAll` | Каждый GET и листинг читает **все** манифесты всех бакетов: O(N) с диска на каждый запрос. Нет индексов. |
| H4 | Удаление | `DELETED` в слотах не выставляется, место не возвращается; счётчиков ссылок на чанки нет. |

### Безопасность

| # | Где | Проблема |
|---|-----|----------|
| S1 | `AccessControlService.isObjectPublicReadable` | `public-read` бакета разрешает анонимный GET любого объекта (в AWS он даёт только листинг). |
| S2 | Разбор bucket policy | Учитывается только `Effect=Allow`, явный `Deny` игнорируется. |
| S3 | `SigV4Filter` | Хэш тела не проверяется: `x-amz-content-sha256` берётся на веру. |
| S4 | `SigV4Filter` | При отсутствии ключей пропускаются все запросы (открытый режим). |
| S5 | `SigV4Filter` | В debug-лог пишется ожидаемая подпись. |

## Целевая архитектура

```
             S3 API (server)
                   │
          ┌────────┴─────────┐
          │  MetaStore (tx)  │  копируемое при записи B+-дерево, один писатель,
          │  B+tree indexes  │  читатели на снимках (MVCC) — нет грязного чтения
          └────────┬─────────┘
                   │ chunkKey → {blobId, crc32c, len, refcount}
          ┌────────┴─────────┐
          │  Pool placement  │  взвешенное rendezvous-хэширование (HRW,
          │  (HRW, weights)  │  «хэш приоритетов») по нескольким блобам пула
          └────────┬─────────┘
        ┌──────────┼──────────┐
     blob_1.raw  blob_2.raw  blob_N.raw   кукушкины таблицы v2: заголовок,
                                          CRC32C на слот, блокировка, fsync
```

### Почему copy-on-write B+-дерево, а не WAL + JSON

* Атомарность и стойкость к сбоям даются конструкцией: новые страницы пишутся в свободное место,
  затем `fsync`, затем переключается одна из двух мета-страниц (с номером транзакции и CRC).
  Сбой в любой момент оставляет на диске предыдущий целостный снимок — отдельный журнал не нужен
  (подход LMDB / CouchDB / Btrfs).
* Изоляция: один писатель (сериализуемость), читатели держат корень снимка и никогда не видят
  незафиксированных страниц — защита и от «грязного чтения», и от «грязной записи».
* Индексы — это просто дополнительные деревья в той же транзакции: `(bucket, key) → manifest`,
  `blobId → manifests`, `chunkKey → chunk-запись`. Листинг с префиксом — диапазонный проход по листьям.

### Почему rendezvous-хэширование (HRW) для выбора блоба

Для каждого чанка блоб выбирается как `argmax_b  -w_b / ln(h(chunkKey, b))` — взвешенный HRW.
Свойства:
* при добавлении блоба переезжает только ~1/N чанков (в отличие от `hash % N`);
* веса = свободная ёмкость, поэтому полный блоб естественно получает меньше чанков;
* если первый по приоритету блоб полон, берётся следующий в том же порядке (детерминированный fallback);
* реальное место чанка всё равно записывается в индекс `chunkKey → blobId`, поэтому чтение — один
  поиск в B+-дереве, без перебора блобов; HRW нужен для размещения и дедупликации по пулу.

## Этапы

| Ветка | Содержание |
|-------|------------|
| `01-engine-safety` | C1–C5: атомарная вставка в кукушку (поиск пути вытеснений в памяти, перенос с конца), блокировка на блоб, `floorMod`, полные read/write, постоянный канал и `fsync`. |
| `02-security` | S1–S5. |
| `03-chunk-integrity` | C7: формат блоба v2 (заголовок, CRC32C и длина в слоте), проверка на чтении, сравнение байт при дедупе, повторный хэш с солью при коллизии. |
| `04-btree-metastore` | Собственное транзакционное хранилище метаданных: страничное copy-on-write B+-дерево, MVCC-снимки, API транзакций. |
| `05-metastore-integration` | H1–H3: репозитории поверх MetaStore, индексы, атомарная замена версии объекта, миграция из JSON. |
| `06-multi-blob-pool` | Несколько блобов в пуле, взвешенный HRW, индекс чанков с refcount. |
| `07-gc-and-resize` | H4, C6: подсчёт ссылок, освобождение слотов, безопасное расширение под блокировкой. |

Подробности каждого этапа — в `docs/architecture/NN-*.md` соответствующей ветки.
