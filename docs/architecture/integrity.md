# Целостность данных

Объект проверяется на каждом участке пути — от клиента до диска и обратно.

| # | Слой | Что защищает | Кто проверяет и когда | При несовпадении |
|---|---|---|---|---|
| 1 | SigV4 | тело не подменено в пути | `x-amz-content-sha256` (`Sha256VerifyingInputStream`), подписи фрагментов и trailer в `aws-chunked` (`AwsChunkedInputStream`) — при загрузке | `400 XAmzContentSHA256Mismatch` / `403 SignatureDoesNotMatch`, объект не сохраняется |
| 2 | S3-суммы | клиент и сервер видят одни байты | `x-amz-checksum-*` (заголовок или trailer), `Content-MD5` (`MultiDigestInputStream`) — до фиксации | `400 BadDigest`, ничего не записано |
| 3 | CRC32C чанка / записи | диск не исказил чанк кукушки или запись `.sob` | при каждом чтении, в том числе `Range`; слот: длина + CRC32C данных, запись `.sob`: CRC заголовка и данных | `ChunkCorruptedException` / `SmallObjectCorruptedException` → `500` или обрыв |
| 4 | CRC32C всего объекта | состав и порядок чанков, манифест указывает на «те» данные | пишется всегда; проверяется при каждом **полном** чтении (`GET`, источник `CopyObject`/`UploadPartCopy`, `restore`) | `GET` обрывается, копирование — `500` без фиксации |
| 5 | CRC страниц метахранилища | манифесты, реестры, индексы | при каждом чтении страницы; плюс CRC метаданных слота и мета-страницы | `CorruptedPageException`, слот в карантине |

Слой 3 ловит порчу байтов на диске; слой 4 — то, чего слой 3 не видит (чанк цел, но манифест ссылается не на тот: подмена списка ключей, обрезанный список, неверный размер последнего чанка); слой 2 замыкает кольцо
с клиентской стороны.

## Алгоритмы

`ChecksumAlgorithm`: `CRC32`, `CRC32C`, `CRC64NVME` (собственная реализация, полином `0xAD93D23594C93659` в отражённой форме), `SHA1`, `SHA256`; значение — base64 от digest big-endian. Один проход по байтам (`MultiDigest`) считает MD5 (ETag),
CRC32C объекта и сумму клиента.

## Загрузка

- Разбор заголовков (`S3Checksums.parse`): `x-amz-checksum-<alg>`, `x-amz-sdk-checksum-algorithm`/`x-amz-checksum-algorithm`, `x-amz-trailer`, `Content-MD5`. Несколько сумм (или сумма + trailer), несовпадающие алгоритмы, неизвестный
  алгоритм, значение не той длины — `400 InvalidRequest`; плохой `Content-MD5` — `400 InvalidDigest`. Алгоритм без значения — сервер считает и сохраняет сам.
- Trailer: значение, пришедшее после тела, сверяется с посчитанным; не объявленный в `x-amz-trailer` или отсутствующий объявленный — `400 InvalidRequest`. Порядок проверок подписанного trailer: подписи фрагментов → подпись trailer → сумма
  (подмена trailer — `403`, честно подписанная неверная сумма — `400 BadDigest`).
- **Проверка до фиксации.** Тело сначала в временный файл; сверка стоит между копированием и записью в блобы/манифест, поэтому при несовпадении не создаётся ничего (ни записи `.sob`, ни чанков, ни манифеста); прежняя версия остаётся.
- **SigV4 payload:** `x-amz-content-sha256` из 64 hex-символов проверяется потоково (`PayloadVerificationException` на EOF); `UNSIGNED-PAYLOAD` и `STREAMING-UNSIGNED-PAYLOAD-TRAILER` допустимы при `allow-unsigned-payload=true`;
  подпись каждого фрагмента: `HMAC(signingKey, "AWS4-HMAC-SHA256-PAYLOAD\n" + ts + "\n" + scope + "\n" + sig(N-1) + "\n" + sha256("") + "\n" + sha256(chunk))`; данные фрагмента отдаются читателю только после проверки,
  поток обязан закончиться нулевым фрагментом (обрыв — `IncompleteBody`, 400); длина сверяется с `x-amz-decoded-content-length`. Другие `STREAMING-*` (SigV4a) — `501`.

## Хранимые суммы

В манифесте: `crc32c` (CRC32C объекта, base64 big-endian) — **всегда**; `checksumAlgorithm`/`checksumValue`/`checksumType` (`FULL_OBJECT` или `COMPOSITE`, у `COMPOSITE` значение с суффиксом `-N`) — если клиент выбрал алгоритм.
`CopyObject` сохраняет алгоритм источника (если `FULL_OBJECT`) и пересчитывает значение по скопированным байтам.

## Multipart

Тип по умолчанию как в S3: `COMPOSITE` для CRC32/CRC32C/SHA1/SHA256, `FULL_OBJECT` для CRC64NVME; недопустимые сочетания — `400 InvalidRequest`. Суммы частей хранятся в `mpu_parts`; `Complete` сверяет `<ChecksumXXX>` из запроса
с хранимыми (`BadDigest`/`InvalidPart`) и вычисляет сумму объекта по значениям частей без чтения данных ([metadata-model.md](metadata-model.md)). Часть без суммы при заданном алгоритме загрузки сервер считает сам (мягче AWS); часть с другим алгоритмом
отвергается.

## Чтение

- `HEAD` и полный `GET` с `x-amz-checksum-mode: ENABLED` отдают `x-amz-checksum-<alg>` и `x-amz-checksum-type`: сумму клиента или (иначе) CRC32C объекта `FULL_OBJECT`. Для `Range` и `?partNumber` не отдаются.
- Полное чтение пересчитывает CRC32C по ходу и сверяет в конце. Для `SMALL` проверка идёт до единственной записи в выход, для `CHUNKED`/`MULTIPART` — **до записи последнего чанка**: при несовпадении потребитель не получает последние
  ≤ `chunkSize` байт, и клиент с `Content-Length` видит сбой передачи, а не «успешный» повреждённый файл. В лог — `ERROR Whole-object CRC32C mismatch: bucket=… key=… manifest=…`.
  Ответ ещё не отправлен — `500`; заголовки ушли — `ResponseAbortedException`, соединение закрывается. Начальные уже отправленные байты вернуть нельзя (HTTP): клиентам стоит сверять сумму (`checksum-mode`).
- `Range` не читает объект целиком и опирается только на слой 3.

## Консоль

`verify --id` перечитывает объект и проверяет слои 3 и 4, сумму клиента (`FULL_OBJECT`; составную без границ частей не пересчитать) и MD5 против ETag (не multipart). `verify-all [--pool]` — все живые объекты, итог
`RESULT: OK` или `RESULT: FAILED`. `scrub --id` проверяет все слоты/записи блоба. Метрика `sectoriadb_integrity_crc_failures_total{kind}` растёт при любом провале. Сопоставление с кодом — `ObjectVerificationService`.

## Ограничения

Составные суммы `verify` не пересчитывает; сброшенные в карантин слоты не ремонтируются; различия с AWS (CRC32C по умолчанию вместо CRC64NVME, мягкий режим части без суммы) перечислены выше.
