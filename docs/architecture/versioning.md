# Версионирование бакетов и lifecycle (ADR, этап 24)

> Решение принято 2026-10-29 перед реализацией. Причина: случайный `DELETE` или перезапись сейчас откатываются только из резервной копии.

## Контекст

`objects` указывает на текущую версию ключа; при перезаписи и удалении прежняя версия «выводится из обращения» (`Trees.retire`): манифест
удаляется сразу, ссылки на чанки освобождаются, адреса записей малых объектов уходят в очередь сборщика (этап 19). Версионирование требует,
чтобы прежние версии жили, пока их явно не удалят или не истечёт правило lifecycle.

## Решение

1. **Состояние бакета** — поле `versioning` записи пула: нет (никогда не включали), `Enabled`, `Suspended`. Выключить совсем нельзя (как в S3).
2. **`objects` не меняет смысла:** текущая *живая* версия ключа. Если последняя версия — маркер удаления, записи в `objects` нет. Все
   существующие пути (GET, HEAD, листинг, multipart, ACL, сборщик) работают как прежде.
3. **Дерево `versions`**: ключ `(бакет, ключ, u64 обратный номер)` — версии ключа от новой к старой; значение — вид (версия или маркер),
   `versionId`, id манифеста (для версии), время. Индекс `version_ids`: `(бакет, ключ, versionId)` → обратный номер.
   Номер — монотонный счётчик хранилища (`stats`), обратный (`Long.MAX_VALUE − n`), чтобы обход шёл от новых.
4. **`versionId`** версии — id её манифеста (UUID, непрозрачная строка, как у S3); у маркера — свой UUID. Объект, записанный без
   версионирования или при `Suspended`, имеет версию `null`; текущая `null`-версия в `versions` не записана (инвариант: если текущий манифест
   без `versionId`, он новейший), а при вытеснении записывается туда строкой с `versionId = "null"`.
5. **Прежние версии не выводятся из обращения:** их манифесты и ссылки на чанки остаются; `retire` вызывается только при окончательном
   удалении версии (`DELETE ?versionId`, lifecycle, `Suspended`-перезапись `null`-версии). Дальше всё как раньше: надгробие, сборщик, грейс.
6. **Операции:**

   | Операция | Нет версионирования | `Enabled` | `Suspended` |
   |---|---|---|---|
   | PUT | как раньше | новая версия; прежняя текущая остаётся (`null` — строкой в `versions`) | новая версия `null`; прежняя `null` удаляется, настоящая остаётся |
   | DELETE без `versionId` | как раньше | маркер удаления новейшим, `objects` без записи | маркер `null` (прежняя `null`-версия удаляется) |
   | DELETE `?versionId` | `null` — как DELETE | версия или маркер удаляются окончательно; если удалена новейшая — текущей становится следующая версия (маркер — объект «удалён») | так же |
   | GET/HEAD `?versionId` | `null` — текущая | указанная версия; маркер — `405` с `x-amz-delete-marker: true` | так же |

7. **Lifecycle** (подмножество S3): правила с `Filter/Prefix`, `NoncurrentVersionExpiration/NoncurrentDays` (версия становится
   нетекущей в момент появления более новой) и `Expiration/ExpiredObjectDeleteMarker` (маркер, у которого не осталось версий). Хранится в записи
   пула; применяется проходом по `versions` в планировщике сборщика, пачками. Остальные элементы lifecycle — `501 NotImplemented`
   при `PutBucketLifecycleConfiguration` (не молча игнорируются).
8. **Формат хранилища 3:** новые деревья создаются по мере использования, существующие записи не меняются — миграция 2 → 3 пустая, номер
   поднимается, чтобы сборка версии 2 не открыла хранилище с версиями (она бы не знала о `versions` и удалила бы данные прежних версий сборщиком).

## Последствия

- Место: при `Enabled` перезаписи не освобождают место, пока нет правила lifecycle — это ожидаемо и указано в документации; метрика
  `sectoriadb_metastore_tree_entries{tree="versions"}` показывает число версий и маркеров.
- `DeleteBucket` отказывает (`BucketNotEmpty`), пока у бакета есть версии или маркеры.
- Не делается: блокировки объектов (Object Lock), MFA Delete, правила lifecycle для текущих версий по возрасту (`Expiration/Days`),
  переходы классов хранения.
