# Метахранилище

Модуль `sectoriadb-metastore`: встраиваемое key-value хранилище в одном файле `sectoria.db` — именованные B+-деревья, ACID-транзакции, снимки (MVCC).
Зависит только от JDK и slf4j; события наблюдаемости отдаёт через `MetaStoreListener`. Файл открывает один процесс (`FileLock`), второй сервер на том же каталоге не стартует.
Какие деревья и ключи использует SectoriaDB — [metadata-model.md](metadata-model.md).

## Файл

Страницы фиксированного размера `pageSize` (степень двойки 512…65536, по умолчанию 4096; хранится в файле и для существующего файла побеждает). Страница `id` лежит по смещению `id * pageSize`.

**Мета-страницы (0 и 1).** magic `SECTMETA` · версия формата (1) · `pageSize` · `txId` последней зафиксированной транзакции · корень каталога деревьев · первая страница цепочки freelist ·
`pageCount` (граница выделенных страниц) · CRC32C `[0, 48)`. Транзакция `T` пишет мета-страницу в слот `T % 2`, поэтому одна из двух копий всегда цела. При открытии слот игнорируется, если
magic/версия/CRC неверны или `pageCount * pageSize` больше файла; берётся слот с большим `txId`. Нет годных слотов — `CorruptedPageException`.

**Остальные страницы:** общий заголовок 8 байт — CRC32C `[4, pageSize)`, тип (1 лист, 2 ветвь, 3 overflow, 4 freelist), `count`. CRC проверяется при **каждом** чтении страницы.

- Лист: записи `keyLen u16 | key | kind u8 | (valLen u16 | value  либо  head u64 | length u64)`. Значение внутри листа, если запись не больше `(pageSize − 8) / 4`; иначе в цепочке overflow-страниц (до 64 МиБ). Пустые значения всегда внутри листа.
- Ветвь: `child0 u64`, затем пары `key | child`; `child[i]` содержит ключи `< keys[i]`.
- Freelist: записи `pageId u64 | groupTxId u64` (0 — свободна сразу; иначе освобождена транзакцией `groupTxId` и ждёт, пока её перестанут читать снимки).
- Каталог деревьев — тоже B+-дерево: имя дерева → `rootPageId u64 | entryCount u64`.

## Дерево

Порядок ключей — беззнаковое лексикографическое (`Arrays.compareUnsigned`). Ключ до 2 КиБ, но не более `(pageSize − 8) / 3 − 24` (в узел всегда помещаются три максимальные записи). Деление узла — в точке,
минимизирующей больший из двух размеров по байтам. Слияние после удаления, если узел меньше `pageSize / 4` и результат помещается; заимствования у соседа нет (возможны недогруженные узлы — корректность не страдает).
Сестринских указателей нет (при COW их обновление копировало бы соседей); курсор — стек «корень → лист», любая модификация инвалидирует курсор внутри write-транзакции.

`Keys` — композитные ключи с сохранением порядка: строка в UTF-8 (`0x00` экранируется как `0x00 0xFF`, терминатор `0x00 0x01` — одна строка не является префиксом другой), `longUnsigned`/`longSigned` (8 байт big-endian),
`raw` (только последним компонентом), `Keys.prefixEnd` для верхней границы префикса.

## Copy-on-write и коммит

Write-транзакция **никогда** не меняет страницу, достижимую из зафиксированного корня: узел копируется на новую страницу (из свободных или `pageCount++`), копируются родители до корня. Страницы, выделенные самой транзакцией,
правятся на месте. Коммит транзакции `T = txId + 1`:

1. изменённые корни и счётчики деревьев записываются в каталог;
2. освобождённые транзакцией страницы (и старая цепочка freelist) попадают в группу `T`;
3. строится новая цепочка freelist;
4. записываются все грязные страницы;
5. `FileChannel.force` — **барьер 1**: данные на диске;
6. записывается мета-страница в слот `T % 2` (меньше 64 байт в одном секторе, CRC делает рваную запись обнаружимой);
7. `force` — **барьер 2**;
8. новое состояние публикуется читателям (volatile-ссылка).

Транзакция без изменений ничего не пишет. Сбой на шагах 1–5 оставляет файл, открывающийся как предыдущий коммит; после барьера 2 коммит состоялся целиком. Свободными для повторного использования транзакцией `T` считаются
только страницы, недостижимые из корня `T−1` и его freelist, поэтому откат на `T−1` всегда видит целые данные. Страницы, освобождённые транзакцией `U`, возвращаются в оборот, когда `min(txId живых читателей, последний коммит) ≥ U`;
долгоживущий читатель удерживает страницы своего снимка (файл растёт), поэтому читающие транзакции закрывают всегда. Файл не усекается; freelist переписывается целиком на каждом коммите (16 байт на свободную страницу).

**Диагностика.** `MetaStore.stats()` отдаёт `oldestReaderMillis` — возраст самой старой открытой читающей транзакции (метрика `sectoriadb_metastore_oldest_reader_seconds`); читатель, закрытый после пяти секунд, пишет в лог `WARN … kept every page freed meanwhile`
(`-Dsectoriadb.metastore.trace-readers=true` добавляет стек места, где он начат). `MetaStore.treeStats()` — страницы каждого дерева и заполнение листьев (в прогонах заполнение 0,5–0,7: слияния без заимствования недогружают узлы, но стабильно).

**Рост файла на длительной нагрузке — разбор (этап 19).** Проверены гипотезы «читатель удерживает страницы», «стоимость freelist», «раздутие деревьев». В soak-прогонах читателей дольше секунд не было (`live_readers` 0–5, предупреждений нет), свободных страниц в обычное время 150–700 (страницы
переиспользуются сразу), заполнение листьев стабильно. Рос **объём живых деревьев**: за 7 минут прогона с `gc.grace=1m` при 9997 живых объектах в `manifests` было 87 417 записей (24 тыс. страниц из 30 тыс.), в очереди надгробий 77 420: сборщик освобождал не больше 10 000 надгробий за проход,
а удалений было около 280 в секунду. Причина и исправление — [garbage-collection.md](garbage-collection.md#скорость-сборки-сборщик-не-должен-отставать-от-мусора). Кратковременные скачки свободных страниц (десятки тысяч сразу) дают массовые операции (компакция файла малых объектов переписывает манифесты одной транзакцией);
пока такой объём свободен, каждый коммит переписывает freelist целиком (около 1,5 МБ на 90 тыс. страниц) — остаётся известным ограничением.

## Изоляция

Одна write-транзакция одновременно, любое число read-транзакций на снимках. Исключены грязное и неповторяющееся чтение, фантомы (снимок неизменяем), грязная запись и потерянное обновление
(read-modify-write внутри write-транзакции атомарен), рваные чтения нескольких деревьев (снимок общий). Запись сериализуема; write skew возможен, только если решение принято по чтению вне write-транзакции.
Read-транзакция и курсор — не потокобезопасны (один поток).

## Групповой коммит

Единственный писатель был пределом записи: коммит одной транзакции (два `fsync`) стоит почти столько же, сколько десяти. API `submit(body)` / `writeGrouped(body)` ставит тело записи в ограниченную очередь
(`queue-capacity`); поток `metastore-committer`:

1. берёт первое тело, **занимает слот писателя**, и только потом забирает всё накопившееся (до `max-batch-size`; искусственной задержки нет, `max-wait-micros = 0`);
2. открывает **одну** `WriteTxn` и применяет тела строго по очереди, каждое в точке сохранения (savepoint);
3. коммитит один раз и **только после этого** завершает будущие.

Тело, бросившее исключение, откатывается к своей точке сохранения без влияния на соседей (`sectoriadb_metastore_group_body_rollbacks_total`); итог равен последовательному выполнению в порядке очереди.
Откат основан на эпохах узлов (грязный узел старой эпохи копируется перед правкой) и на отложенном повторном использовании страниц, освобождённых телом. Тело не может вызвать `commit()` и вложенный `submit`.
Читатели видят состояние до пачки или после неё целиком. Размер пачки ограничен числом тел и страниц (`max-batch-pages`). Тело выполняется в потоке коммиттера — оно должно быть коротким и без блокирующего ввода-вывода.
Монопольными (через `beginWrite`) остаются редкие операции: удаление бакета, `replaceBlob`, освобождение чанков сборщиком. Поток коммиттера переживает прерывания и перезапускается.

## Сбой коммита и восстановление на месте

Копирование при записи оставляет закоммиченный снимок целым при любом сбое, поэтому «отравляется» только сторона записи:

- Чтение продолжается по последнему успешному коммиту.
- Запись отказывает (`MetaStoreUnavailableException`, в S3 — `503 SlowDown` или `507` при `No space left on device`), пока не восстановится. `beginWrite` (и коммиттер в начале пачки) под слотом писателя:
  выдерживает паузу `recovery-backoff` (1 с), читает обе мета-страницы, **стирает** мета-страницу неудавшегося коммита (иначе после сбоя процесса она указывала бы на перезаписанные страницы) и при необходимости переписывает
  мета-страницу снимка из памяти, перестраивает состояние свободных страниц из сохранённой цепочки freelist, откатывает `pageCount`, снимает признак отравления (один `fsync`). Любая неудача оставляет хранилище отравлённым.
- Метрика: `sectoriadb_metastore_recoveries_total{result}`; в логе `Metadata store recovered after a failed commit`. Перезапуск нужен, только если диск не оживает.

## Проверка целостности

`verify()` блокирует писателей и проверяет CRC всех достижимых страниц, строгий порядок ключей и границы диапазона, одинаковую глубину листьев, отсутствие пустых листьев, размеры узлов, число записей против каталога,
длины overflow-цепочек и что каждая страница `[2, pageCount)` учтена ровно один раз (дерево / overflow / freelist / свободна).

## Ограничения

Значение целиком в памяти (`byte[]`, до 64 МиБ); грязные узлы write-транзакции держатся в памяти до коммита; нет межпроцессного доступа; страницы читаются без собственного кэша (опора на page cache ОС);
файл не усекается; ошибки ввода-вывода внутри чтения — `UncheckedIOException`.
