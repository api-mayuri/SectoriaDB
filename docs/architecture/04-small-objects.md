# Этап 04 — малые объекты

Ветка `04-small-objects`, растёт из `03-chunk-integrity`. Обратная совместимость со старыми данными не требуется (решение
владельца), но существующие JSON-поля продолжают читаться: новые поля имеют значения по умолчанию.

## 1. Зачем

Размер чанка теперь 16 КиБ (корзина из 4 слотов = 64 КиБ). Если класть в такую таблицу объект в 200 байт:

* он занимает **целый слот 16 КиБ** — потеря места в десятки раз (иконки, JSON, миниатюры, пустые «папки»);
* каждый такой объект создаёт нагрузку на кукушку: слот, запись метаданных с двумя `fsync`, вытеснения, рост заполненности,
  автоматический `resize` гигабайтной таблицы из-за тысяч крошечных файлов.

Поэтому **объекты меньше размера чанка (`sectoriadb.default-chunk-size`) вообще не проходят через чанкинг и кукушку**: они
хранятся целиком, одной записью, в отдельном виде блоба — **файле малых объектов** (small-object blob, SOB). Нулевой объект
не хранится нигде.

## 2. Как выбирается способ хранения

`FileStorageService.store`/`storeStream` (CopyObject и Complete Multipart идут через `storeStream`, поэтому подчиняются тем же
правилам): после того как тело записано во временный файл и размер известен —

| Размер | `storageKind` | Где |
|---|---|---|
| 0 | `EMPTY` | только манифест, ни блоба, ни слотов |
| `1 .. chunkSize-1` | `SMALL` | одна запись в `small_*.sob` пула |
| `>= chunkSize` | `CHUNKED` | как раньше: кукушкина таблица |

Граница строгая: объект ровно в `chunkSize` байт — уже `CHUNKED`. Порог — `props.getDefaultChunkSize()`; если оно больше 64 МиБ
(предел одной записи, запись буферизуется в памяти), крупнее 64 МиБ объекты остаются `CHUNKED`.

### Манифест

`ManifestEntity` получил поля (старые манифесты без них читаются как `CHUNKED`):

| Поле | Значение |
|---|---|
| `storageKind` | `CHUNKED` (по умолчанию) / `SMALL` / `EMPTY` |
| `poolId` | пул объекта (нужен для `EMPTY`, у которого нет блоба) |
| `smallBlobId`, `smallOffset`, `smallLength`, `smallCrc32c` | только `SMALL`: файл, смещение записи, длина и CRC32C данных |

У `SMALL` и `EMPTY` `blobFileId = null` (это поле только про кукушкины блобы), поэтому `ResizeService` их не затрагивает.
`JsonManifestRepository` резолвит `smallBlobId` в `ManifestEntity.getSmallBlob()`; общий `getPhysicalBlob()` отдаёт
«блоб с байтами» любого вида. `countByBlobFileIdAndDeletedFalse` и `findByBlobFileId` считают ссылки и по `smallBlobId`
(нельзя удалить SOB, на который ссылаются живые объекты).

### Реестр блобов

`BlobFileEntity.kind` (`CUCKOO` по умолчанию — старые `blobs.json` читаются; `SMALL`). У SMALL `numBuckets = chunkSize = 0`.
Все места, где блобы перебираются «для кукушки», учитывают вид:

* `BlobService.chooseBlobFileForWrite` — только `CUCKOO`;
* `HashTableCache.get` — для не-`CUCKOO` бросает `IllegalArgumentException`;
* `ResizeService.resizeBlobFile` и `AutoResizeScheduler` — SOB пропускают/отвергают (у SOB нет слотов, он растёт откатом на новый файл);
* `PoolService.deleteBucket` — теперь удаляет **все** блобы пула (оба вида) и закрывает их каналы в кэшах;
* shell: `blobs`, `blob`, `pool`, `status`, `scrub`, `resize`, `info`, `ls --pool` понимают оба вида.

## 3. Формат файла `small_<8hex>.sob`

Все числа big-endian. Файл лежит в каталоге пула рядом с `blob_*.raw`.

```
[0 .. 4096)        заголовок
[4096 .. tail)     записи, каждая начинается с границы 8 байт
```

### Заголовок (4096 байт)

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 8 | magic `SDBSMOB1` |
| 8 | 4 | formatVersion = 1 |
| 12 | 4 | зарезервировано |
| 16 | 8 | время создания, epoch millis |
| 24 | 40 | нули |
| 64 | 32 | слот контрольной точки A |
| 96 | 32 | слот контрольной точки B |
| 128 | 3964 | нули |
| 4092 | 4 | CRC32C статической части — байтов `[0, 64)` |

Неверный magic, CRC или неизвестная версия — `InvalidBlobHeaderException` с понятным текстом; файл не открывается.

**Контрольная точка** (`checkpointTail`) — подсказка для восстановления: смещение, до которого записи заведомо долговечны.
Она лежит не в CRC-защищённой статической части, а в двух слотах по 32 байта (в первом 512-байтовом секторе):

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 8 | `checkpointTail` |
| 8 | 8 | generation (нечётный → слот A, чётный → B; побеждает валидный слот с большим generation) |
| 16 | 12 | нули |
| 28 | 4 | CRC32C байтов `[0, 28)` |

Зачем так: перезапись всех 4096 байт заголовка может оборваться посередине, и тогда CRC заголовка не сойдётся —
файл стал бы неоткрываемым из-за подсказки. Слоты по 32 байта живут внутри одного сектора (запись сектора атомарна на
практике), пишутся поочерёдно, а оба битых слота просто означают «проверять данные с самого начала» (медленнее, но верно).

### Запись (record)

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 4 | recordMagic `0x53524543` («SREC») |
| 4 | 1 | state: 1 `ACTIVE`, 2 `DELETED` |
| 5 | 1 | flags (0) |
| 6 | 2 | зарезервировано |
| 8 | 4 | dataLength |
| 12 | 4 | CRC32C данных |
| 16 | 8 | sequence — монотонный счётчик записей файла |
| 24 | 4 | ownerTag — младшие 32 бита хэша id манифеста (информативно, для разбора руками) |
| 28 | 4 | CRC32C заголовка записи по байтам `[0, 28)` **кроме байта state (смещение 4)** |

За заголовком идут `dataLength` байт данных и нули до кратности 8. Размер записи (`span`) = `32 + dataLength`, округлённое вверх
до 8. Минимум на диске — 40 байт (1 байт данных), вместо 16 КиБ слота.

### Почему state исключён из CRC заголовка

Удаление должно менять состояние записи атомарно. Вариант «перезаписать все 32 байта заголовка» плох: заголовок с
выравниванием 8 может пересекать границу 512-байтового сектора, и оборванная перезапись превратит здоровую запись в «битую» —
а она выглядит как оборванный хвост, после которого восстановление отрежет всё, что за ней. Поэтому CRC не покрывает байт
state, а удаление — это **запись одного байта** (`2`) по смещению `offset + 4`: один байт в одном секторе пишется атомарно.
Платим тем, что сам байт state не защищён CRC; он проверяется отдельно (допустимы только 1 и 2), а искажение state в
«чужое» допустимое значение равносильно потере/воскрешению одного объекта — манифест остаётся источником истины (см. §6).

## 4. Протокол и устойчивость к сбоям

### Добавление

Под блокировкой файла (записи сериализованы, чтения нет):

1. собрать запись (заголовок + данные + нули) в один буфер; `sequence = nextSequence`;
2. записать её по смещению `tail` (полный цикл записи, как в стадии 01);
3. `force` (если `sectoriadb.fsync=true`);
4. только теперь продвинуть в памяти `tail` (volatile) — запись становится видимой читателям;
5. если с последней контрольной точки прошло больше `checkpoint-interval-bytes` (16 МиБ) — записать следующий слот контрольной точки и `force`.

Если шаги 2–3 упали, `tail` не сдвигается, файл урезается обратно до `tail` (по возможности), ошибка уходит вызывающему, а
следующее добавление просто перепишет это место.

Затем (уже вне SOB) `FileStorageService` сохраняет манифест. **Порядок «сначала данные, потом манифест» определяет
последствия сбоев**: если процесс упал между ними, остаётся ACTIVE-запись, на которую ничего не ссылается — это утечка места
(её соберёт GC, этап 08), но не потеря данных и не манифест без данных.

### Чтение

`read(offset, length, crc)` не берёт блокировок (позиционный `FileChannel.read`) и никогда не смотрит за опубликованный `tail`.
Проверяются: смещение (выровнено, внутри `[4096, tail)`), magic и CRC заголовка, state = `ACTIVE`, длина и CRC равны
значениям из манифеста, CRC32C прочитанных данных. Любое несоответствие — `SmallObjectCorruptedException`
(`extends IOException`, как `ChunkCorruptedException`; в S3 это 500, а не молчаливо неверные данные). `Range` на SMALL — срез
одной прочитанной и проверенной записи.

### Восстановление при открытии

1. проверить заголовок (см. выше), прочитать слоты контрольной точки;
2. пройти записи от 4096: у **всех** записей проверяется CRC заголовка (читаются только 32 байта и перепрыгивается
   `span`), по ним пересчитываются живые/мёртвые записи и байты, `nextSequence = max(sequence)+1`;
   у записей **начиная с контрольной точки** дополнительно проверяется CRC данных;
3. первая невалидная запись, после которой **нет ни одной валидной**, — оборванный хвост (torn tail): логический `tail` =
   её начало; файл урезается до него, следующее добавление перезаписывает это место. Невалидна — значит: плохой magic/CRC,
   неверный state, длина за концом файла или (для записи после контрольной точки) неверный CRC данных у последней записи;
4. если же за невалидным местом **найдена валидная запись** (поиск идёт по границам 8 байт), это повреждение в середине
   журнала, а не хвост. Оборвать таким образом мог только последний append (добавления сериализованы и каждое
   фиксируется до следующего). Такой блоб открывается **только для чтения** (`isWritable() == false`): ничего не
   перезаписывается и не урезается, остальные записи читаются, проблема пишется в лог и видна в `scrub`.
   `BlobService.chooseSmallBlobForWrite` пропускает такие файлы и заводит новый.

Почему это безопасно: любая запись, подтверждённая клиенту, прошла `force` до продвижения `tail` и до сохранения манифеста;
всё, что восстановление отрезает, — не более одной записи, которая ещё не была подтверждена. Данные до контрольной точки не
перепроверяются при открытии (их порча найдётся при чтении или в `scrub`) — иначе открытие гигабайтного файла
было бы полным чтением диска.

## 5. Удаление

`FileStorageService.delete`: сначала `manifest.deleted = true` (сохранён), **потом** `markDeleted(offset)` — запись одного
байта state + `force`. Сбой между ними оставляет «удалённый» объект с ACTIVE-записью: утечка, не потеря. Ошибка при
пометке не проваливает удаление (пишется WARN). Повторная пометка идемпотентна. Чтение DELETED-записи — ошибка.

Пространство **не освобождается**: SOB лишь считает `liveRecords/deadRecords` и `liveBytes/deadBytes` (по
`span`, пересчитываются при открытии) — `SmallObjectBlob.stats()`, видны в shell (`blob`, `blobs`). Это готовый крючок под
компакцию.

## 6. Откат на новый файл (rollover)

`sectoriadb.small-object.max-file-bytes` (по умолчанию 1 ГиБ). Когда `tail + span` превысил бы лимит, `append` возвращает
`null`; `BlobService.chooseSmallBlobForWrite(pool, len)` перебирает SOB пула от новых к старым и берёт первый открытый,
записываемый и с местом, иначе создаёт новый (под `synchronized`, чтобы два PUT не создали по файлу). Пустой файл принимает
одну запись любого размера. Старые файлы остаются читаемыми; `FileStorageService` при гонке (файл заполнился между выбором и
записью) выбирает заново (до 8 попыток).

## 7. Параллелизм

Добавления и удаления одного файла идут под его `ReentrantLock`; чтения — без блокировок (позиционные чтения
потокобезопасны), они видят только записи ниже опубликованного `tail`. Разные SOB независимы. Выбор файла для записи сериализован.
Чтение, гонящееся с удалением той же записи, может получить ошибку «DELETED» — как и GET, гонящийся с DELETE.

## 8. Shell

* `mkblob --pool P --small` — создать SOB вручную (обычно создаётся автоматически при первом малом объекте);
* `blobs`, `pool`, `status` — столбец Kind; для SOB: размер файла и live/dead байты (`READ-ONLY`, если найдено повреждение);
* `blob --id` — записи и байты live/dead, признак «Writable»;
* `scrub --id` — проходит **все** записи, проверяет CRC32C данных, печатает `records/active/deleted/ok/corrupt`,
  проблемы (до 100) и `RESULT: clean|DAMAGED`;
* `info`, `ls --pool` — показывают вид хранения; `resize` на SOB сообщает, что это не поддерживается.

| Параметр | По умолчанию |
|---|---|
| `sectoriadb.small-object.max-file-bytes` | `1073741824` |
| `sectoriadb.small-object.checkpoint-interval-bytes` | `16777216` |

Порог «малого» объекта — `sectoriadb.default-chunk-size`; `sectoriadb.fsync` распространяется и на SOB.

## 10. Тесты

* `SmallObjectBlobTest` (core): круговой обмен для размеров 0…16383; 8 потоков × 300 добавлений и чтение всего; оборванный
  хвост (урезание посреди записи, битый заголовок, битые данные) — отброшена только последняя запись, предыдущие целы,
  следующее добавление берёт тот же `tail`; повреждение в середине → read-only; порча при чтении; удаление переживает
  переоткрытие; rollover при крошечном лимите; битые слоты контрольной точки; плохой magic/CRC/версия.
* `SmallObjectStorageTest` (core): 0/1/chunk-1 → `EMPTY`/`SMALL`, chunk и chunk+1 → `CHUNKED`; Range для всех видов;
  `restore`/`restoreRange`; пометка удаления; перезапуск; rollover через сервис; старые JSON без новых полей.
* `S3SmallObjectsTest` (server): PUT/GET/HEAD/Range/DELETE, перезапись, граница размера чанка, пустой объект, CopyObject,
  multipart, завершающийся малым объектом (в этой реализации минимального размера части нет), удаление бакета.

## 11. Отложено и ограничения

* **Компакция SOB** (переписать живые записи в новый файл, поменять `smallBlobId/smallOffset` в манифестах, удалить старый
  файл) и сбор утёкших ACTIVE-записей без манифеста — этап `08-gc-and-resize`; счётчики live/dead уже есть.
* Нет сжатия, нет дедупликации малых объектов (на чанках дедуп есть, тут одна запись на объект).
* Поиск валидной записи после повреждения (resync) можно обмануть объектом, внутри которого лежит корректно оформленная
  запись с верным CRC; в таком случае блоб ошибочно открывается read-only (безопасная сторона ошибки), а не перезаписывается.
* Каталог после создания файла не `fsync`-ится (как и для `blob_*.raw`).
* Метаданные (`blobs.json`, манифесты) по-прежнему обычные JSON без транзакций — этапы 05–06.
