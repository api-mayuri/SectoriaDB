# 04. Транзакционное хранилище метаданных (B+-дерево, copy-on-write)

Пакет `org.example.sectoriadb.metastore` (модуль `sectoriadb-core`). Встраиваемое key-value хранилище в
одном файле: именованные B+-деревья, ACID-транзакции, снимки (MVCC). Предназначено для замены хрупких
JSON-файлов; интеграция с репозиториями — этап `05-metastore-integration`. Зависимостей, кроме JDK, нет.

## 1. Файл

Файл состоит из страниц фиксированного размера (`pageSize`, степень двойки от 512 до 65536, по умолчанию
4096; задаётся при создании и хранится в мета-странице, для существующего файла побеждает значение из файла).
Страница с номером `id` лежит по смещению `id * pageSize`. Числа — big-endian.

### 1.1 Мета-страницы (страницы 0 и 1)

| смещение | размер | поле |
|---------:|-------:|------|
| 0  | 8 | magic: ASCII `SECTMETA` (`0x534543544D455441`) |
| 8  | 4 | версия формата (сейчас 1) |
| 12 | 4 | `pageSize` |
| 16 | 8 | `txId` последней зафиксированной транзакции |
| 24 | 8 | номер корневой страницы каталога деревьев (0 — каталог пуст) |
| 32 | 8 | номер первой страницы цепочки freelist (0 — цепочки нет) |
| 40 | 8 | `pageCount` — верхняя граница выделенных страниц (high-water mark) |
| 48 | 4 | CRC32C байтов `[0, 48)` |
| 52 | … | нули до конца страницы |

Транзакция `T` пишет мета-страницу в слот `T % 2`, поэтому две копии чередуются, и одна из них всегда
остаётся целой. При открытии читаются оба слота; слот игнорируется, если magic/версия/CRC неверны, а также
если `pageCount * pageSize` больше размера файла (хвост файла потерян). Из оставшихся берётся слот с
наибольшим `txId`. Если слот 0 повреждён, `pageSize` определяется перебором размеров 512…65536 по слоту 1.
Если годных слотов нет — `CorruptedPageException`.

### 1.2 Общий заголовок остальных страниц (8 байт)

| смещение | размер | поле |
|---------:|-------:|------|
| 0 | 4 | CRC32C байтов `[4, pageSize)` |
| 4 | 1 | тип: 1 лист, 2 ветвь, 3 overflow, 4 freelist |
| 5 | 1 | зарезервировано |
| 6 | 2 | `count` (число ключей / записей / байт данных — по типу) |

CRC проверяется при **каждом** чтении страницы; несовпадение — `CorruptedPageException` (с номером страницы).

### 1.3 Лист (тип 1)

С байта 8 подряд `count` записей:
`keyLen u16 | key | kind u8 | ...`, где `kind = 0` — значение внутри страницы: `valLen u16 | value`;
`kind = 1` — значение в overflow-цепочке: `head u64 | length u64`.
Размер записи: `2 + keyLen + 1 + (2 + valLen | 16)`. Значение хранится внутри листа, если вся запись не
больше `(pageSize - 8) / 4`, иначе уходит в overflow.

### 1.4 Ветвь (тип 2)

С байта 8: `child0 u64`, затем `count` пар `keyLen u16 | key | child u64`. Ключ `keys[i]` разделяет
потомков: `child[i]` содержит ключи `< keys[i]`, `child[i+1]` — `>= keys[i]`. В ветви `count + 1` потомков.

### 1.5 Overflow (тип 3)

`8: next u64` (0 — конец цепочки), `16…`: данные; `count` — число байт данных на странице
(не более `pageSize - 16`). Цепочка имеет заранее известную длину (`length` в записи листа).

### 1.6 Freelist (тип 4)

`8: next u64`, `16…`: `count` записей по 16 байт: `pageId u64 | groupTxId u64`. `groupTxId = 0` —
страница свободна для немедленного повторного использования, иначе — страница освобождена транзакцией
`groupTxId` и ждёт, пока её перестанут читать снимки (см. раздел 4).

### 1.7 Каталог деревьев

Каталог — тоже B+-дерево (его корень в мета-странице): ключ — имя дерева в UTF-8, значение — 16 байт
`rootPageId u64 | entryCount u64`. Пустое дерево имеет корень 0.

## 2. Дерево

* Порядок ключей — беззнаковое лексикографическое сравнение (`Arrays.compareUnsigned`).
* Ключ до 2 КиБ (так хватает на ключ S3 в 1024 байта плюс имя бакета), но не более `(pageSize - 8) / 3 - 24` (для страницы 512 байт — 144). Это гарантирует,
  что любой узел вмещает не менее трёх записей максимального размера, и деление всегда возможно.
* Значение до 64 МиБ. Большие значения — в overflow-цепочках (тоже copy-on-write, при замене/удалении
  страницы освобождаются).
* **Деление**: переполненный узел делится в точке, минимизирующей больший из двух размеров (по байтам, а не по
  числу записей). Разделитель из листа копируется вверх, из ветви — поднимается.
* **Удаление и слияние**: после удаления узел меньше `pageSize / 4` сливается с соседом (правым, а для
  последнего потомка — левым), если результат помещается в страницу (для ветвей в слитый узел
  входит и разделяющий ключ родителя). Если не помещается — узел остаётся «недогруженным»: заимствование
  (перераспределение) не реализовано. Следствия: пустой лист всегда исчезает (он всегда помещается в соседа);
  не-корневая ветвь с единственным потомком теоретически возможна, но корректна; корень-ветвь с одним
  потомком схлопывается, пустое дерево получает корень 0.
* **Курсоры** — стек «корень → лист». Сестринских указателей нет (при COW их обновление потребовало бы
  копировать соседей). Курсор внутри write-транзакции инвалидируется любой модификацией
  (`ConcurrentModificationException`).

## 3. Copy-on-write и протокол коммита

Write-транзакция **никогда** не изменяет страницу, достижимую из зафиксированного корня. Изменяемый узел
копируется на новую страницу (id берётся из свободных или из `pageCount++`), копия правится в памяти;
родитель тоже копируется, чтобы указать на новый id, и так до корня. Страницы, выделенные самой
транзакцией, правятся на месте. Большие значения записываются в overflow-страницы сразу (они недостижимы
до коммита), остальные грязные страницы копятся в памяти.

Коммит транзакции `T = txId + 1`:

1. Изменённые корни/счётчики деревьев записываются в каталог (он тоже копируется).
2. Страницы, освобождённые транзакцией (и старая цепочка freelist), попадают в группу `T` списка ожидающих.
3. Строится новая цепочка freelist (страницы под неё берутся из свободных, иначе из конца файла);
   в ней — вся информация о свободных и ожидающих страницах.
4. Записываются все грязные страницы и страницы freelist, при необходимости файл дорастает до `pageCount`.
5. `FileChannel.force` — **барьер 1**: все данные на диске.
6. Записывается мета-страница в слот `T % 2` (новые корень каталога, корень freelist, `pageCount`, CRC).
7. `FileChannel.force` — **барьер 2**.
8. Новое состояние публикуется читателям (volatile-ссылка).

Транзакция без изменений ничего не пишет и не увеличивает `txId`. `abort` (закрытие без `commit`) просто
отбрасывает грязные страницы и возвращает взятые из freelist страницы; выделенное из конца файла забывается
(`pageCount` не менялся).

### Почему это crash-safe

* До шага 6 ни одна страница, достижимая из последней валидной мета-страницы, не перезаписана: новые
  версии лежат на свободных страницах или за прежним `pageCount`. Сбой на любом шаге 1–5 оставляет файл в
  состоянии, которое открывается как предыдущий коммит (лишние записанные страницы — мусор, о котором
  мета-страница не знает).
* Свободными для повторного использования транзакцией `T` считаются только страницы, не достижимые из
  корня `T-1` и из freelist-цепочки `T-1`: старая цепочка попадает в группу `T`, которую `T` сама не
  использует. Поэтому откат на `T-1` после неудачной `T` всегда видит целые данные.
* Шаг 6 пишет менее 64 байт в начале страницы (в пределах одного сектора), а CRC делает «рваную» запись
  обнаруживаемой: невалидная мета-страница игнорируется и работает предыдущая. Слоты чередуются, поэтому
  запись `T` никогда не затирает мета-страницу `T-1`.
* Если после барьера 1 процесс умер до записи мета-страницы — коммит просто не состоялся; если после
  барьера 2 — состоялся полностью. Промежуточных состояний нет.
* При ошибке ввода-вывода во время коммита хранилище переходит в состояние «отравлено»
  (`IllegalStateException` на новых транзакциях) и должно быть открыто заново: состояние файла
  по-прежнему согласованно, а свободные списки в памяти уже не заслуживают доверия.
* Тесты: `CrashSafetyTest` (обнуление/порча новейшей мета-страницы, усечение хвоста, имитация сбоя
  между барьерами через тестовый `commitHook`, 80 раундов случайных сбоев с повторным открытием и
  сверкой с моделью).

## 4. Свободные страницы

Состояние в памяти (меняется только владельцем write-блокировки) и на диске (цепочка freelist):

* `available` — страницы, которые можно выдавать прямо сейчас;
* `pending[U]` — страницы, освобождённые транзакцией `U`.

Страницы, освобождённые транзакцией `U`, были достижимы из корня `U-1` и недостижимы из корня `U` и
более поздних. Снимок читателя `R` может ссылаться на них, только если `R <= U-1`. Поэтому группа
`U` переходит в `available`, когда `min(txId живых читателей, последний коммит) >= U` (проверяется при
`beginWrite`). Страницы, выделенные и освобождённые внутри одной транзакции, используются повторно сразу.

* Живые читатели учитываются в памяти (`txId -> счётчик`). Долгоживущий читатель держит все страницы своего
  снимка: пока он открыт, файл растёт; закрывать `ReadTxn` обязательно (`try-with-resources`).
* После перезапуска читателей нет, поэтому при открытии все страницы freelist (и ожидающие) считаются
  доступными.
* Файл не растёт неограниченно при перезаписи одних и тех же ключей (тест
  `fileStaysBoundedUnderOverwriteChurn`; при закрытом читателе — `oldSnapshotSurvivesManyCommits...`).
* Цепочка freelist переписывается целиком при каждом коммите (16 байт на свободную страницу; при странице
  4 КиБ — 254 записи на страницу). Для метаданных это приемлемо; при миллионах свободных страниц стоит
  перейти на дерево freelist.

## 5. Изоляция и MVCC

* Ровно одна write-транзакция одновременно (`beginWrite` блокируется, `tryBeginWrite(timeout)` — с таймаутом).
  Любое число read-транзакций; каждая видит снимок на момент `beginRead`.
* Предотвращаются: **грязное чтение** (незафиксированные данные недостижимы из зафиксированного корня),
  **неповторяющееся чтение** и **фантомы** (снимок неизменяем, в том числе для диапазонных сканов),
  **грязная запись** и **потерянное обновление** (писатели сериализованы; read-modify-write внутри
  write-транзакции атомарен — тест со счётчиком из N потоков), **рваные чтения** нескольких деревьев (снимок общий
  для всех деревьев хранилища).
* Не предотвращается write skew между read-транзакциями и последующей записью, если решение принято
  на основе чтения вне write-транзакции: читайте то, от чего зависит запись, внутри write-транзакции
  (она видит последнее зафиксированное состояние плюс свои изменения, т. е. изоляция записей — serializable).
* Read-транзакции и курсоры не потокобезопасны: одна транзакция — один поток.

## 6. API

```java
MetaStore store = MetaStore.open(Path.of("meta.db"),
        MetaStoreOptions.defaults().pageSize(4096).fsync(true));

try (WriteTxn tx = store.beginWrite()) {          // close() без commit() = abort
    BTree objects = tx.tree("objects");           // создаётся, если нет
    objects.put(Keys.builder().string("bucket").string("a/b.txt").build(), value);
    objects.delete(oldKey);
    tx.commit();
}

try (ReadTxn tx = store.beginRead()) {
    BTree objects = tx.tree("objects");           // нет дерева -> пустое, только чтение
    Optional<byte[]> v = objects.get(key);
    try (Cursor c = objects.scan(fromInclusive, toExclusive)) {     // null = без границы
        while (c.next()) { c.key(); c.value(); }
    }
    objects.scanPrefix(Keys.builder().string("bucket").build());
    long n = objects.size();
}

store.write(tx -> { tx.tree("t").put(k, v); return null; });   // commit/abort автоматически
store.writeVoid(tx -> tx.dropTree("old"));
String s = store.read(tx -> tx.tree("t").get(k).map(String::new).orElse(null));

MetaStore.Stats st = store.stats();     // pageSize, pageCount, freePages, lastTxId, fileSize, liveReaders
MetaStore.VerifyReport r = store.verify(); // CorruptedPageException при нарушении
store.close();
```

`WriteTxn`: `tree(name)`, `dropTree(name)`, `treeNames()`, `hasTree(name)`, `commit()`.

`Keys` — композитные ключи с сохранением порядка: строка (UTF-8, `0x00` экранируется как `0x00 0xFF`,
завершается `0x00 0x01`, поэтому `"a" < "a\0" < "ab"`, а кодировка «бакет» является префиксом кодировки
«бакет + ключ»), `longUnsigned`/`longSigned` (8 байт big-endian, у знаковой перевёрнут старший бит),
`raw` (только последним компонентом), `Keys.Reader` для разбора, `Keys.prefixEnd` для верхней границы префикса.

`verify()` блокирует писателей и проверяет: CRC всех достижимых страниц, строгий порядок ключей и
вхождение в диапазон родителя, одинаковую глубину листьев, отсутствие пустых листьев, размеры узлов,
соответствие числа записей каталогу, длины overflow-цепочек, и что каждая страница файла `[2, pageCount)`
учтена **ровно один раз** (дерево / overflow / freelist-цепочка / свободна), т. е. нет ни утечек, ни
двойных ссылок.

## 7. Ограничения

* Ключ ≤ `min(2048, (pageSize-8)/3-24)` байт, значение ≤ 64 МиБ (значение целиком в памяти `byte[]`).
* Грязные узлы write-транзакции хранятся в памяти до коммита; очень большие транзакции расходуют память.
* Нет заимствования соседних записей при удалении — возможны недогруженные узлы (корректность не страдает).
* Нет сжатия/очистки хвоста файла: освободившиеся страницы переиспользуются, но файл не усекается.
* Freelist переписывается целиком на каждом коммите (см. раздел 4).
* Нет межпроцессного доступа: файл блокируется (`FileLock`), второе открытие — ошибка.
* Страницы читаются без кэша (опора на page cache ОС); ошибки ввода-вывода — `UncheckedIOException`.
* При сбое ввода-вывода внутри коммита экземпляр `MetaStore` непригоден до переоткрытия.
