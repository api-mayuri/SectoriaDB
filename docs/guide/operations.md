# Эксплуатация

## Запуск в Docker

```bash
cp .env.example .env            # задайте ключ: SECTORIADB_S3_ACCESS_KEY / SECTORIADB_S3_SECRET_KEY (секрет не короче 16 символов)
deploy/gen-self-signed.sh       # для проверки: самоподписанный сертификат в deploy/certs/ (боевой — см. «TLS через nginx»)
docker compose up -d --build    # сервисы sectoriadb и nginx (TLS)
docker compose logs -f sectoriadb
```

Для разработки без TLS: `docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build` — дополнительно публикует S3-порт `127.0.0.1:8080` и запускает веб-интерфейс s3manager.

| Что | Как устроено |
|---|---|
| Образ | двухстадийный `Dockerfile`: сборка Maven, запуск на `eclipse-temurin:21-jre-alpine` от непривилегированного пользователя `sectoria` |
| Порты | `443` и `80` — nginx (HTTPS и редирект на него), единственный вход для S3-клиентов; `8080` — S3 API сервера, **на хост не публикуется** (виден только nginx по сети compose; в `docker-compose.dev.yml` — `127.0.0.1:8080`); `9464` — метрики и health, только `127.0.0.1` хоста; `8081` — s3manager (только в `docker-compose.dev.yml`, loopback) |
| TLS | сервис `nginx` (`nginx:1.27.5-alpine`), конфигурация `deploy/nginx/sectoriadb.conf`, сертификат `deploy/certs/{fullchain,privkey}.pem`; сервер получает `SECTORIADB_S3_REQUIRE_SECURE_TRANSPORT=true` и отвечает `403 InsecureTransport` на всё, что пришло не по HTTPS |
| Том | **один** именованный том `sectoriadb-store` → `/data`: метаданные в `/data/meta`, блобы и спул загрузок в `/data/storage` (спул по умолчанию `<data-dir>/.tmp`, то есть внутри тома). Переживает пересборку и перезапуск. Один том нужен, чтобы снимок был атомарным сразу для метаданных и блобов ([резервное копирование](#резервное-копирование)) |
| Остановка | `server.shutdown=graceful` (30 с), `stop_grace_period: 40s`: текущие запросы дозавершаются |
| Перезапуск | `restart: unless-stopped`; `-XX:+ExitOnOutOfMemoryError` завершает процесс при нехватке памяти, чтобы он поднялся чистым |
| Healthcheck | `wget` к `http://127.0.0.1:9464/actuator/health` раз в 30 с (старт до 40 с, 3 попытки); S3-порт для этого не годится — анонимные запросы получают `403`. nginx и s3manager стартуют после `service_healthy` |
| Консоль | `docker attach sectoriadb` (compose включает `stdin_open`/`tty`); разовые команды — [admin-shell.md](admin-shell.md) |

Первый запуск: пока нет ни одного ключа, все S3-запросы получают `403` (если не включён `allow-open-setup`). Создайте ключ
`docker compose exec sectoriadb java -jar /app/sectoriadb.jar mk-key --desc "my key"` или задайте переменные окружения.

Запуск без Docker: `mvn package -DskipTests`, затем `java -jar sectoriadb-server/target/SectoriaDB-1.0-SNAPSHOT.jar` (нужен JDK 21).
Свойства: [configuration.md](configuration.md).

## TLS через nginx

Сервер сам TLS не терминирует (и не будет): шифрование выносится в nginx, который в `docker-compose.yml` уже стоит перед сервером. Конфигурация — [deploy/nginx/sectoriadb.conf](../../deploy/nginx/sectoriadb.conf);
**проверено** на nginx 1.27.5 с реальными клиентами (таблица в [recommendations.md](recommendations.md#обратный-прокси-nginx)).

**Что делает конфигурация**
- `443`: TLS 1.2/1.3, современные шифры (ECDHE + AES-GCM/ChaCha20, без сессионных билетов), HSTS (`max-age=63072000`), HTTP/2 для клиентов, которые его умеют.
- `80`: `301` на `https://$host$request_uri` (путь и запрос сохраняются как есть). Для нестандартного внешнего порта HTTPS (`HTTPS_PORT`) поправьте адрес редиректа в конфигурации.
- Прокси к `sectoriadb:8080` без переписывания пути, `Host` как пришёл (с портом), `X-Forwarded-Proto`/`X-Forwarded-For`, без буферизации запроса и ответа, тело до 5 ГиБ, таймауты по часу, keep-alive к серверу.
- Порт управления (`9464`: метрики и health без подписи) через nginx **не проксируется**.

**Сертификат**
- Проверка на своей машине: `deploy/gen-self-signed.sh [имя-или-IP ...]` создаёт `deploy/certs/fullchain.pem` и `privkey.pem` (по умолчанию `localhost`, `127.0.0.1`, `::1`). Клиентам нужно доверять ему:
  `aws --ca-bundle deploy/certs/fullchain.pem …` (или `AWS_CA_BUNDLE`), `curl --cacert …`, `ca_certs_file` в s3cmd, `--ca-cert` в rclone; `--no-verify-ssl` — только для проверок.
- Боевой: положите в `deploy/certs/` цепочку сертификатов (`fullchain.pem`) и ключ (`privkey.pem`) от корпоративного CA или Let's Encrypt. Каталог в `.gitignore`, ключ не коммитить.
  Let's Encrypt: получите сертификат `certbot` любым способом (например, `certbot certonly --standalone -d s3.example.com`, пока nginx остановлен, или webroot — в `server` на порту 80 в конфигурации оставлен комментарий-подсказка) и скопируйте
  `fullchain.pem`/`privkey.pem` из `/etc/letsencrypt/live/<имя>/` в `deploy/certs/` (копируйте файлы, а не симлинки: симлинки на каталог вне монтирования внутри контейнера не откроются).
  Автоматизации выпуска в проекте нет. После обновления сертификата: `docker compose exec nginx nginx -s reload`.
- Имя сертификата должно совпадать с именем, по которому ходят клиенты (path-style: `https://s3.example.com/bucket/key`; виртуальные хосты `bucket.s3.example.com` не поддерживаются).

**Обязательно за прокси**
- `sectoriadb.s3.require-secure-transport=true` (в compose включено по умолчанию, переменная `SECTORIADB_S3_REQUIRE_SECURE_TRANSPORT`): запрос не по HTTPS получает `403 InsecureTransport` до проверки подписи.
  Схему сервер берёт из `X-Forwarded-Proto` (`server.forward-headers-strategy=native`, `RemoteIpValve` Tomcat), **но только если запрос пришёл от доверенного прокси** — адреса из `server.tomcat.remoteip.internal-proxies`
  (по умолчанию loopback и частные сети: `10/8`, `172.16/12`, `192.168/16`). От остальных адресов заголовок игнорируется, так что подделать его снаружи нельзя.
  В compose сеть имеет фиксированную подсеть `172.31.250.0/24`, у nginx постоянный адрес `172.31.250.10`, и сервер доверяет `X-Forwarded-*`
  **только ему** (`SERVER_TOMCAT_REMOTEIP_INTERNALPROXIES`, переменная `PROXY_ADDRESS_REGEX` в `.env`). Запрос с поддельным `X-Forwarded-Proto: https`
  от любого другого контейнера сети получает `403 InsecureTransport` (проверено). Если подсеть занята, поменяйте её в `docker-compose.yml` вместе
  с адресом nginx и `PROXY_ADDRESS_REGEX`. Без compose задайте `server.tomcat.remoteip.internal-proxies` равным адресу своего прокси.
  В `docker-compose.dev.yml` проверка выключена, потому что там клиенты ходят по HTTP.
- Свойство защищает от ошибок настройки (клиент по `http://`, порт, случайно открытый наружу). Оно не заменяет шифрование на пути: TLS-соединение клиента заканчивается в nginx, участок nginx → сервер идёт по сети compose открытым текстом.
  Если nginx и сервер на разных хостах — поднимите между ними VPN/WireGuard или отдельную сеть.
- Если пересоздали контейнер `sectoriadb` не через compose, перечитайте адрес: `docker compose restart nginx` (nginx разрешает имя сервера при старте; compose перезапускает его сам благодаря `depends_on … restart: true`).

**Политика бакета «только TLS».** Условие `Bool` / `aws:SecureTransport` в политиках вычисляется (единственное поддерживаемое условие, [s3-usage.md](s3-usage.md#политики-бакета)). Политики действуют только на анонимные запросы,
поэтому типичный сценарий — публичный бакет, читаемый только по HTTPS:
`{"Effect":"Deny","Principal":"*","Action":"s3:*","Resource":["arn:aws:s3:::b","arn:aws:s3:::b/*"],"Condition":{"Bool":{"aws:SecureTransport":"false"}}}`.
Для подписанных запросов то же гарантирует `require-secure-transport` на уровне сервера.

## Что лежит на диске

Всё состояние — один том `sectoriadb-store`, смонтированный в `/data` (`SECTORIADB_META_DIR=/data/meta`, `SECTORIADB_DATA_DIR=/data/storage`). Без Docker держите оба каталога на одной файловой системе по той же причине.

```
/data/                            (том sectoriadb-store)
  meta/
    sectoria.db                   все метаданные: пулы, блобы, манифесты, индексы, индекс чанков, очереди GC, multipart
    credentials.json              ключи доступа (атомарная замена файла)
    oplogs.jsonl                  журнал операций консоли и хранилища (команда audit)
    sectoriadb.log (+ дневные)    журнал приложения
  storage/
    .tmp/                         спул тел загрузок (чистится при старте; внутри тома, поэтому занимает место того же диска)
    <бакет>/blob_<uuid>.raw       кукушкины блобы: разрежённые файлы (8 ГиБ логических при настройках по умолчанию)
    <бакет>/small_<uuid>.sob      журналы малых объектов
```

`blob_*.raw` разрежённые: логический размер большой, занято столько, сколько записано (`du`, а не `ls -l`). Файловая система должна
поддерживать разрежённые файлы (ext4, xfs, overlayfs — да). **Любая копия тома обязана сохранять разрежённость** (`tar -S`, `cp` с `SEEK_HOLE`, `rsync -S`):
без этого каждый блоб развернётся до 8 ГиБ нулей. busybox-`tar` из образа сервера разрежённость не сохраняет — скрипты копирования используют GNU tar в отдельном контейнере.

## Резервное копирование

Своего движка копирования в сервере нет, и он не нужен: хранилище **консистентно при аварийной остановке по построению** (данные пишутся до коммита метаданных, коммит — переключение одной мета-страницы;
проверено `kill -9` и снимками работающего сервера, [fault-injection.md](../testing/fault-injection.md)). Поэтому копия тома, снятая в один момент времени, — это то же, что диск после потери питания:
сервер при старте сам доведёт её до согласованного состояния. Всё состояние лежит в одном томе, так что копировать нужно ровно одну вещь — **атомарно**. Копирование `meta` и `storage` по очереди у работающего сервера копией не является
(метаданные, снятые позже блобов, ссылаются на данные, которых в копии нет; такая «копия» не проходит `verify-all`, проверено контрольным прогоном `NEGATIVE=1 snapshot-backup.sh`).

| Способ | Простой | Как |
|---|---|---|
| Горячая копия: атомарный снимок тома | нет | снимок файловой системы (LVM, ZFS, Btrfs) или диска (облако) во время работы; восстановление — смонтировать/скопировать снимок и запустить сервер |
| Холодная копия | да, на время архивирования | `deploy/backup/cold-backup.sh` |

### Горячая копия (снимок)

Снимок должен быть атомарным для всей файловой системы тома, где лежат `meta/` и `storage/`. Примеры (**не проверялись в этой среде** — нет LVM, ZFS, Btrfs и привилегий на них; логика «снимок = потеря питания» проверена
имитацией, см. [fault-injection.md](../testing/fault-injection.md#резервная-копия-снимком-работающего-сервера)):

```bash
# LVM (том /dev/vg0/sectoria смонтирован в /srv/sectoria; ext4/xfs с lvcreate --snapshot заморозятся на момент снимка сами)
lvcreate --snapshot --size 10G --name sectoria-snap /dev/vg0/sectoria
mount -o ro,nouuid /dev/vg0/sectoria-snap /mnt/snap     # nouuid нужен для xfs
# ... скопировать /mnt/snap (tar -S / rsync -aS / restic / borg) ...
umount /mnt/snap && lvremove -y /dev/vg0/sectoria-snap

# ZFS (набор данных tank/sectoria)
zfs snapshot tank/sectoria@$(date -u +%Y%m%dT%H%M%SZ)
zfs send -i tank/sectoria@prev tank/sectoria@now | ssh backup zfs receive -F pool/sectoria      # инкрементально

# Btrfs (том — отдельный subvolume /srv/sectoria)
btrfs subvolume snapshot -r /srv/sectoria /srv/snapshots/sectoria-$(date -u +%Y%m%dT%H%M%SZ)

# облачный диск: снимок диска со всем томом (AWS EBS, GCP PD, Azure managed disk), без остановки сервера
aws ec2 create-snapshot --volume-id vol-0123456789abcdef0 --description sectoriadb
```

Снимок, снятый без заморозки файловой системы (EBS, PD), — тоже «потеря питания»: сервер переживает её. Не нужны ни остановка сервера, ни `fsfreeze`, ни команды консоли. Расписание — частота, с которой вы готовы терять
подтверждённые записи (всё записанное после последнего снимка пропадает при восстановлении); снимок ловит ровно то, что было на диске в момент снимка.

**Восстановление из снимка:** смонтируйте снимок (или создайте том из облачного снимка) как том `/data`, запустите сервер; он восстанавливается как после `kill -9`. Затем `deploy/backup/verify-backup.sh <каталог-снимка>` (на копии) или `verify-all` на остановленном экземпляре.
Для Docker с каталогом на хосте: `volumes: sectoriadb-store: {driver: local, driver_opts: {type: none, o: bind, device: /srv/sectoria}}`.

### Холодная копия (скрипты `deploy/backup/`)

Вспомогательные скрипты для малых установок без снимков. Нужны Docker и compose; образ GNU tar (`debian:12-slim`, `BACKUP_IMAGE`) скачивается при первом запуске; `zstd` на хосте используется, если есть, иначе `gzip`.

```bash
deploy/backup/cold-backup.sh [каталог]   # по умолчанию $SECTORIADB_BACKUP_DIR или ~/sectoriadb-backups (вне репозитория, umask 077: внутри секреты ключей)        # остановить sectoriadb, архив тома → <каталог>/sectoriadb-<UTC>.tar.zst(.gz) + .sha256, запустить
deploy/backup/verify-backup.sh архив          # проверить КОПИЮ: распаковать во временный том, offline verify-all, удалить том; код возврата ≠ 0 при сбое
docker compose down && docker volume rm <проект>_sectoriadb-store
deploy/backup/restore.sh архив                # распаковать в НОВЫЙ том (существующий том не трогает), затем docker compose up -d
```

- `cold-backup.sh` останавливает только сервис `sectoriadb` (graceful, до 40 с); nginx остаётся и отвечает `502`, пока идёт копирование. Сервер запускается снова в любом случае, в том числе при ошибке архивирования.
- `restore.sh` отказывается писать в существующий том и проверяет `.sha256`, если он лежит рядом. Куда восстанавливать — второй аргумент (по умолчанию том, который использует compose).
- `restore.sh` без файла `.sha256` отказывается восстанавливать архив; для собственного tar без суммы есть `--no-verify`. Относительные пути скриптов считаются от текущего каталога.
- Образы `debian`, `nginx`, `temurin`, `maven` закреплены по digest; обновляйте digest вместе с тегом. `docker-compose.dev.yml`: `s3manager` включается только профилем (`--profile s3manager`) и стартует без права удаления (`S3MANAGER_ALLOW_DELETE=true` включает).
- Журнал nginx (`access_log`) не содержит строки запроса: подписи presigned-ссылок не попадают в `docker logs`. Docker ротирует логи (50 МиБ x 5).
- `verify-backup.sh` принимает и каталог (смонтированный снимок, копия): он копируется во временный том и проверяется там, оригинал не изменяется. Безопасен при работающем сервере. В cron: `0 4 * * 0  /opt/sectoriadb/deploy/backup/verify-backup.sh /backups/latest.tar.zst || mail …`.
- Скрипты проверены на compose-стеке из этого репозитория: холодная копия, проверка, восстановление в новый том, чтение объектов после восстановления ([fault-injection.md](../testing/fault-injection.md#холодная-копия-и-проверка-скрипты-deploybackup)).

### Что ещё нужно знать

1. `credentials.json` лежит в томе; секреты в нём в открытом виде — копии (архивы, снимки, выгрузки) защищайте так же, как сами ключи: шифрованный диск или `age`/`gpg` для архивов перед выгрузкой за пределы хоста (`age -r <публичный-ключ> -o архив.age архив.tar.zst`).
2. Файлы `.tmp/` и `sectoriadb.log` восстанавливать не нужно (первый чистится при старте). Журнал `oplogs.jsonl` нужен только для расследований (хранятся активный файл и пять архивов по 100 МБ).
3. Копия, не прошедшая `verify-all`, — не копия. Проверяйте по расписанию, на копии, а не на живом экземпляре ([recommendations.md](recommendations.md#резервные-копии-и-проверка)).
4. Один узел — одна точка отказа: снимки на том же физическом диске не защищают от его потери. Выносите копии (репликация снимков ZFS/Btrfs, копирование архивов, облачные снимки в другой зоне).

### Переход со старой раскладки на два тома

До этапа 18 compose создавал два тома, `<проект>_sectoriadb-meta` и `<проект>_sectoriadb-data`. Совместимость форматов не нарушена (содержимое то же), миграционного кода нет — достаточно скопировать оба тома в один новый
(`<проект>` — имя каталога проекта, `docker volume ls`):

```bash
docker compose down                                  # сервер остановлен: копия должна быть согласованной
docker volume create --label com.docker.compose.project=<проект> --label com.docker.compose.volume=sectoriadb-store <проект>_sectoriadb-store
docker run --rm -v <проект>_sectoriadb-meta:/from/meta:ro -v <проект>_sectoriadb-data:/from/storage:ro \
  -v <проект>_sectoriadb-store:/to debian:12-slim cp -a /from/. /to/      # GNU cp сохраняет разрежённость
docker compose up -d --build
deploy/backup/verify-backup.sh ...                   # по желанию: либо verify-all, как в admin-shell.md
# после проверки старые тома можно удалить: docker volume rm <проект>_sectoriadb-meta <проект>_sectoriadb-data
```

Тот же результат даёт перенос через S3 (`rclone sync` / `aws s3 sync` со старого экземпляра на новый): так переносятся только объекты, но не ключи, ACL и политики ([recommendations.md](recommendations.md#обновления)).

## Шифрование на диске

В сервере нет кода шифрования и не будет: данные шифруются слоем хранения, под файловой системой тома. Это закрывает вопрос «а если украдут диск» без изменений в сервере, и один шифрованный том сразу покрывает метаданные,
блобы, спул и `credentials.json`. Включайте шифрование там, где лежит том `/data`; снимки и копии зашифрованного тома остаются зашифрованными только если их делает тот же слой (облачные снимки) или вы шифруете архивы сами.

**От чего защищает:** кража или выбраковка диска и сервера, чтение снимков и копий диска вне хоста, извлечение данных с «вынутого» носителя.
**От чего не защищает:** от root или любого процесса на **работающем** хосте (том смонтирован, ключ в памяти), от атаки на S3-ключи, от уязвимости в сервере, от компрометации гипервизора/облачного аккаунта с правом использовать ключ KMS,
от резервных копий, снятых поверх шифрования (tar с открытого тома лежит открытым). Шифрование не заменяет TLS (он между клиентом и nginx) и IAM-политики.

### LUKS (dm-crypt) на Linux-хосте

**Не проверялось в этой среде:** в песочнице нет `cryptsetup` и подсистемы device-mapper (нет `/dev/mapper`), а установка пакетов закрыта. Проверена только вторая половина рецепта — монтирование отдельной файловой системы
в Docker-том через `driver_opts` (ext4 на loop-устройстве, сервер запустился и записал данные); шаги с `cryptsetup` приведены по документации и должны быть пройдены на тестовом хосте до боевого использования.

```bash
# 1. зашифровать раздел (УНИЧТОЖАЕТ его содержимое); пароль — только для первичной настройки, дальше ключевой файл
cryptsetup luksFormat --type luks2 /dev/sdb
cryptsetup luksHeaderBackup /dev/sdb --header-backup-file /safe/place/sdb-luks-header.img      # потеря заголовка = потеря данных
cryptsetup open /dev/sdb sectoria-crypt                                                          # /dev/mapper/sectoria-crypt
# 2. файловая система и монтирование
mkfs.ext4 -L sectoria /dev/mapper/sectoria-crypt            # xfs тоже подойдёт; нужны разрежённые файлы
mkdir -p /srv/sectoria && mount /dev/mapper/sectoria-crypt /srv/sectoria
mkdir -p /srv/sectoria/store && chown 100:101 /srv/sectoria/store   # пользователь sectoria в образе: uid 100, gid 101
# 3. Docker-том на этом каталоге
docker volume create --driver local --opt type=none --opt o=bind --opt device=/srv/sectoria/store sectoriadb-store
```

В `docker-compose.yml` вместо объявления `sectoriadb-store: {driver: local}` (или через `docker-compose.override.yml`):

```yaml
volumes:
  sectoriadb-store:
    driver: local
    driver_opts:
      type: none
      o: bind
      device: /srv/sectoria/store        # каталог должен существовать: Docker его не создаёт
```

После перезагрузки раздел закрыт: сервер не поднимется, пока вы не откроете и не смонтируете его. Порядок на старте: `cryptsetup open` → `mount` → `docker compose up -d`. Если Docker стартует раньше монтирования, контейнер получит пустой каталог
**на незашифрованном корневом диске** и создаст там пустое хранилище — задайте зависимость службы Docker от mount-юнита (`RequiresMountsFor=/srv/sectoria` в drop-in для `docker.service`) и не ставьте `restart: always`, пока это не настроено.

**Ключи.**
- Ключ не должен лежать на том же диске в открытом виде (иначе шифрование бессмысленно). Варианты по убыванию надёжности: ввод пароля при загрузке/вручную; ключевой файл на съёмном носителе или на отдельной машине, который подключают на время `cryptsetup open`;
  автоматическая разблокировка по TPM2 (`systemd-cryptenroll --tpm2-device=auto`) или по сети (Clevis + Tang) — удобно для серверов без оператора, защищает от кражи диска, но не от кражи всего сервера целиком.
- Заведите второй слот ключа (`cryptsetup luksAddKey`), храните резервную копию заголовка (`luksHeaderBackup`) и пароль восстановления отдельно от сервера. Потеря единственного ключа или повреждение заголовка необратимо уничтожает данные, и никакой `verify-all` этого не исправит.
- Отзыв: `cryptsetup luksKillSlot` убирает слот, но не перешифровывает данные — после компрометации ключа создайте новый том и перенесите данные.
- Swap и гибернация: если на хосте есть незашифрованный swap, содержимое памяти процесса (включая куски объектов) может попасть на диск; шифруйте swap или отключите его. Файлы `.env` (ключи S3) и `deploy/certs/privkey.pem` лежат вне тома — храните их на шифрованном разделе тоже.

### Шифрованные диски облака

**Не проверялось здесь** (нет облачного аккаунта); рецепты — по документации провайдеров, команды сверьте с их текущими версиями.
- **AWS EBS.** Включите шифрование по умолчанию для региона (`aws ec2 enable-ebs-encryption-by-default --region …`) или создавайте том с `--encrypted --kms-key-id <ключ>`. Моментальные снимки зашифрованного тома и тома из них шифруются тем же ключом.
  Свой ключ KMS (CMK) даёт управление доступом, ротацию и отзыв: отключение ключа делает диск и снимки нечитаемыми.
- **GCP Persistent Disk.** Диски шифруются всегда (ключи Google); для ключа заказчика — CMEK: `gcloud compute disks create … --kms-key projects/…/cryptoKeys/…`.
- **Azure Managed Disks.** Шифрование на стороне хранилища включено по умолчанию (ключи платформы); для своих ключей — Disk Encryption Set с ключом в Key Vault.
- Во всех трёх случаях данные расшифровывает платформа для работающей ВМ: защита от кражи носителя и от доступа к снимкам вне аккаунта, но не от того, у кого есть право использовать ключ или root в ВМ. Права на ключ KMS выдавайте отдельно от прав на снимки.

## Обновление

Формат файлов на диске в ходе разработки (этапы 01–15) менял несовместимо: старые блобы, JSON-метаданные, каталог `.multipart` и метаданные до
индекса чанков не читаются и не мигрируют (см. [CHANGELOG](../../CHANGELOG.md)). Для текущей версии действует правило: перед заменой образа
сделайте резервную копию; заголовки файлов несут версию формата (`SDBBLOB1`, `SDBSMOB1`, `SECTMETA`), и неизвестная версия отвергается явной ошибкой,
а не тихой порчей. Поэтому обновление с версии, чей формат на диске иной, — это создание хранилища заново и перезаливка данных.
Метахранилище создаёт новые деревья по мере использования, так что расширения формата внутри одной версии читаются.

Один процесс на каталог метаданных: второй сервер на том же `meta-dir` не стартует (блокировка файла).

## Сборка мусора и возврат места

Удаление и перезапись объекта сразу освобождают только ссылки на чанки. Место возвращает сборщик ([garbage-collection.md](../architecture/garbage-collection.md)):

- через период ожидания (`sectoriadb.gc.grace`, 15 минут) освобождаются слоты чанков без ссылок; освобождённые слоты переиспользуются новыми вставками;
- раз в 6 часов обход блобов находит копии чанков от оборванных загрузок;
- файлы `small_*.sob` с долей мёртвых записей ≥ 50 % (и ≥ 1 МиБ) переписываются; файл, куда сейчас идут записи, не трогается;
- **файлы `blob_*.raw` не уменьшаются**: слоты переиспользуются, но размер файла не падает. Чтобы вернуть место ОС, пересоздайте бакет.

Наблюдать: `gc status`, метрики `sectoriadb_chunks_gc_queue_length`, `sectoriadb_gc_freed_*_total`, `sectoriadb_gc_last_run_timestamp_seconds`.
Принудительно: `gc run --grace 0s` (читатель, держащий старую версию, может получить ошибку). Если GC выключен (`gc.enabled=false`), место не возвращается,
пока вы сами не запустите `gc run`.

## Рост и `resize`

Пул растёт добавлением блобов (`pool.grow-threshold-percent`, до `pool.max-blobs`); фоновая проверка раз в минуту. Если пул упёрся в `max-blobs` при заполнении выше порога,
в логе появляется предупреждение (также в `status`): поднимите `pool.max-blobs` (память: ≈9 МиБ на блоб) или расширьте блоб командой `resize --id … --buckets N` — запись
при этом не останавливается, старый файл удаляется через G, остатки сбоя убираются при старте.

## Восстановление после сбоев

- **Аварийное завершение (`kill -9`, потеря питания).** Ничего специального не требуется. Данные пишутся до коммита метаданных, коммит — переключение одной мета-страницы
  `sectoria.db`: объект либо виден целиком, либо отсутствует. Недописанное остаётся «мусором» для сборщика (обход блобов), недостроенный блоб от `resize`
  удаляется при старте. Для проверки: остановить сервер, `verify-all` (`RESULT: OK`).
- **Порча данных.** Любое чтение сверяет CRC; `500` на `GET` (или обрыв) и рост `sectoriadb_integrity_crc_failures_total` — инцидент. Найти: `verify-all`, `scrub --id`.
  Слоты с неверной записью метаданных попадают в карантин (не читаются и не перезаписываются, `sectoriadb_cuckoo_slots_quarantined`). Автоматического ремонта нет —
  восстановление из резервной копии; повторная загрузка тех же байт лечит битый чанк на месте.
- **Сбой метахранилища (диск не отвечает).** Чтение продолжается по последнему зафиксированному снимку, запись отвечает `503 SlowDown` или `507`, и сама возобновляется,
  когда диск снова работает (пауза `recovery-backoff`); в логе `Metadata store recovered after a failed commit`. Перезапуск не нужен; признак проблемы —
  `sectoriadb_metastore_recoveries_total{result="failure"}`.
- **Не стартует: файл занят.** Другой процесс держит `sectoria.db`. Остановите его.

## Заполнение диска

| Закончилось место на | Поведение |
|---|---|
| томе данных (`data-dir`) | запись отвечает `507 InsufficientStorage`, сервис жив (`/actuator/health` = UP), чтение работает; после освобождения места запись проходит без перезапуска |
| томе метаданных | первая ошибка записи `507`, дальше запись `507`/`503 SlowDown`, чтение работает; запись возобновляется сама, когда место появилось |
| томе спула (`upload-tmp-dir`) | загрузка или копия, которая вместе с уже идущими не оставит `sectoriadb.storage.min-free-bytes` (1 ГиБ), отвечает до начала приёма тела `503 SlowDown` (место занято другими загрузками) или `507 InsufficientStorage` (не поместится и в пустой очереди) |
| любом томе (спул, метаданные, данные) заметно раньше полного заполнения | любая запись (`PutObject`, `UploadPart`, `CopyObject`, `CreateMultipartUpload`, `CreateBucket`) при свободном месте меньше `sectoriadb.storage.min-free-bytes` отвечает `507`; чтение и удаление работают. Порог держит запас для metastore: на совсем полном томе не проходят и удаления |

Освободить место сервер сам не может: удалите объекты (и дождитесь/запустите `gc run`) или расширьте том. Мониторинг: `sectoriadb_disk_free_bytes{dir}`, алерты
`SectoriaDiskFreeLow`, `SectoriaDiskFullSoon` ([monitoring.md](monitoring.md)).

## Логи

- Консоль: `HH:mm:ss УРОВЕНЬ [логгер] [requestId операция] сообщение`; файл `<meta-dir>/sectoriadb.log` (полный формат; ротация по дням и по 100 МБ, 30 дней, архивы не более 500 МБ суммарно).
  Команда `logs --n N` показывает хвост файла.
- Уровень по умолчанию `INFO`; имён ключей объектов в логах нет (имя бакета есть в строках `Storing file` уровня `DEBUG`), секреты и подписи не логируются никогда. Запросы дольше `slow-request-ms` — `WARN Slow request: requestId=… operation=…`.
- **Объём логов на нагруженном сервере.** Построчные события хранилища (`Storing file…`, `Stored…`, `Object deleted…`, события multipart-загрузок, чтение и восстановление файлов, загрузка и вытеснение таблиц) пишутся на уровне `DEBUG`; на `INFO` остаются события жизненного цикла и администрирования (создание и удаление бакетов, пулов и блобов, расширение, компакция, проход сборщика мусора с работой, ключи доступа, открытие метахранилища).
  Каждая операция записи и удаления объекта по-прежнему пишет запись в `oplogs.jsonl` (хранится не более пяти архивов по 100 МБ), `sectoriadb.log` перекатывается на 100 МБ (архивы — до 500 МБ). До этого изменения `warp mixed` (около 1000 `PUT`/с) давал за 33 минуты 400 МБ `sectoriadb.log`. Подробные строки включает `LOGGING_LEVEL_ORG_EXAMPLE_SECTORIADB_STORAGE=DEBUG`.
- Каждый ответ несёт `x-amz-request-id`; тот же идентификатор в журнале и теле ошибки позволяет сопоставить жалобу клиента со строкой лога.

### Профиль `debug`

`SPRING_PROFILES_ACTIVE=debug` (или `--spring.profiles.active=debug`) включает `DEBUG` для приложения и `org.springframework.web`: **каждый запрос пишется вместе с бакетом и ключом**,
заметная нагрузка на CPU. Только для расследований; не оставляйте на постоянной основе.

## Безопасность эксплуатации

- Не публикуйте порт метрик `9464` наружу (без подписи), порт `8081` s3manager (полные права) и сам `8080` (только через nginx с TLS: [TLS через nginx](#tls-через-nginx)); `.env` и `deploy/certs/` не коммитьте.
- Не отключайте авторизацию на доступном из сети сервере (`sectoriadb.s3.auth.enabled=false` — только для разработки), не оставляйте `allow-open-setup=true`.
- Подробнее — [security.md](../architecture/security.md).
