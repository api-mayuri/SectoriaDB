# Рекомендации по использованию

Практическое руководство: подходит ли SectoriaDB под вашу задачу и что сделать перед тем, как положить в неё данные, которые жалко потерять.
Все утверждения сверены с кодом и свойствами; ссылки ведут к подробностям.

## Когда SectoriaDB подходит и когда нет

**Подходит**
- Один узел: домашний сервер, небольшая команда, стенд, резервные копии, медиа-архив, хранилище для приложений, которым нужен S3 API (path-style, SigV4).
- Много мелких объектов (меньше 16 КиБ хранятся целиком в журнале без накладных расходов слота) и повторяющиеся данные (дедупликация по бакету).
- Нужна проверяемая целостность: CRC32C на каждом чтении, `verify-all`, `x-amz-checksum-*`.

**Не подходит (пока)**
- Нужна отказоустойчивость узла: **репликации нет** (один узел), потеря диска — потеря данных; защита — снимки и копии на другом носителе или площадке и, при необходимости, репликация на уровне хранилища (ZFS/Btrfs send, облачные снимки в другую зону).
- Нужны пользователи, группы, роли, STS или OIDC: их нет. Права задаются **IAM-политикой на ключ** (стандартный документ AWS), ключ без политики имеет полный доступ ([security.md](../architecture/security.md#авторизация-подписанных-запросов-iam)).
- Нужны версионирование, блокировки объектов, CORS, lifecycle, шифрование на стороне сервера, POST-форма, S3 Select — не реализованы ([s3-usage.md](s3-usage.md)).
- Нужна масштабируемая запись: один писатель метаданных, потолок — коммиты в секунду вашего диска ([sandbox-results.md](../reports/sandbox-results.md), на песочнице порядка тысячи мелких `PUT`/с).
- Хостинг для недоверенных арендаторов без политик: ключи без IAM-политики не изолированы друг от друга; с политиками (один ключ на арендатора) бакеты изолированы, но ресурсы сервера общие.

## Чек-лист перед боевым использованием

1. **TLS-прокси впереди.** Сервер не терминирует TLS; перед ним стоит nginx из `docker-compose.yml` ([проверенная конфигурация ниже](#обратный-прокси-nginx)): настоящий сертификат в `deploy/certs/`, `SECTORIADB_S3_REQUIRE_SECURE_TRANSPORT=true` (в compose так по умолчанию), порт `8080` наружу не публикуется — только `443`/`80` nginx.
   Не запускайте боевой экземпляр с `docker-compose.dev.yml` (там нет TLS).
2. **Порт управления `9464` никогда не публиковать наружу** (метрики и health без аутентификации). В compose он уже на `127.0.0.1`, через nginx не проксируется; на голом jar привяжите `management.server.address=127.0.0.1`.
3. **Ключи** — через `mk-key` или `SECTORIADB_S3_CREDENTIALS`; **не запускайте с `sectoriadb.s3.auth.allow-open-setup=true`** и не отключайте `sectoriadb.s3.auth.enabled`. Один ключ — одному приложению или арендатору, с политикой наименьших прав ([ниже](#один-ключ-на-приложение-или-арендатора)). s3manager (`8081`, только в `docker-compose.dev.yml`) работает с полными правами: на проде не запускайте.
4. **`sectoriadb.fsync=true`** (по умолчанию). Отключение даёт скорость ценой потери подтверждённых записей при сбое питания — только для тестов.
5. **Один том, и он зашифрован.** `docker-compose.yml` уже держит всё состояние в одном томе `sectoriadb-store` (`/data/meta`, `/data/storage`, спул загрузок внутри): снимок одного тома атомарен для метаданных и блобов.
   На боевом хосте смонтируйте под этот том зашифрованную файловую систему (LUKS) или используйте шифрованный диск облака: шифрования на уровне приложения нет ([operations.md](operations.md#шифрование-на-диске)). Вне Docker держите `meta-dir` и `data-dir` на одной файловой системе.
6. **Расписание снимков тома и проверка копий.** Горячая копия — атомарный снимок тома (LVM, ZFS, Btrfs, снимок облачного диска) по расписанию; для малых установок — `deploy/backup/cold-backup.sh` из cron. Восстановление пробуется заранее, а не в день аварии:
   `deploy/backup/verify-backup.sh` по расписанию на **копии** (в cron раз в неделю или после каждого снимка), код возврата ≠ 0 — повод для тревоги. Копии храните не на том же диске ([резервные копии](#резервные-копии-и-проверка)).
7. **Память**: куча под `cache.max-resident-tables` (см. ниже); `restart: unless-stopped` и `ExitOnOutOfMemoryError` уже в образе.
8. **Запас диска** (см. ниже) и алерты (см. ниже).
9. Часы сервера и клиентов синхронизированы (NTP): допуск подписи ±15 минут.
10. **Длительный прогон на вашем железе до запуска в бой.** Утечка файловых дескрипторов, рост метахранилища или медленный дрейф задержки проявляются за часы: `bench/warp/soak.sh --duration 8h` ([benchmarking.md](../testing/benchmarking.md#длительный-прогон-soak)); смотрите отчёт о дрейфе в конце. Короткие прогоны песочницы (десятки минут) этого не заменяют.

## Один ключ на приложение или арендатора

Ключ без политики может всё: прочитать и удалить любой бакет. Это сохранено для совместимости, но на боевом сервере выдавайте каждому приложению или арендатору **свой ключ с минимальной политикой** (`key-policy`, действует сразу, без перезапуска):

| Кому | Политика ([deploy/iam](../../deploy/iam/)) |
|---|---|
| Приложение читает данные одного бакета | `read-only.json` |
| Приложение или арендатор работает со своим бакетом | `read-write.json` (подставьте имя бакета) |
| Резервное копирование: добавлять объекты, но не читать и не удалять | `backup-writer.json` (перезапись существующего ключа остаётся возможной, версионирования нет; держите отдельный бакет на запуск или проверяйте имена) |
| Администратор | ключ без политики, хранится отдельно |

```bash
$X mk-key --desc "tenant-a"                                    # выдаст ID и секрет
sed 's/example-bucket/tenant-a/g' deploy/iam/read-write.json > /tmp/tenant-a.json
$X key-policy --id ID --file /tmp/tenant-a.json
$X keys                                                        # колонка Policy: yes
```

Арендатору дайте бакет, созданный администратором (`CreateBucket` в политику не включайте), и не давайте `s3:PutBucketPolicy`, `s3:PutBucketAcl`, `s3:PutObjectAcl`: иначе он сможет открыть свой бакет анонимам. Изоляция только по бакетам и префиксам:
общих ресурсов сервера (диск, память, потоки) политики не делят, лимиты на ключ см. [security.md](../architecture/security.md#лимиты-и-защита-от-злоупотреблений).

## Обратный прокси (nginx)

**Проверено.** Конфигурация [deploy/nginx/sectoriadb.conf](../../deploy/nginx/sectoriadb.conf) (сервис `nginx` в `docker-compose.yml`, образ `nginx:1.27.5-alpine`) прошла проверку реальными клиентами при включённой проверке подписи
(матрица ниже). Установка, сертификаты и `require-secure-transport` — [operations.md](operations.md#tls-через-nginx).

Требования к прокси, вытекающие из устройства сервера, и как они выполнены:

| Требование | Директива | Что будет без неё |
|---|---|---|
| `Host` как пришёл, вместе с портом | `proxy_set_header Host $http_host;` | SigV4 подписывает `host`: `SignatureDoesNotMatch` |
| Путь не переписывается | `proxy_pass http://sectoriadb;` **без URI-части** | nginx отправил бы нормализованный путь; ключи с пробелами, `+`, `%`, `//`, `../`, юникодом и эмодзи не сошлись бы с подписью. `merge_slashes off` не нужен: путь берётся из исходной строки запроса (проверено и с `merge_slashes on`) |
| Тело до 5 ГиБ | `client_max_body_size 5g;` | `413` на больших загрузках (проверено: заголовок `Content-Length` больше лимита сразу даёт `413`) |
| Без буферизации запроса и ответа | `proxy_request_buffering off; proxy_buffering off;` | тело ложится на диск прокси и доходит до сервера после полной загрузки; `GET` большого объекта не стримится |
| Длинные операции | `proxy_send_timeout`, `proxy_read_timeout`, `send_timeout` — `3600s` | обрыв на минутной загрузке/скачивании |
| HTTP/1.1 и keep-alive к серверу | `proxy_http_version 1.1; proxy_set_header Connection "";` + `upstream … { keepalive 32; }` | новое TCP-соединение на каждый запрос |
| Схема для сервера | `proxy_set_header X-Forwarded-Proto $scheme;` | `require-secure-transport` отвергает все запросы; `aws:SecureTransport` в политиках не сработает |
| Заголовки с `_` | `underscores_in_headers on;` | nginx по умолчанию молча отбрасывает такие заголовки (S3-клиентам они не нужны, но не теряем) |

Что проверено в потоке данных (через nginx, подпись включена): `aws-chunked` с `Transfer-Encoding: chunked` и `Expect: 100-continue` (так по умолчанию грузит `aws cli`/botocore) проходит; `Expect: 100-continue` с известной длиной — клиент получает `100 Continue` и `200`;
`PUT` с `Transfer-Encoding: chunked` без `aws-chunked` и без `Content-Length` получает `411 MissingContentLength` — так же, как без прокси (сервер требует размер, [security.md](../architecture/security.md)); HTTP/2 к nginx работает (`curl --http2`);
TLS 1.0 и 1.1 отвергаются (`protocol version`), 1.2 и 1.3 принимаются. Известное ограничение сервера, не прокси: `%2F` внутри пути (закодированный `/`) отклоняет Tomcat (`400`) и без nginx; SDK и CLI слэш в ключе не кодируют.

**Матрица клиентов** (все через `https://localhost`, самоподписанный сертификат из `deploy/gen-self-signed.sh`, `sectoriadb.s3.auth.enabled=true`, `require-secure-transport=true`):

| Клиент | Что проверено | Итог |
|---|---|---|
| `aws cli` 1.46.1 (botocore 1.43) | `mb`, `cp` малого и 200 МиБ (multipart, 25 частей, `aws-chunked` + трейлер CRC32), `cp` обратно (sha256 совпал), `ls`, `GET` с `Range`, `presign` + `curl` (диапазон и целиком), `put-object --checksum-algorithm SHA256`, загрузка из stdin, 9 ключей с пробелами, `+`, `%`, `//`, `../`, `?#&;`, юникодом и эмодзи (запись, чтение, листинг) | работает |
| `rclone` 1.75.2 | `copy` каталога (малые, 120 МиБ, имя с пробелом, `+` и эмодзи), multipart (`--s3-upload-cutoff 50M`, 8 частей), `check --download`, `copy` обратно (`diff -r` пуст) | работает |
| `s3cmd` 2.4.0 | `ls`, `put`/`get` с именем из пробела, `+` и юникода, multipart 40 МиБ (`--multipart-chunk-size-mb=15`) | работает |
| `curl` 8.5 | presigned `GET` (HTTP/1.1 и HTTP/2, `Range`), `PUT` по presigned-ссылке с `Expect: 100-continue`, `--aws-sigv4` с путём `../` | работает |
| `minio/warp` 1.3.1 | `mixed`, 16 потоков, 1 МиБ и 4 КиБ, `--tls --insecure` | без ошибок |
| `http://localhost:80` | `301` на `https://localhost/<тот же путь и запрос>` | работает |
| `http://localhost:8080` с хоста | порт не опубликован: соединение отвергнуто | как задумано |
| запрос в сервер мимо nginx по HTTP (из сети compose) | `403 InsecureTransport` | как задумано |

Накладные расходы TLS и прокси, один короткий замер (`warp mixed`, 16 потоков, 30 с, 4 vCPU песочницы, на которых одновременно работают warp, nginx и сервер — это худший случай; цифры не про боевое железо и сильно зависят от процессора и от того, где клиент):

| Профиль `warp mixed` | напрямую (`sectoriadb:8080`) | через nginx + TLS (`nginx:443`) | разница |
|---|---|---|---|
| 1 МиБ, два прогона в разном порядке | 490 и 488 МиБ/с (817 и 814 объектов/с) | 340 и 314 МиБ/с (566 и 523 объектов/с) | −31…−36 % |
| 4 КиБ, один прогон | 2561 объектов/с | 1991 объектов/с | −22 % |

Ошибок в прогонах не было. Отключение HTTP/2 на nginx цифры не меняет (320 МиБ/с на 1 МиБ). Это порядок величины на 4 vCPU, где процессор делят warp, nginx и сервер; на своём железе замерьте сами (`bench/warp`).

## Резервные копии и проверка

- Хранилище **консистентно при аварийной остановке по построению** (данные до метаданных, атомарный коммит одной мета-страницы; проверено `kill -9` во время `PUT` и multipart, тестами потери несброшенных записей и копиями работающего сервера — [fault-injection.md](../testing/fault-injection.md)).
  Поэтому атомарный снимок тома эквивалентен аварийному выключению питания и откатывается сам при старте. Копирование `meta` и `storage` у работающего сервера «по очереди» снимком не является: такая копия не проходит `verify-all` (проверено контрольным прогоном).
- Что делать: **снимок единственного тома по расписанию** (LVM `lvcreate --snapshot`, ZFS `zfs snapshot`, Btrfs `btrfs subvolume snapshot -r`, снимок облачного диска) — горячо, без остановки и без команд консоли. Или `deploy/backup/cold-backup.sh` (короткая остановка).
  Восстановление — смонтировать снимок как `/data` и запустить сервер; последние подтверждённые записи после снимка не вернутся (частота снимков = допустимая потеря).
- Регулярно проверять **копию**, а не живой экземпляр: `deploy/backup/verify-backup.sh архив-или-каталог` поднимает одноразовый контейнер на копии и выполняет `verify-all` (OFFLINE); успех — `RESULT: OK` и код возврата 0. Копия, не прошедшая проверку, не копия.
- Реплики нет: снимки на том же диске не спасают от потери диска. Отправляйте копии на другой носитель, площадку или зону (репликация снимков ZFS/Btrfs, облачные снимки в другой зоне, копирование архивов).
- `credentials.json` (секреты открытым текстом) лежит в том же томе — копии защищайте так же, как ключи: шифрованный диск, облачные снимки зашифрованного диска, `age`/`gpg` для архивов.
- Журнал и `.tmp` восстанавливать не нужно. Подробности и команды — [operations.md](operations.md#резервное-копирование).

## Память и JVM

Каждая резидентная таблица кукушкиного блоба — около 9 МиБ кучи при настройках по умолчанию; `sectoriadb.cache.max-resident-tables` (64) — около 576 МиБ, предел мягкий (используемые таблицы не закрываются).
Куча в образе — 70 % лимита контейнера. Правило: лимит контейнера ≥ 1,5 ГиБ при значении по умолчанию; для малого контейнера уменьшайте `SECTORIADB_CACHE_MAX_RESIDENT_TABLES` (каждый бакет с чанковыми объектами — минимум одна таблица, а пул растёт блобами до `pool.max-blobs`=16).
Следите за `sectoriadb_cuckoo_tables_loaded / sectoriadb_cuckoo_tables_max` и паузами GC; частые вытеснения (`sectoriadb_cuckoo_tables_evicted_total`) значат, что активных блобов больше лимита и чтение «холодных» страдает от загрузки таблицы.

## Запас места на диске

- Тома: данные (`blob_*.raw` — разрежённые, растут по мере записи; новые блобы добавляются при заполнении 75 %), метаданные (`sectoria.db` растёт и не усекается), спул загрузок (`<data-dir>/.tmp`: нужно место под самые большие параллельные загрузки, до 5 ГиБ каждая).
- Загрузка принимается только если помещается в спул вместе с запасом 64 МиБ (`upload-free-space-reserve-bytes`), иначе `503 SlowDown`.
- Заполнился диск — запись отвечает `507 InsufficientStorage`, чтение работает, после освобождения места запись возобновляется без перезапуска ([operations.md](operations.md)). Не доводите до этого: держите **свободными не менее 15–20 %** (алерт `SectoriaDiskFreeLow` срабатывает на 15 %).
- Удаление возвращает место не сразу и не уменьшает `blob_*.raw` ([garbage-collection.md](../architecture/garbage-collection.md)): планируйте ёмкость по пику.

## Сборка мусора и долгие GET

Период ожидания `sectoriadb.gc.grace` (15 минут): читатель, держащий старую версию объекта дольше этого срока (скачивание очень большого файла медленным клиентом, пока объект перезаписывают или удаляют), может получить обрыв.
Если у вас такие сценарии — увеличьте `grace` (место вернётся позже). Загрузка, не уложившаяся в `grace` после обнаружения повторяющегося чанка, получает `503` с `Retry-After` — клиент должен повторять запрос (все SDK и `aws cli` повторяют `503`).
Не держите `gc.enabled=false` на постоянной основе: место не вернётся.

## Multipart

Каждая часть, кроме последней, не меньше 5 МиБ (`sectoriadb.multipart.min-part-size`), иначе `Complete` отвечает `400 EntityTooSmall`; размер проверяется при `Complete`, а не при `UploadPart`. Частей не больше 10000, один запрос — не более 5 ГиБ.
`aws cli`/SDK/rclone по умолчанию режут по 5–8 МиБ и больше — совместимо. Брошенные загрузки занимают место до `stale-after` (7 суток); смотрите `aws s3api list-multipart-uploads`.

## Мониторинг: какие алерты включить

Правила — `bench/observability/prometheus/alerts.yml` ([monitoring.md](monitoring.md)); для боя нужны минимум эти (подберите пороги по своему железу):

| Алерт | Что делать при срабатывании |
|---|---|
| `SectoriaIntegrityFailure`, `SectoriaQuarantinedSlots` (critical) | остановить запись в затронутый бакет, `verify-all` и `scrub --id` на остановленном сервере, восстановить затронутые объекты из копии |
| `SectoriaTableFull`, `SectoriaFillHigh`, `SectoriaFillCritical` | поднять `sectoriadb.pool.max-blobs` (память!) или проверить рост пула; освободить данные |
| `SectoriaDown`, `SectoriaServerErrors` | логи (`requestId` из ответа), здоровье диска, `docker compose ps`, `/actuator/health` |
| `SectoriaDiskFreeLow`, `SectoriaDiskFullSoon` | расширить том или удалить данные; помнить про период ожидания GC |
| `SectoriaMetastoreRecoveryFailed` | диск метаданных не отвечает или полон; чтение работает, запись вернётся сама после исправления |
| `SectoriaGcErrors`, `SectoriaGcStale`, `SectoriaResizeFailed` | `gc status`, логи; убедиться, что `gc.enabled=true` |
| `SectoriaFsyncSlow`, `SectoriaPutLatencyHigh` | деградация диска; сравнить с базой измерений на вашем железе |
| `SectoriaAuthFailureBurst`, `SectoriaClockSkew` | подбор ключей или сбитые часы клиентов |

Alertmanager в стенде нет — подключите свой.

## Обновления

Формат данных на диске между этапами разработки **несовместим**, миграторов нет ([CHANGELOG](../../CHANGELOG.md)). Политика: поднимите **новый экземпляр** на новой версии с пустыми томами и скопируйте данные через S3:
`aws s3 sync s3://bucket s3://bucket --endpoint-url …` между двумя endpoint'ами (через промежуточный каталог) или `rclone sync old:bucket new:bucket`; затем проверка `verify-all` на новом экземпляре и переключение клиентов.
ACL, политики бакетов и ключи доступа не копируются синхронизацией данных — воспроизведите их (ключи через `mk-key`/окружение). Незавершённые multipart-загрузки не переносятся. Перед переключением оставьте старый экземпляр (и его снимок) нетронутым.

## Настройки клиентов

Всегда **path-style** (`http(s)://host/bucket/key`; virtual-hosted не поддерживается) и регион, равный `sectoriadb.s3.region` (`us-east-1` по умолчанию; иначе `AuthorizationHeaderMalformed`).
Проверялись набором совместимости ([compatibility.md](../testing/compatibility.md)): `aws cli`, boto3 (ceph/s3-tests), `s3cmd`, `mc`, AWS SDK Go/PHP/Ruby и minio-SDK (часть наборов mint завершается с известными отказами). `rclone` в наборы не входит — настройка ниже стандартная, проверьте её на вашем экземпляре.

Ниже — настройки для HTTPS через nginx; проверены на `aws cli` 1.46.1, `rclone` 1.75.2 и `s3cmd` 2.4.0 (в проверке вместо `s3.example.com` был `localhost` с самоподписанным сертификатом). Строки про свой CA нужны только для самоподписанного или корпоративного сертификата;
для Let's Encrypt их не добавляйте.

`aws cli` (`~/.aws/config`):

```ini
[profile sectoria]
region = us-east-1
# ca_bundle нужен только для самоподписанного или корпоративного CA
ca_bundle = /путь/к/fullchain.pem
s3 =
    addressing_style = path
    signature_version = s3v4
    multipart_threshold = 64MB
    multipart_chunksize = 16MB
endpoint_url = https://s3.example.com
```
```ini
# ~/.aws/credentials
[sectoria]
aws_access_key_id = ВАШ_КЛЮЧ
aws_secret_access_key = ВАШ_СЕКРЕТ
```
```bash
aws --profile sectoria s3 cp big.iso s3://bucket/ --checksum-algorithm SHA256       # сервер сверит сумму
aws --profile sectoria s3api head-object --bucket bucket --key big.iso --checksum-mode ENABLED
aws --profile sectoria s3 presign s3://bucket/big.iso --expires-in 3600              # ссылка открывается в curl/браузере
```
`signature_version = s3v4` нужен AWS CLI v1: без него `presign` выдаёт подпись v2 (`AWSAccessKeyId=…`), которую сервер не принимает. Директива `endpoint_url` в профиле работает в AWS CLI v2 и в проверенной v1.46; на старых v1 используйте ключ `--endpoint-url`. По умолчанию клиент (`aws-chunked` с трейлером CRC32) сервер принимает; если ваш клиент шлёт неподдерживаемую сумму/режим — задайте
`request_checksum_calculation = when_required` (новые версии CLI/SDK) — сервер принимает CRC32/CRC32C/CRC64NVME/SHA1/SHA256.

`rclone` (`rclone.conf`):

```ini
[sectoria]
type = s3
provider = Other
access_key_id = ВАШ_КЛЮЧ
secret_access_key = ВАШ_СЕКРЕТ
endpoint = https://s3.example.com
region = us-east-1
force_path_style = true
chunk_size = 16M
```
Свой CA: ключ `--ca-cert /путь/к/fullchain.pem` в командной строке (в `rclone.conf` его нет). Multipart включается выше `upload_cutoff` (по умолчанию 200 МиБ; для проверки `--s3-upload-cutoff 50M`).

`s3cmd` (`~/.s3cfg`):

```ini
access_key = ВАШ_КЛЮЧ
secret_key = ВАШ_СЕКРЕТ
host_base = s3.example.com
host_bucket = s3.example.com
use_https = True
# ca_certs_file нужен только для самоподписанного или корпоративного CA
ca_certs_file = /путь/к/fullchain.pem
bucket_location = us-east-1
signature_v2 = False
```
`s3cmd signurl` подписывает по v2 и выдаёт `http://`-ссылку — для presigned-ссылок используйте `aws s3 presign`.

Для проверки целостности на стороне клиента включайте `--checksum-algorithm` (CLI/SDK) и читайте с `x-amz-checksum-mode: ENABLED`; клиент, не сверяющий длину ответа, может принять обрыв повреждённого `GET` за конец файла.
