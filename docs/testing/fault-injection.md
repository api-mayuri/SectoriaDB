# Отказы и безопасность

Скрипты лежат в `bench/faults/`; каждый печатает `PASS` / `FAIL` / `INFO` и возвращает ненулевой код при `FAIL`. Все они
поднимают собственный контейнер `sectoriadb-fault` (порт 8090, каталоги данных в `bench/faults/work/`), поэтому стенд
на 8080 не затрагивают. `bench/faults/run-all.sh` запускает всё подряд (`snapshot-backup.sh` тоже, около двух минут).

Проверка целостности после отказа выполняется **офлайн**: контейнер останавливается и запускается
`java -jar sectoriadb.jar verify-all` (CLI-режим: без веб-сервера, JVM завершается сам; метахранилище однопроцессное,
поэтому сервер при этом должен быть остановлен). Вывод: число проверенных объектов и `RESULT: OK` или `RESULT: FAILED`.
`verify` и `verify-all` — разовые CLI-команды ([admin-shell.md](../guide/admin-shell.md)).

**Окна отказа при PUT.** Тело запроса сначала сохраняется во временный файл (контрольные суммы проверяются до того,
как что-либо попадёт в блоб), затем чанки пишутся в блоб, затем **одна** транзакция метахранилища делает объект видимым.
Поэтому:

1. отказ при приёме тела: ничего не записано;
2. отказ при записи чанков: в блобе остаются чанки, на которые не ссылается ни один манифест. Они безвредны (объекта нет,
   чтение не затронуто), но занимают место до сборщика мусора ([garbage-collection.md](../architecture/garbage-collection.md): обход блобов освобождает такие слоты); так же ведёт себя отказ между
   записью и коммитом;
3. отказ во время коммита: метахранилище копирует страницы при записи и переключает мета-страницу: транзакция либо
   зафиксирована целиком, либо её нет.

Все три `kill -9` при записи 800 МиБ (10, 50, 90 %) пришлись на окно 2: после перезапуска объекта нет, повторный PUT проходит,
`verify-all` чист.

**Полный диск.** Подробности для каталога данных (ext4 на 64 МиБ, свободно 15 МиБ, объекты по 2 МиБ из случайных данных):
первые 6 PUT проходят, седьмой получает `507 InsufficientStorage` (`The server has run out of storage space...`); сервис
остаётся живым (`/actuator/health` = UP), GET раньше записанных объектов работает, следующие PUT отвечают 507 до
освобождения места, после удаления постороннего файла с этого диска PUT проходит **без перезапуска**, `verify-all` чист.
Метрики:
`sectoriadb_s3_errors_total{code="InsufficientStorage"}`, `sectoriadb_disk_free_bytes{dir="data"}` падает до 0, в логе
`ERROR ... the disk is full`. Освободить место сам сервер не может: удалите объекты и дождитесь сборщика мусора (или `gc run`).

Если заканчивается место на диске **метаданных** (`TARGET=meta`): первая ошибка записи `507`, дальше запись отвечает `507`/`503 SlowDown`, чтение целых объектов продолжает работать по последнему зафиксированному состоянию,
а запись возобновляется сама, когда диск снова работает, без перезапуска (прогон: 7234 PUT по 1 КиБ до `507`, `verify-all` — 7236 объектов, `RESULT: OK`, 9 PASS из 9). Ранняя реализация отравляла хранилище целиком и требовала перезапуска; этого больше нет.

**Порча данных.** При порче байтов в чанке и в записи малого объекта: `verify-all` печатает `CORRUPT` с причиной
(`Chunk corrupted: ... CRC32C mismatch`, `Small object corrupted: ... data CRC32C mismatch`) и завершается `RESULT: FAILED`;
GET отвечает `500 InternalError` (заголовки ещё не отправлены), тело с неверными байтами не отдаётся; счётчик
`sectoriadb_integrity_crc_failures_total{kind="chunk"}` и `{kind="small_record"}` растёт. Объекты с общими чанками
(дедупликация) портятся вместе: это ожидаемо.

**Сеть.** `tc netem` в песочнице недоступен: в ядре нет `CONFIG_NET_SCH_NETEM` (`Error: Specified qdisc kind is unknown`).
На обычном хосте: `docker run --rm --cap-add NET_ADMIN --network container:<сервер> nicolaka/netshoot tc qdisc add dev eth0
root netem delay 100ms 20ms loss 1%` (убрать: `tc qdisc del dev eth0 root`). Вместо него `slowproxy.py` (асинхронный TCP-прокси:
задержка, ограничение скорости, обрыв с RST после N байт) покрывает основное: обрыв PUT на 15 МиБ из 40 не оставляет
частичного объекта и не оставляет «зависших» запросов (`sectoriadb_s3_requests_inflight` возвращается к 0; сервер считает
обрыв как `Http400` для `PutObject`), PUT через медленную линию проходит и читается без искажений.

## Резервная копия снимком работающего сервера

Горячая копия в [operations.md](../guide/operations.md#резервное-копирование) опирается на одно свойство: том, снятый в один момент, — это диск после потери питания, и сервер при старте приводит его в согласованное состояние. `snapshot-backup.sh` проверяет это на работающем сервере:

1. Сервер (`sectoriadb:bench`) стартует с одним томом на `/data`. Четыре потока (`snapshot_check.py write`) в цикле делают `PUT` случайных объектов (70 % — до 64 КиБ, 25 % — до 3 МиБ, 5 % — 6–20 МиБ), перезаписывают те же 40 ключей на поток и удаляют их; перед запросом в журнал пишется `BEGIN ключ sha256`, после ответа `2xx` — `ACK ключ sha256`.
2. Через 8 с и затем каждые 6 с: `docker pause` (cgroup freezer — ни одна инструкция сервера не выполняется, ничего не сбрасывается и не закрывается: это «мгновение снимка»), копия тома во второй том одноразовым контейнером (`cp -a`), копия журнала записей, `docker unpause`.
   Журнал копируется во время заморозки, поэтому в нём только операции, подтверждённые до неё (подтверждение пишется после коммита сервера).
3. Каждая копия проверяется как восстановленная: `verify-all` на копии (`RESULT: OK`), сервер стартует на копии, `snapshot_check.py check` читает каждый ключ журнала: содержимое равно состоянию после последнего `ACK` или любому более позднему `BEGIN`
   (запрос без ответа мог примениться, а мог нет), листинг не содержит неизвестных ключей; счётчик CRC-сбоев 0.

Результат (2026-10-18, образ собран из ветки; `ROUNDS=3 WRITE_SECONDS=45`): **9 PASS, 0 FAIL**. Копии сняты при 459, 931 и 1203 подтверждённых операциях (одновременно шли запросы, включая большие `PUT`), `verify-all`: 136–140 объектов, `corrupt=0 missing=0`;
152–160 ключей журнала совпали с содержимым копии. **Контрольный прогон** (`NEGATIVE=1`: без заморозки, сначала `storage`, через 4 с `meta`, сервер пишет): `verify-all` — `RESULT: FAILED (corrupt=20, missing=102)`, проверка содержимого — 125 ключей из 159 недоступны. Значит, тест ловит несогласованную копию,
а запрет «копировать каталоги по очереди» обоснован.

Что это доказывает и чего нет. Заморозка процесса не равна блочному снимку: копия видит всё, что процесс успел записать в файловую систему (кэш страниц), то есть не меньше, чем увидел бы снимок диска; настоящий снимок мог бы не содержать
ещё не сброшенного хвоста. Устойчивость к такому хвосту проверена отдельно (`kill -9`, потеря несброшенных записей в тестах движка и мета-хранилища, [выше](#отказы)). Реальные снимки LVM, ZFS, Btrfs и облачных дисков в песочнице недоступны и не проверялись.

## Фаззинг парсеров

Парсеры, принимающие недоверенный ввод, покрыты тестами со случайными и мутированными входами (стандартный JUnit, фиксированное зерно — прогон повторяем, общее время около 20 с без запуска контекстов Spring; Jazzer не нужен):
`ParserFuzzTest` (заголовки `Range` и `x-amz-copy-source-range`, `x-amz-copy-source`, декодер `aws-chunked` с подписью и без), `HttpParserFuzzTest` (XML `DeleteObjects`, `CompleteMultipartUpload`, ACL, заголовки `x-amz-acl`/`x-amz-grant-*`, `Range`, copy-source через HTTP, враждебные формы XML: глубина 60 000, 50 000 элементов, 20 000 атрибутов, сущности, внешние сущности),
`SigV4HeaderFuzzTest` (`Authorization`, `x-amz-date`, `x-amz-content-sha256`, параметры presigned-запроса при включённой авторизации). Проверяется только одно: ответ — успех или документ ошибки S3 (4xx; для SigV4 — только 4xx), без 5xx, зависаний и оборванных соединений; чистые парсеры — только документированные исключения (`S3Exception`, `IOException`).
Найдено и исправлено: заголовок `Range: bytes=` (без диапазона) приводил к `ArrayIndexOutOfBoundsException` и ответу `500` — теперь игнорируется, как любой неверный `Range`; разбор неверного XML выводил в stderr процесса строку `[Fatal Error]` на каждый такой запрос в обход журнала — отключено.

## Фаззинг с обратной связью по покрытию (Jazzer, этап 23)

Форматы на диске и XML-тело `CompleteMultipartUpload` фаззятся [Jazzer](https://github.com/CodeIntelligenceTesting/jazzer) (`@FuzzTest`):

| Тест | Цель | Допустимый исход |
|---|---|---|
| `PageFormatFuzzTest#treePageDecode` | страница B+-дерева `sectoria.db` | `CorruptedPageException` |
| `PageFormatFuzzTest#metaPageParse` | мета-страница (половина входов — с верным `MAGIC` и CRC) | недействительна или `UnsupportedFormatException` |
| `LayoutFuzzTest` (3 цели) | заголовки `blob_*.raw`, `small_*.sob`, заголовок записи малого объекта | `InvalidBlobHeaderException` / `null` |
| `RecordFormatFuzzTest` (3 цели) | записи манифеста и чанка, строка очереди надгробий | `IllegalStateException` |
| `CompleteXmlFuzzTest` | тело `CompleteMultipartUpload` (половина входов — правки корректного документа) | `S3Exception` |

`mvn test` воспроизводит только сохранённые входы (`src/test/resources/<пакет>/<Тест>Inputs/<метод>/`) — секунды. Фаззинг одной цели:
`JAZZER_FUZZ=1 mvn -pl sectoriadb-core test -Dtest='RecordFormatFuzzTest#tombstoneRow'` (длительность — `maxDuration` в аннотации; рабочий корпус
`.cifuzz-corpus/` и новые `crash-*` в git не попадают — найденный вход, который стоит сохранить, переносится в каталог `…Inputs`).

Прогон 2026-10-29, по 1–2 минуты на цель в песочнице:

- **найдено и исправлено:** повреждённая строка очереди надгробий (длина поля больше значения) роняла разбор с `BufferUnderflowException`; сборщик
  мусора падал бы на ней в каждом проходе, и очередь вставала навсегда. Теперь разбор проверяет длины и бросает `IllegalStateException`, а сборщик
  отбрасывает такую строку с `ERROR` в журнале и собирает остальные (`DamagedQueueRowTest`; без исправления тест падает);
- ложная находка в самом тесте (перекодирование страницы в буфер меньшего размера) — тест исправлен;
- остальные цели — без находок.

Минуты фаззинга — это проверка дыма, не исчерпывающий поиск; перед релизом стоит запускать цели на часы (ночной прогон).
