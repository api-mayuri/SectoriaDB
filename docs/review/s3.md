## A. Security and correctness
---------------------------------------------------------------------------------------------------

### A1 (H) Anonymous exfiltration via CopyObject into a public-read-write bucket
`s3/access/AccessControlService.java:226-235` allows anonymous `PUT` when the bucket ACL is `public-read-write` (or a policy Allows
`s3:PutObject`). It never looks at `x-amz-copy-source`, and `isPrivateQuery` (l.320-332) only blocks sub-resource params.
`S3ObjectController.copyObject` (l.377-475) then reads ANY bucket/key as the source (no permission check on the source at all),
and `accessControl.applyObjectAcl` (l.456) honours `x-amz-acl: public-read` from the same anonymous request.
Attack: `PUT /open-bucket/loot` + `x-amz-copy-source: /private/secret` + `x-amz-acl: public-read` -> anonymous `GET /open-bucket/loot`
returns the private object. Same for UploadPartCopy only if `uploadId/partNumber` were allowed (they are denied, good).
Fix: in `isAnonymousAllowed` return false when the request has `x-amz-copy-source` (anonymous copy is never meaningful), or evaluate
`s3:GetObject` on the source with the same ACL/policy logic. Add a test to `S3PublicAccessTest`.

### A2 (H) Non-ASCII metadata breaks SigV4 - root cause (doc 08, "other 13")
Tomcat decodes header bytes as ISO-8859-1, so `request.getHeader("x-amz-meta-x")` for the UTF-8 bytes of "é" is the 2-char string "Ã©".
The SDK signs the raw UTF-8 bytes. `SigV4Filter.java:219-220` and `:321-322` do `canonicalRequest.getBytes(UTF_8)`, which turns each
Latin-1 char into 2 bytes (4 bytes instead of 2) -> hash differs -> `SignatureDoesNotMatch`.
Fix (one line each): hash `canonicalRequest.getBytes(StandardCharsets.ISO_8859_1)`. Everything else in the canonical request
(method, percent-encoded URI/query, hex hash) is pure ASCII, so Latin-1 bytes == the exact bytes the client signed, and invalid UTF-8
values are handled too. Keep storing metadata as received (Latin-1 view): it round-trips byte-exact on output
(`S3ObjectController.java:194,349`). Add a SigV4TestClient case with `x-amz-meta-name: Zoë 日本`.
Related: raw non-ASCII bytes in the request LINE are also Latin-1 chars; `SigV4Utils.canonicalizeUri:73` -> `S3Support.percentDecode:160`
re-encodes each char as UTF-8 (double-encodes). SDKs percent-encode, so low impact; fix by decoding unreserved raw chars via ISO_8859_1 bytes.

### A3 (H) Memory DoS: unbounded `readAllBytes()` / DOM parsing of request bodies (authenticated)
- `S3AclController.java:59` (PutBucketAcl), `:95` (PutObjectAcl), `:158` (PutBucketPolicy): `request.getInputStream().readAllBytes()`.
  A key holder sends a multi-GB body -> OOM of the whole server.
- `S3BucketController.java:120/148` DeleteObjects: `db.parse(body)` builds a DOM of an arbitrary size; the 1000-key check (l.122) comes AFTER parsing.
- `S3MultipartController.java:349/818` CompleteMultipartUpload: same, plus `new byte[16 * partNums.size()]` (l.382) before any check.
- `AccessControlService.parseAclFromXml` receives the already-read byte[].
Fix: one helper `RequestBodies.readLimited(request, maxBytes)` using `readNBytes(max+1)` and throwing `EntityTooLarge`/`MalformedXML`; limits:
policy 20 KiB (AWS limit), ACL 64 KiB, DeleteObjects 2 MiB (1000 keys x 1 KiB + overhead), CompleteMultipartUpload 2 MiB (10 000 parts x ~200 B).
Parse from the capped byte[]. Optional: StAX instead of DOM and cap element counts.

### A4 (H) aws-chunked parser: allocate-before-receive and unbounded trailers (memory DoS)
- `s3/auth/AwsChunkedInputStream.java:343` `new byte[chunkSize]` with chunkSize up to MAX_CHUNK_SIZE=16 MiB (l.258) taken from the header line
  BEFORE a single data byte arrived. 200 Tomcat threads x 16 MiB = 3.2 GiB heap from tiny requests. Fix: grow the buffer as bytes arrive
  (read in 64 KiB steps into a ByteArrayOutputStream-like growable array) and lower the cap to 8 MiB (AWS SDKs use 64 KiB..8 MiB).
- `readTrailers` (l.391-403) loops until an empty line with no cap on line COUNT: every line <= 8 KiB (MAX_LINE) but unlimited lines
  accumulate in the `trailers` map (and in unsigned-trailer mode no signature is needed). Cap to e.g. 16 trailers / 16 KiB total.
- `readLine` (l.424-436) reads byte-by-byte from the servlet stream: fine for bound (8192), but the header line itself is read only
  after the previous chunk completed; keep MAX_LINE <= 1 KiB for the chunk header line (a valid one is ~100 B) and keep 8 KiB for trailers.
- `x-amz-decoded-content-length` is only used for the 5 GiB pre-check (`S3Support:69`); the decoded length is never compared with what was
  actually decoded. With signed chunks truncation is caught by the signature chain, with `STREAMING-UNSIGNED-PAYLOAD-TRAILER` a short body
  that still ends with a 0-chunk is accepted. Compare in `AwsChunkedInputStream` at the final chunk (pass the declared length in).
- No cap on the TOTAL decoded size (see A5).

### A5 (H) No effective upload size limit when Content-Length is absent -> temp-volume DoS
`S3Support.requireDeclaredSizeWithinLimit:67-77` uses `getContentLengthLong()` which is -1 for `Transfer-Encoding: chunked` and ignores a
missing `x-amz-decoded-content-length`; `FileStorageService.stageStream` (core :357-375) then `Files.copy`s to `java.io.tmpdir` with no cap,
and CopyObject (S3ObjectController:429) and UploadPart (S3MultipartController:186) do the same. Real S3 answers 411 MissingContentLength.
Fix: (1) for PutObject/UploadPart without Content-Length and without decoded length -> 411; (2) wrap the body in `LimitedInputStream(5 GiB)`
that throws `EntityTooLarge`; (3) check `Files.getUsableSpace(tmpdir) > declared + reserve` before spooling (503 SlowDown); (4) put the temp
dir under the data dir (`sectoriadb.tmp-dir`) so ops can size it. Also copy: spool 2x the object (see E3).

### A6 (H) Slow-body DoS (doc 08: 220 slow authenticated PUTs exhaust the 200 Tomcat threads) - concrete settings and code
Root causes: `server.tomcat.connection-timeout=10m` (application.properties:7) is the socket read timeout, so a client that trickles one byte
every <10 min holds a worker for the whole upload; there is no minimum-rate rule, no per-key concurrency cap, and workers are platform threads.
Layered fix:
1. Virtual threads (Java 21, Boot 3.3): `spring.threads.virtual.enabled=true`. A blocked body read then costs ~KBs, not a platform thread.
   Caveats: replace `synchronized` around I/O (`S3MultipartController.ETAG_LOCK`, any in core) with `ReentrantLock` (pinning on Java 21), and keep
   `server.tomcat.max-connections=2048`, `server.tomcat.accept-count=200` so FDs stay bounded.
2. Tighter timeouts: `server.tomcat.connection-timeout=60s` (idle between bytes), `server.tomcat.keep-alive-timeout=30s`,
   `server.tomcat.max-swallow-size=1MB`. Paused video players then reconnect with `Range` (the S3 contract) instead of pinning a thread 10 min.
3. Minimum-rate guard (the real fix). A wrapper stream applied in `SigV4Filter.VerifiedBodyRequest` and in `S3Support.openBody`:
```java
final class MinRateInputStream extends FilterInputStream {
    private final long graceNanos = 30_000_000_000L; private final long minBytesPerSec = 2_048;
    private final long start = System.nanoTime(); private long total;
    @Override public int read(byte[] b, int o, int l) throws IOException {
        int n = super.read(b, o, l);
        if (n > 0) total += n;
        long el = System.nanoTime() - start;
        if (el > graceNanos && total * 1_000_000_000L / el < minBytesPerSec)
            throw new SlowBodyException();          // -> 408 RequestTimeout, connection closed
        return n;
    }
}
```
   (also override `read()`; the check only triggers when a read returns, so combine with the 60 s socket timeout for fully idle clients).
4. Per-access-key in-flight limiter after authentication in `SigV4Filter` (Semaphore per access key id, e.g. 64 concurrent body-carrying requests,
   `503 SlowDown` + `Retry-After` when exhausted; release in `finally`). It is the only layer that stops one valid key from consuming the whole pool.
5. Slow READERS (GET) hold a worker in `out.write` until the 60 s write timeout; same limiter applies (count GETs separately, higher limit).
6. Operationally: nginx `client_body_timeout`, `limit_conn` per IP (already in doc 08).

### A7 (H/M) CompleteMultipartUpload is not idempotent and not concurrency-safe (doc 08)
`S3MultipartController.java:491-496` deletes the upload dir right after commit, so a client retry (SDKs retry Complete after a lost response;
Complete can run for minutes) gets `NoSuchUpload` although the object exists. Also two concurrent Completes of the same upload both stage and
commit (no per-upload lock), Abort or the 7-day cleanup (l.710-733) can delete files under a running Complete (-> NoSuchFileException -> 500),
and UploadPart can replace `part-N` after Complete has validated the ETag.
Fix (filesystem interim): per-upload state file `state.json` {OPEN|COMPLETING|COMPLETED, completedEtag, objectManifestId, completedAt} guarded by a
per-uploadId lock map (`ConcurrentHashMap<String, ReentrantLock>`); Complete sets COMPLETING (second caller gets 409 OperationAborted / waits),
on success writes COMPLETED and KEEPS `meta`+`state` for 24 h (parts are deleted). A repeat Complete with COMPLETED state and the same part list
returns the stored 200 body. UploadPart/Abort on COMPLETING/COMPLETED -> `NoSuchUpload`. See E2 for the metastore design.

### A8 (M) UploadPart: part file, ETag file and checksum file are updated independently -> mismatched ETag
`S3MultipartController.java:196-209`: part file moved first, then `etags.properties` and `checksums.properties` rewritten separately under a
JVM-global static lock (`ETAG_LOCK`, l.217). Two concurrent uploads of the SAME partNumber (common on SDK retry after a timeout) can leave
file from A + ETag from B, so Complete streams bytes whose MD5 differs from the ETag it reports. Also: no fsync of part/props (a crash can leave the
ETag recorded for a short or zero-length part, silently producing a corrupt object whose ETag is a lie), and each part rewrites the whole
properties file (O(parts^2) = ~50 M entries written for 10 000 parts) under ONE lock shared by all uploads of all buckets.
Fix: name part files by content id (`part-00001-<etagHex>`), record `{partNumber -> file, etag, size, checksum}` in one per-upload record updated
under the per-upload lock, fsync file + record, delete the superseded file afterwards. Or go to E2.

### A9 (M) CompleteMultipartUpload: part-order check is dead, part-count/size limits missing
- `parseCompleteXml` sorts the list (`:853 result.sort`) before `completeMultipartUpload` verifies ascending order (`:359-364`), so `InvalidPartOrder` can
  never fire for out-of-order parts (only duplicates are caught). Remove the sort.
- No `partNumber` upper bound in Complete (1..10000 is checked in UploadPart only), no max count of parts, `PartNumber<=0` is silently dropped (`:844`).
- ETag omitted by the client is accepted (`:392`); S3 requires it.
- No `EntityTooSmall` (known, doc 08) and no per-part max (5 GiB is enforced only via Content-Length of UploadPart).
- `Location` is hard-coded to `http://s3.amazonaws.com/...` (`:503`); build from the request (scheme/host) or omit.
- Eager open of ALL part files: `streams.add(Files.newInputStream(...))` at `:429` inside the validation loop defeats the "lazy" `LazySequenceInputStream`
  (its javadoc claims "Prevents holding thousands of file descriptors"): 10 000 parts = 10 000 FDs, and an `InvalidPart` thrown mid-loop LEAKS every
  stream already opened (never closed). Fix: pass `List<Path>` and open lazily in `LazySequenceInputStream`.

### A10 (M) UploadPartCopy range parsing throws wrong errors; no bounds
`S3MultipartController.java:289-292`: `Long.parseLong` on user input. Malformed -> `NumberFormatException` (an `IllegalArgumentException`) ->
`S3ExceptionHandler.handleIllegalArgument` (l.92-117) maps it to **404 NoSuchKey** with the NumberFormat message; missing `-` -> `ArrayIndexOutOfBounds` -> 500;
`end` beyond the object or `start>end` is unchecked and ends in an `IllegalArgumentException` from core -> again 404 NoSuchKey.
Same trap anywhere a `NumberFormatException` escapes: `listParts` (`max-parts` negative -> `limit(maxParts+1)` IAE, `Integer.MAX_VALUE+1` overflows, l.548),
`part-number-marker`, `max-uploads`, `S3ObjectController.checkPartNumber`. Fix: shared `RangeSpec.parseCopyRange(header, total)` -> `InvalidRange`/`InvalidArgument`,
validate integers in one `S3Params` helper, and never classify errors by exception message (A12).

### A11 (M) Silent no-ops: conditional writes and ACL parse errors
- `PutObject`/`CopyObject` ignore `If-None-Match: *`, `If-Match` (doc 08 "not implemented") and answer 200. Clients that use them as locks overwrite data
  silently. Return `501 NotImplemented` when these headers are present on PUT/Copy/Complete (like the sub-resource policy in `S3Support.requireOnlyQueryParams`),
  or implement them inside the commit transaction.
- `AccessControlService.applyBucketAcl/applyObjectAcl` (l.47-119) wrap everything in `catch (Exception) { log.warn }`: a malformed ACL body, an unknown canned ACL
  (`normalizeCannedAcl:246-257` maps ANY unknown value to "private") returns 200 OK without applying anything. Return `MalformedACLError` / `InvalidArgument`.
  Also `new String(body)` (l.70,109) uses the platform charset; use UTF-8. `parseAclFromXml:289` accepts any URI that merely contains `global/AllUsers`;
  compare with `equals("http://acs.amazonaws.com/groups/global/AllUsers")`.
- `CopyObject`: `x-amz-metadata-directive` compared case-sensitively at `S3ObjectController:416` and case-insensitively at `:424` (lowercase `replace` on a self-copy
  is rejected although it is a REPLACE); `x-amz-copy-source-if-*` headers silently ignored.
- Tagging PUT is accepted and discarded (`S3AclController:331-349`), GET returns an empty set: data loss presented as success; return 501 on PUT or store the tags.

### A12 (M) Error mapping by message substring; message leaks
`S3ExceptionHandler.java:92-117` classifies any `IllegalArgumentException` by `msg.contains("Bucket"|"Pool"|"not found"|"already exists")`, default **NoSuchKey 404**, and
echoes `msg` (internal core text, possibly paths/ids) to the client. `:179-199` does the same for `IllegalStateException` (`"still has"`, `"not empty"`),
duplicated in `S3BucketController.java:93-101`. No stack trace or file path leaks through `handleGeneral` (generic text, requestId, ERROR log with stack): good.
Fix: typed core exceptions (`BucketNotFoundException`, `BucketAlreadyExistsException`, `BucketNotEmptyException`) mapped 1:1; unknown `IllegalArgumentException` -> 400
InvalidArgument with a FIXED message, never 404, never the raw message. Remove the "legacy" handler once core is typed.
Related low items: `handleClientAbort` javadoc "Catch-all for unexpected errors" is stranded above it (l.201-204); `SocketTimeoutException` from slow bodies falls to
`handleGeneral` and logs an ERROR with a stack per slow client (log flood) - map to 408 at INFO.

### A13 (M) SigV4 canonicalization and verification gaps
a. Multi-valued headers: `SigV4Filter:186` and `:306` use `request.getHeader(h)` (first value). AWS joins repeated header lines with ",". Use
   `String.join(",", Collections.list(request.getHeaders(h)))` (each trimmed).
b. `SigV4Utils.canonicalizeQuery:90-91` and `SigV4Filter.parseQueryParams:372-373`, `S3Support.requireOnlyQueryParams:92` use `URLDecoder.decode`, which throws
   `IllegalArgumentException` on a lone `%`/bad hex. In the filter this is OUTSIDE the MVC advice: `?X-Amz-Signature=a&b=%` from an ANONYMOUS client (presign branch runs
   `parseQueryParams` before any key lookup) and `?x=%` with a valid (public) access-key id reach `canonicalizeQuery` -> unhandled -> container 500 + stack in the log.
   Use `S3Support.percentDecode` plus an explicit '+' -> ' ' step for query strings and treat malformed input as `400 InvalidArgument`/`AuthorizationQueryParametersError`.
   Note `percentDecode` replaces invalid UTF-8 with U+FFFD (distinct keys `%FF`/`%FE` alias) - decode with `CharsetDecoder(REPORT)` and reject.
c. Presigned detection `queryString.contains("X-Amz-Signature")` (l.107) is a substring test on the raw string: a signed header request whose `prefix=` contains that text is
   sent down the presign path (400). Detect by parsed parameter NAME.
d. No requirement that sensitive headers be signed: `host`, `x-amz-content-sha256` (when present) and every `x-amz-*` header must appear in SignedHeaders (AWS rejects
   otherwise). Today `x-amz-acl`, `x-amz-copy-source`, `x-amz-meta-*`, `x-amz-checksum-*` can be injected/altered by an on-path proxy without breaking the signature; an
   unsigned `x-amz-content-sha256` lets a MITM swap body+hash. Add the check after `parseAuthHeader`.
e. `timestamp.startsWith(dateStr)` (l.177, 295) accepts an empty/short date; use `timestamp.substring(0,8).equals(dateStr)` with a length check.
f. Credential region is accepted as sent; the injected `region` field (l.59,73) is never read -> dead code and no region enforcement (doc 02 claims scope checks). Compare to
   `sectoriadb.s3.region` or drop the property.
g. `SignedHeaders` empty or containing unknown names produce a ":" canonical line instead of a clean 400 (l.183-192, 305); reject empty.
h. Presign: `X-Amz-Date`/`X-Amz-Expires` parse failures return 400 InvalidArgument (fine); unknown/duplicated params last-wins in `parseQueryParams` but are ALL in the canonical
   query - no bypass, just confusing; fine.
i. `Sha256VerifyingInputStream.verifyAtEof:514-521` sets `finished=true` BEFORE throwing, so a second `read()` after the mismatch returns -1 as if the stream ended cleanly.
   Remember the failure and rethrow. (Callers today abort, so L.)
j. `credentialService.listAll().isEmpty()` on EVERY request (l.88): cache or expose `hasAnyKey()`.

### A14 (M) response-* overrides and content sniffing on public objects
`S3ObjectController.getObject:140-145,181,189-193`: `response-content-type`, `response-content-disposition`, ... are honoured for ANONYMOUS reads of public objects. AWS
rejects them for unsigned requests (400 InvalidRequest). Anyone can turn a public object into `text/html` on the server origin (XSS on the API origin) or force
downloads. Fix: reject any `response-*` param when the request has no verified identity (set a request attribute in SigV4Filter on success; check in controller).
Also consider `X-Content-Type-Options: nosniff` on GET/HEAD.

### A15 (M) GET/HEAD `?partNumber` (doc 08)
`S3ObjectController.checkPartNumber:278-298` infers part count by parsing the ETag suffix `-N` (domain knowledge leaked into the controller) and answers 501 for multipart objects.
Store part boundaries in the manifest at Complete: `ManifestEntity.partSizes: long[]` (or `List<PartInfo{size, etag, checksum}>`), then
`GET ?partNumber=N` = range read of [sum(sizes[<N]), +sizes[N-1]) with `206`, `Content-Range`, `x-amz-mp-parts-count`; HEAD same; `partNumber=1` of a single-part
object keeps the current behaviour. The multipart controller already has all sizes (`Files.size(part)`) at Complete time (l.572 shows the data exists). Needs a
core manifest field + metastore codec bump (doc 07).

### A16 (L/M) Conditional GET/HEAD semantics
`S3ObjectController:159-167`: `ifNoneMatch.equals(etag)` is an exact string compare: no `*`, no comma lists, no weak `W/`, quotes mandatory; `If-Modified-Since` is evaluated
even when `If-None-Match` is present (RFC 7232 says ignore it); `If-Match`/`If-Unmodified-Since` (412) should be evaluated BEFORE 304 checks. HEAD (l.302-356) supports only
If-None-Match/If-Match (no -Since, no 304 `ETag`/`Last-Modified` headers, no `Range`). GET 304 has no `Last-Modified`. Extract `ConditionalRequest.evaluate(request, entity)` used by GET, HEAD and CopyObject.
`parseRange:244-266`: `bytes=5` (no dash) is treated as `5-` (should be ignored as malformed); `If-Range` unsupported.

### A17 (L/M) Multipart bookkeeping gaps
- `validateUploadId:754-783` checks the bucket but NOT the object key of the URL: `PUT /b/anything?uploadId=X&partNumber=1` and `POST /b/other?uploadId=X` act on upload X
  (S3: NoSuchUpload). Compare `meta.key` with `extractKey`.
- `listParts:575` reports `LastModified = now` (use part file mtime); `max-parts`/`max-uploads` not validated/capped; `listMultipartUploads:600-682` scans ALL upload dirs of ALL
  buckets for every call (O(total uploads) file reads), no `upload-id-marker`, ignores `delimiter`, does not check the bucket exists (empty list instead of NoSuchBucket),
  NPE/NumberFormat on a corrupt `meta.properties` (l.636,643).
- DeleteBucket does not abort uploads; the upload dirs of a deleted bucket remain and become visible again if the bucket name is recreated.
- CreateMultipartUpload ignores `x-amz-acl`/grants (object stays private - safe but a silent gap) and has no cap on open uploads per bucket/key or on total part bytes
  (inode/disk DoS by a key holder). Add `sectoriadb.multipart.max-uploads` and a disk-free guard.
- `MultipartCleanup:710-733` expires by `initiatedAt` (7 days) not last activity (kills legitimate long uploads; AWS has no default expiry), a corrupt `initiatedAt` throws
  `NumberFormatException` out of the `@Scheduled` method aborting the sweep of all other uploads, and it deletes dirs while a Complete may be reading them (A7).
- Parts are not fsynced and live in `<dataDir>/.multipart`, outside the metastore, GC, `verify`, metrics and shell (E2).

### A18 (L/M) Encoded slash/backslash in keys (verify)
Tomcat answers 400 for `%2F` (ALLOW_ENCODED_SLASH=false) and `%5C` (ALLOW_BACKSLASH=false) in the path. Valid S3 keys can contain a backslash, and `%2F` is equivalent to `/` for
S3. If required for compatibility set the system properties `org.apache.tomcat.util.buf.UDecoder.ALLOW_ENCODED_SLASH=true` and
`org.apache.catalina.connector.CoyoteAdapter.ALLOW_BACKSLASH=true` in `Application.main` (before `SpringApplication.run`) and re-test signing for those keys. Probe with `s3cmd`/boto3 `put_object(Key='a\\b')`.

### A19 (L) XML output hygiene
- `S3Support.xmlEscape:131-135` keeps XML-1.0-invalid control characters (key `a%01b` is legal in S3): listing XML built by string concatenation (`listObjectVersions`,
  `listParts`, `listMultipartUploads`, DeleteResult, CopyObjectResult, ACL) becomes non-well-formed and breaks the listing for every client that does not use `encoding-type=url`
  (a writer can poison a bucket listing). Emit invalid chars as numeric references or strip them. Jackson/Woodstox in `S3Error` for a missing key with such a char
  (`Resource` field) may throw while writing the error (verify with `GET /b/%01` on a missing key).
- `SigV4Filter.sendError:503-521` hand-builds XML with its own `escapeXml` (no quote escaping, no control-char handling) and reflects client text (`"Cannot parse timestamp: " + timestamp`,
  `"Unsupported algorithm: " + algorithm`); pass through `S3Error` (Jackson) or `S3Support.xmlEscape`.
- `S3AclController.getBucketLocation:213` concatenates the configured region unescaped.

### A20 (L) Application: secrets in logs
`Application.java:90` `log.warn("Failed to parse credential from env: {}", cred, e)` logs the whole `ak:sk:desc` string including the SECRET KEY (and a stack trace). Log only the index/access key id.
`new ObjectMapper()` bean (l.110-115) replaces Spring Boot's auto-configured mapper (loses Boot defaults such as `FAIL_ON_UNKNOWN_PROPERTIES=false`, jdk8/parameter-names modules); prefer a
`Jackson2ObjectMapperBuilderCustomizer`. `S3AclController.java:164` creates yet another `new ObjectMapper()` per PutBucketPolicy and `AccessControlService:40` `new`s the evaluator instead of injecting a bean.

### A21 (L/M) Policy evaluation cost
`BucketPolicyEvaluator.evaluate:39-47` parses the policy JSON on every anonymous request, and `AccessControlService:207-211` evaluates the same policy twice for a bucket list. With no size
limit on PutBucketPolicy (A3) a large policy is a CPU amplifier for ANONYMOUS callers. Parse once at PutBucketPolicy (reject unparseable/invalid statements there, as AWS does:
`MalformedPolicy`) and cache the compiled `ParsedPolicy` in `PoolEntity`/a `ConcurrentHashMap<bucket, ParsedPolicy>` invalidated on set/delete. The warn-log for unparseable policy (l.45)
is attacker-triggerable per request (log flood) once cached validation exists it disappears. `glob` is O(n*m) worst case: fine with the 20 KiB cap. Documented design limit: policies
(including Deny) do not apply to signed requests (doc 02).

### A22 (info) Verified-OK areas
Path traversal: `uploadId` is a strict lowercase UUID regex (S3MultipartController:751-757) and part names are `%05d` of a range-checked int; object keys never reach the file system
(manifest/blob ids are generated). XXE: all three DOM parsers use `XmlSupport.newSecureDocumentBuilder` (no DOCTYPE). Signature/chunk-signature/trailer comparisons are constant time.
Error responses carry no stack traces or paths (`handleGeneral`, `S3ErrorController`, `S3MvcErrors`). SigV4 query sorting/encoding by code point, empty values (`delete` -> `delete=`),
repeated params (values sorted per key), `+`->space and unreserved set follow the spec (`SigV4Utils:82-106,193-215`; covered by SigV4UtilsTest, I would add repeated-key and `%2B` vs `+` cases).

## B. Dead code, duplication, needlessly public API
---------------------------------------------------------------------------------------------------
Dead / unused:
- `S3ObjectController.poolService` (field + ctor param, l.57,62,64): never used. `SigV4Filter.region` (l.59,73): never read.
- Imports: `S3BucketController` and `S3MultipartController` import `javax.xml.parsers.DocumentBuilderFactory` (unused, all parsing goes through XmlSupport); `S3Support` imports `java.util.UUID` (unused).
- `S3Support.httpDate` (l.35): zero callers (controller keeps its own `HTTP_DATE`, S3ObjectController:53-55, identical formatter).
- `S3Exception.accessDenied` (l.383): zero callers. `AwsChunkedInputStream` 1- and 2-arg constructors (l.276-282): only the 3-arg one is called.

## E. Architecture
---------------------------------------------------------------------------------------------------
### E1 Controllers contain storage orchestration
- `S3ObjectController.putObject:98-122` and `copyObject:429-474` and `S3MultipartController.completeMultipartUpload:459-489` all re-implement the same protocol:
  `stageStream -> set attributes -> try { applyAcl; commitObject } finally { abortStaged }`. The GC upload-hold release is a contract the controller must remember; forgetting the `finally`
  leaks a hold (blocks the sweep until `upload-ticket-ttl`). Move into core: `ObjectService.put(PutCommand)` / `copy(CopyCommand)` / `completeMultipart(CompleteCommand)`, with the try/finally inside.
- CopyObject spools the whole source to a temp file (`:429-433`), then re-reads it into `stageStream` (3x I/O: read blobs, write temp, read temp, write blobs; 5 GiB of temp space). Because chunks are
  content-addressed with refcounts (docs 03, 09), a same-pool copy can be a metadata-only operation: `fileService.copyObject(srcManifest, destKey, attrs)` building a new manifest that references the
  same chunk keys (refcount +1 inside the commit transaction); cross-pool copy can pipe `streamToOutput` through a `PipedInputStream` instead of a temp file.
- Controllers call `ManifestRepository`/`PoolService` directly (S3BucketController.listObjects, S3AclController, S3MultipartController:276) instead of a service: authorisation/ACL, bucket checks and
  metrics cannot be applied uniformly. Introduce `ObjectFacade`/`BucketFacade` in the server module (thin) or push into core services.
- Domain knowledge in the web layer: multipart part count derived from the ETag string (`checkPartNumber`), ACL canned-string handling (`"public-read".equals(...)` x6 across AccessControlService/S3Controllers) -> `Acl` enum with `fromHeader/fromXml/grantsAnonymousRead()`.
- Access control is scattered: anonymous decision in `AccessControlService.isAnonymousAllowed` called from the AUTH filter by re-parsing the URI (own `extractBucketFromUri`/`extractKeyFromUri`, duplicating `S3Support.extractKey` and the Spring mapping),
  while signed requests are never policy-checked. Risk of the two parsers diverging (today they fail closed because bucket names with `%` do not exist). Resolve bucket/key/operation ONCE (a `S3Request` value object built by the filter and
  put in a request attribute, as `OperationClassifier` in `observability` already does for metrics) and let both the filter and the controllers use it.

### E2 Multipart state: filesystem vs metastore (recommendation: move to the metastore)
Current: `<dataDir>/.multipart/<uuid>/{meta.properties, etags.properties, checksums.properties, part-NNNNN}`.
Problems: not transactional with the metastore (crash between part file and ETag; bucket delete does not cascade; Complete = copy parts -> temp file -> blobs = 3x disk and 3x I/O, A5/E1); not durable (no fsync) despite
`sectoriadb.fsync=true`; invisible to GC/`verify`/metrics/shell/backup (orphaned parts on crash are only found by a 7-day mtime sweep keyed on `initiatedAt`); global static lock; O(N) listing; no idempotency record; parts cannot provide boundaries for `?partNumber`.
Proposal (fits docs 06/07/09/10):
- Trees `mpu_uploads: (bucket, key, uploadId) -> {initiated, attrs, checksumAlg/type, state, completedManifestId, completedEtag}` and `mpu_parts: (uploadId, partNumber) -> {etag, size, md5, checksum, partManifestId}`.
  `ListMultipartUploads` becomes a range scan on `(bucket, prefix..)`; `ListParts` a range scan on `(uploadId, > marker)`.
- UploadPart stores the part through the SAME path as PutObject (`stageStream`) as a hidden "part manifest" (with upload hold), so parts are chunk-deduplicated, CRC-checked (doc 03), refcounted and visible to GC.
- Complete = ONE metastore transaction: validate parts, build the final manifest as the ordered list of part chunk lists (manifest v3 `parts[]` with size/etag/checksum per part: gives `GET ?partNumber=N`, correct `x-amz-mp-parts-count`, and zero-copy completion
  with no temp file), retire the part manifests, mark the upload COMPLETED with the result (idempotent retry returns it; GC removes the record after 24 h).
- Abort/expiry = delete rows + parts go to `chunk_gc` (grace period protects in-flight readers); bucket delete cascades inside its transaction; metrics `sectoriadb_mpu_open`, `..._bytes`.
- Chunk alignment: parts are rarely multiples of the 16 KiB chunk size, so the final manifest keeps per-part chunk lists (reads iterate parts; range reads map offsets over `partSizes`), rather than concatenating byte streams.
Interim (if time is short): keep the filesystem but implement `MultipartUploadStore` behind an interface with a per-upload lock, one state file per upload written atomically + fsynced, a COMPLETED tombstone (A7), lazy part opening (A9), and a startup scan reconciling orphans.

### E3 Package structure (server module)
Observed cycles: `s3` -> `s3.auth` (S3Support.openBody imports AwsChunkedInputStream) and `s3.auth` -> `s3` (SigV4Utils/SigV4Filter import S3Support), `s3.access` -> `s3` (S3Support, XmlSupport). `observability` imports `s3.*` and is imported by `s3` (S3ExceptionHandler, S3ObjectController...). All shared helpers sit in the `s3` root next to controllers.
Proposed layout:
```
org.example.sectoriadb
  Application
  s3.http        S3Headers, S3Paths (percentDecode, extractKey), S3RequestId, RequestBodies (limited/min-rate/openBody), RangeSpec, ConditionalRequest, CopySource, ResponseHeadersFilter   <- leaf package
  s3.xml         DTO records (responses), XmlSupport, parsers (DeleteRequestParser, CompleteMultipartParser, AclXmlParser), XmlWriter/escape
  s3.error       S3Exception, S3ErrorCode, S3ExceptionHandler, S3ErrorController, S3MvcErrors, ResponseAbortedException
  s3.auth        SigV4Filter, SigV4Verifier, SigV4Utils (pkg-private), AwsChunkedInputStream, Sha256VerifyingInputStream, VerifiedBodyRequest, ChunkSigningContext, AuthFailure, AuthException, PayloadVerificationException
  s3.access      AccessControlService, Acl, BucketPolicyEvaluator, ParsedPolicy (+cache), AnonymousAccessDecider
  s3.api         S3ServiceController (ListBuckets), S3BucketController, S3BucketConfigController (acl/policy/location/stubs), S3ObjectController, S3ObjectSubresourceController (acl/tagging)
  s3.multipart   MultipartController, MultipartUploadStore (+ MetaStore impl later), MultipartUpload/PartRecord, CompleteMultipartService, LazySequenceInputStream, MultipartCleanup
```
Dependency rule: `http` and `xml` and `error` depend on nothing in `s3`; `auth` and `access` depend on `http`/`xml`; `api`/`multipart` depend on all of them and on core; nobody depends on `api`.
Mechanical steps: (1) extract `s3.http` from S3Support, (2) move `s3.auth` helpers, (3) split controllers, (4) response-header filter.
