## Цель и рамки

- **Цель:** одноузловая версия, которой можно доверить данные (релиз 1.0), затем по шагам — отказоустойчивость. Распределённость — последней.
- **Вне рамок:** SQL и документная модель. Отдельное решение после 1.0.
- **Правило этапов:** одна ветка на этап, номер ветки продолжает нумерацию; следующий этап не начинается, пока не выполнен критерий готовности предыдущего.

### Этап 0. Закрыть критический разбор (`20-critical-fixes`)

Порядок из [critical-review](reports/critical-review.md#порядок-исправлений-в-20-critical-fixes):
P1 кэш страниц метахранилища → P4 журнал операций → P2 мёртвые байты `.sob` → S3 ключ, адрес и `requestId` в журнале → S2 запрет по умолчанию для ключа без политики → S1 шифрование секретов.

- **(дополнение)** Мелкие пункты разбора, которые закрываются здесь же: S5 — неподдерживаемое условие политики даёт отказ, а не игнорируется; S6 — `WARN` при старте без TLS и доверенного прокси; S7 — временная блокировка адреса после серии неудачных подписей; P7 — проверка `credentials.json` не чаще раза в секунду.
- Метрики этапа: попадания в кэш страниц, байты чтения метахранилища, мёртвые байты `.sob`.

### Этап 1. Платформа (`21-platform`)

- Перейти на Spring Boot 4.x и Java 25 (у 3.3.x открытая поддержка закончилась в июне 2025); вместе с ними — Spring Shell и Tomcat, убрать ручную фиксацию `tomcat.version`.
- Проверка зависимостей на известные уязвимости (CVE) — локальной командой Maven перед каждым релизом; CI/CD не используется (решение владельца 2026-10-29).
- **(дополнение)** Переход на Spring Boot 4 тянет Jackson 3 (другие пакеты и API): затронуты `credentials.json`, журнал операций и кодек манифеста. Нужен тест, что файлы, записанные старой версией, читаются новой.

### Этап 2. Формат на диске и обновления (`22-disk-format`)

- Номер версии формата в заголовках `sectoria.db`, `blob_*.raw`, `small_*.sob` и в кодеках записей; отказ старта на неизвестной версии.
- Мигратор N−1 → N и тест на снимке данных предыдущей версии.
- **(дополнение)** Строки очереди надгробий уже имеют два формата (с маркером `0x01` и без, этап 19) — это первый кандидат на явную версию кодека.

### Этап 3. Проверка на настоящем железе (`23-hardware-validation`)

- На локальной машине с диском 2 ТБ: загрузка 1 ТБ и заполнение диска на 70–90 %; soak 8 ч и 24 ч. Распределённый warp с отдельной машины-клиента — когда она появится; до тех пор клиент на той же машине, и это указывается в отчёте.
- `bench/compare/compare.sh` против SeaweedFS, Garage и Versity на том же железе.
- `bench/faults/run-all.sh` на физическом диске, включая снимки файловой системы и LUKS.
- S8: Jazzer по разборщикам запросов и чтению форматов на диске.
- **(дополнение)** P3 (три `fsync` на PUT, двойная запись тела через спул) решать по результатам этого этапа: на NVMe цена `fsync` другая, оптимизировать без замера на целевом железе рано.

### Этап 4. Версионирование бакета (`24-versioning`)

- `PutBucketVersioning`, `versionId` в существующих операциях, `ListObjectVersions`, delete-marker.
- Lifecycle: срок хранения нетекущих версий.
- **(дополнение)** Затрагивает модель надгробий: сейчас замещённая версия сразу удаляется из `manifests` (этап 19). При включённом версионировании она должна остаться текущей записью версии, а в очередь сборщика попадать только по lifecycle. Нужен отдельный ADR до начала этапа.

### Этап 5. Релиз 1.0 (`25-release-1.0`)

- Слияние в `main`, тег `v1.0.0`, образ в реестре с дайджестом; удалить ветки `wip/11-*`.
- `SECURITY.md` с порядком сообщения об уязвимостях, политика поддержки версий.
- Итоговое обновление README и документации (ранее планировалось отдельным этапом 21).
- Демо-стенд — после тега.

### Блок B: этапы 6–8

- **Этап 6, резервный узел.** Поток коммитов метахранилища и новых чанков на standby, чанки раньше ссылающегося коммита; метрика отставания; ручное переключение.
  **(дополнение)** У метахранилища нет журнала упреждающей записи: коммит — это новые страницы и смена мета-страницы. Отгружать можно страницы коммита (в soak в среднем 48 на коммит), это укладывается в модель копирования при записи, но формат потока нужно спроектировать.
- **Этап 7, кластер.** Транзакции метахранилища как записи журнала Raft на 3 узлах (Apache Ratis); узлы данных — текущий движок под внутренним RPC; HRW по узлам с доменами отказа, RF = 3; шлюз без состояния; scrub и ремонт; добавление и вывод узлов.
- **Этап 8, erasure coding.** Полосы k+m (например, 4+2) для крупных и холодных объектов, перевод из RF = 3 по возрасту или размеру.

## Проверки на каждом этапе

| Проверка | Чем | Когда |
|---|---|---|
| Сборка, тесты, стиль, документация | `mvn -B verify` | локально перед каждым коммитом |
| Совместимость S3 | `bench/compat/s3tests.sh`, `mint.sh` | каждый этап, сравнение с прошлым числом пройденных |
| Отказы | `bench/faults/run-all.sh` | каждый этап |
| Нагрузка | `bench/warp/matrix.sh`, затем `compare.sh` | каждый этап, одно железо |
| Дрейф | `bench/warp/soak.sh`: 45 мин на этап, 8 и 24 ч перед релизом | каждый этап / релиз |
| Фаззинг | Jazzer | ночной прогон с этапа 3 |
| Кластер | тесты в стиле Jepsen | этапы 6–7 |

Перед чтением цифр метрики сервера сверяются с отчётом warp (правило из [sandbox-results](reports/sandbox-results.md)).

## Риски

1. **Распределённость раньше времени** — ошибки движка смешаются с ошибками консенсуса. Снижение: критерии готовности, промежуточный этап 6.
2. **Дедупликация и `refcount` в кластере** — каждый PUT меняет счётчики сотен чанков через журнал Raft. Снижение (проверить замером): крупнее единица репликации, групповой коммит поверх Raft, шардирование метаданных по бакетам.
3. **Данные людей до совместимости формата** — до этапа 2 первое обновление уничтожит данные. Класть только то, что есть в другом месте.

## Открытые решения

| Решение | Варианты | К этапу |
|---|---|---|
| Совместимость формата | миграция при старте / команда `migrate` | 2 |
| Модель версий и надгробий | см. дополнение к этапу 4 | 4 |
| Резервный узел | своя отгрузка страниц / снимки ZFS/Btrfs с отправкой / сразу кластер | 6 |
| Консенсус метаданных | Apache Ratis / свой Raft | 7 |
| Единица репликации | чанк 16 КиБ / полоса чанков / блоб целиком | 7 |
| SQL и документный слой | отдельный проект / часть SectoriaDB / отказаться | после 5 |
