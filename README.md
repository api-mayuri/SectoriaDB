# SectoriaDB

S3-совместимое хранилище объектов на Java и Spring Boot. Работает с `aws cli`, SDK и веб-интерфейсами, которые
умеют разговаривать по S3 API. Данные лежат в собственных блоб-файлах: крупные объекты — в кукушкиных хэш-таблицах
(Cuckoo hash table), мелкие (меньше размера чанка) — в append-only файлах малых объектов; метаданные — во встроенном транзакционном хранилище (copy-on-write B+-дерево в одном файле `sectoria.db`), без внешней базы данных.

> Проект учебный и экспериментальный. Перед использованием для важных данных прочитайте раздел
> [Ограничения](#ограничения).

## Возможности

**Операции S3**

| Область | Что поддерживается |
|---|---|
| Бакеты | создание, удаление, `HeadBucket`, список бакетов |
| Объекты | `PutObject`, `GetObject` (в том числе `Range`), `HeadObject`, `DeleteObject`, `CopyObject` |
| Листинг | `ListObjectsV2` и `ListObjects` (v1) с префиксами и пагинацией |
| Multipart | создание, загрузка частей, завершение, отмена, список частей и загрузок, копирование части |
| Контрольные суммы | `x-amz-checksum-crc32` / `crc32c` / `crc64nvme` / `sha1` / `sha256` (заголовок или trailer `aws-chunked`), `Content-MD5`, `x-amz-checksum-algorithm`, составные суммы multipart (`COMPOSITE`/`FULL_OBJECT`), `x-amz-checksum-mode: ENABLED` на `HEAD`/`GET`; несовпадение — `BadDigest` и объект не сохраняется |
| Доступ | ACL бакетов и объектов, политики бакетов, публичное чтение, presigned-ссылки |
| Прочее | теги объектов, заглушки для `location`, `versioning`, `cors`, `lifecycle`, `encryption` |

**Аутентификация**

- AWS Signature Version 4: заголовок `Authorization` и presigned-ссылки.
- Несколько ключей доступа, их можно включать, выключать и удалять без перезапуска.
- Поддержка `aws-chunked` (потоковая подпись, которую использует AWS CLI), в том числе trailing-контрольных сумм.

**Эксплуатация**

- Загрузка и скачивание больших файлов потоком, без чтения всего файла в память.
- Автоматическое расширение блоба, когда он заполняется.
- Консоль администратора (Spring Shell) и журнал операций.
- Готовые `Dockerfile` и `docker-compose.yml`.

## Быстрый старт в Docker

Понадобятся Docker и Docker Compose.

1. Создайте файл с настройками:

   ```bash
   cp .env.example .env
   ```

2. Задайте ключ доступа. Откройте `.env` и укажите свои значения:

   ```dotenv
   SECTORIADB_S3_ACCESS_KEY=ваш_access_key
   SECTORIADB_S3_SECRET_KEY=ваш_секретный_ключ_не_короче_16_символов
   ```

3. Запустите сервис:

   ```bash
   docker compose up -d --build
   ```

После запуска:

| Адрес | Что это |
|---|---|
| `http://localhost:8080` | S3 API |
| `http://localhost:8081` | веб-интерфейс s3manager (сторонний, необязательный) |

Данные хранятся в Docker-томах `sectoriadb-meta` и `sectoriadb-data` и переживают пересборку и перезапуск контейнера.

После изменения кода пересобирайте образ той же командой: `docker compose up -d --build sectoriadb`.

## Ключи доступа

Ключами управляют командами консоли администратора. Они работают рядом с запущенным сервером:

```bash
X="docker compose exec -T sectoriadb java -jar /app/sectoriadb.jar"

$X mk-key --count 3 --desc "для бэкапов"   # создать ключи
$X keys                                    # список ключей
$X keys --secret                           # список вместе с секретами
$X disable-key --id ID                     # временно выключить
$X enable-key --id ID                      # включить обратно
$X rm-key --id ID1,ID2 --yes               # удалить
```

Один ключ — одному приложению или человеку. Тогда любой ключ можно отозвать, не ломая остальных.

Ключи также можно передать через переменные окружения (`SECTORIADB_S3_CREDENTIALS`, формат
`ACCESS:SECRET:описание`, несколько ключей через запятую). Подробности — в [`.env.example`](.env.example).

## Работа через AWS CLI

```bash
aws configure set aws_access_key_id     <AccessKeyId>
aws configure set aws_secret_access_key <SecretKey>
aws configure set default.region        us-east-1

aws s3 --endpoint-url http://localhost:8080 mb s3://my-bucket
aws s3 --endpoint-url http://localhost:8080 cp photo.jpg s3://my-bucket/
aws s3 --endpoint-url http://localhost:8080 ls s3://my-bucket
aws s3 --endpoint-url http://localhost:8080 cp s3://my-bucket/photo.jpg ./copy.jpg
aws s3 --endpoint-url http://localhost:8080 rm s3://my-bucket/photo.jpg
```

Временная ссылка на файл (по умолчанию объекты приватны):

```bash
aws s3 --endpoint-url http://localhost:8080 presign s3://my-bucket/photo.jpg --expires-in 3600
```

Как открыть файл или бакет всем, как работает публичный доступ и чего лучше не делать — в
[руководстве по S3](docs/S3-GUIDE.md).

## Запуск без Docker

Нужны JDK 21 и Maven.

```bash
mvn package -DskipTests

# С авторизацией (по умолчанию)
java -Dspring.shell.interactive.enabled=false -jar sectoriadb-server/target/SectoriaDB-1.0-SNAPSHOT.jar

# Для разработки, без авторизации
java -Dspring.shell.interactive.enabled=false -Dsectoriadb.s3.auth.enabled=false \
     -jar sectoriadb-server/target/SectoriaDB-1.0-SNAPSHOT.jar
```

Без флага `spring.shell.interactive.enabled=false` запускается интерактивная консоль администратора.
Список команд выводит `help`.

Основные команды консоли:

| Группа | Команды |
|---|---|
| Пулы | `mkpool`, `pools`, `pool`, `rmpool` |
| Блобы | `mkblob` (`--small` — файл малых объектов), `blobs` (чанки и доля размещения HRW по блобам), `blob`, `resize` (расширить один блоб без остановки записи), `scrub`, `rmblob` |
| Файлы | `store`, `ls`, `info`, `get`, `rm`, `verify`, `verify-all` |
| Ключи | `mk-key`, `keys`, `rm-key`, `enable-key`, `disable-key` |
| Доступ | `bucket-acl`, `object-acl`, `public-list` |
| Служебные | `status`, `config`, `logs`, `audit` |

## Настройка

Параметры задаются в `application.properties`, системными свойствами (`-Dsectoriadb.…`) или переменными окружения.

| Параметр | По умолчанию | Описание |
|---|---|---|
| `sectoriadb.meta-dir` | `./sectoriadb-meta` | каталог с метаданными (`sectoria.db`), ключами доступа и журналом операций |
| `sectoriadb.data-dir` | `./sectoriadb-data` | каталог с блоб-файлами |
| `sectoriadb.default-chunk-size` | `16384` | размер чанка, байт (16 КиБ; корзина из 4 слотов = 64 КиБ) |
| `sectoriadb.default-num-buckets` | `65536` | число корзин в каждой из двух таблиц нового блоба (по умолчанию 2·65536·4·16 КиБ = 8 ГиБ данных) |
| `sectoriadb.max-evictions` | `32` | максимум вытеснений при вставке в таблицу |
| `sectoriadb.small-object.max-file-bytes` | `1073741824` | размер файла малых объектов (1 ГиБ), после которого пул получает новый |
| `sectoriadb.small-object.checkpoint-interval-bytes` | `16777216` | как часто (в байтах дозаписи) сдвигается контрольная точка восстановления в заголовке `.sob` |
| `sectoriadb.pool.initial-blobs` | `1` | сколько кукушкиных блобов создаётся при первом чанковом объекте бакета (несколько блобов позволяют вставкам идти параллельно) |
| `sectoriadb.pool.max-blobs` | `16` | предел кукушкиных блобов в бакете (таблица каждого занимает в памяти около 9 МиБ) |
| `sectoriadb.pool.grow-threshold-percent` | `75` | при такой суммарной заполненности блобов бакета (и когда ни один блоб не принимает чанк) добавляется новый блоб |
| `sectoriadb.pool.location-cache-entries` | `65536` | LRU подсказок «чанк → блоб», экономит поиски в индексе при чтении (`0` выключает) |
| `sectoriadb.cache.max-resident-tables` | `64` | сколько таблиц кукушкиных блобов держать в памяти (≈9 МиБ каждая); остальные вытесняются по LRU, таблица в работе не закрывается; `sectoriadb.cache.max-resident-table-bytes` задаёт ещё и бюджет в байтах |
| `sectoriadb.cache.max-open-small-blobs` | `256` | сколько файлов малых объектов держать открытыми |
| `sectoriadb.metastore.recovery-backoff` | `1s` | пауза между попытками метахранилища восстановить запись после сбоя коммита (пока диск не работает, запись отвечает `503 SlowDown` / `507`, чтение продолжается) |
| `sectoriadb.auto-resize.enabled` | `true` | фоновая проверка роста пулов (добавляет блоб по порогу выше) |
| `sectoriadb.auto-resize.check-interval-ms` | `60000` | период этой проверки |
| `sectoriadb.gc.enabled` | `true` | фоновая сборка мусора: освобождает место удалённых и перезаписанных объектов, см. [Сборка мусора](#сборка-мусора) |
| `sectoriadb.gc.grace` | `15m` | период ожидания G: мусор моложе него не трогается (загрузка, нашедшая чанк в индексе, и читатель старой версии успевают закончить) |
| `sectoriadb.gc.interval`, `max-chunks-per-run`, `batch-size` | `1m`, `10000`, `16` | пауза между проходами, предел освобождаемых слотов за проход, чанков на одну эксклюзивную транзакцию |
| `sectoriadb.gc.sweep-interval` | `6h` | обход блобов в поиске копий оборванных загрузок |
| `sectoriadb.gc.small-compact-dead-percent` | `50` | компакция `small_*.sob`, когда мёртвые записи занимают столько процентов (и не меньше `small-compact-min-dead-bytes`, 1 МиБ) |
| `sectoriadb.s3.region` | `us-east-1` | регион для подписи запросов |
| `sectoriadb.s3.auth.enabled` | `true` | проверка подписи SigV4 |
| `server.port` | `8080` | порт HTTP |
| `management.server.port` | `9464` | порт метрик и health (`/actuator/prometheus`, `/actuator/health`), без подписи SigV4, см. [Мониторинг](#мониторинг) |
| `sectoriadb.observability.slow-request-ms` | `2000` | запросы дольше этого порога пишутся в лог на уровне WARN (`0` выключает) |

Переменные окружения для Docker (`HOST_PORT`, `JAVA_OPTS` и другие) описаны в [`.env.example`](.env.example).
Для больших файлов увеличьте память: `JAVA_OPTS=-Xmx1g`.

## Как это устроено

| Понятие S3 | Что это внутри SectoriaDB |
|---|---|
| Бакет | пул хранилища — отдельный каталог с блоб-файлами |
| Объект | манифест в `sectoria.db` со списком ключей чанков, типом содержимого и ETag |
| Данные | блобы: несколько `blob_*.raw` — большие разрежённые файлы с хэш-таблицей чанков (чанк кладётся в блоб по взвешенному rendezvous-хэшированию, место записывается в индекс чанков) и `small_*.sob` — журналы малых объектов |

Способ хранения выбирается по размеру объекта (поле `storageKind` манифеста):

| Размер | Вид | Где лежит |
|---|---|---|
| 0 байт | `EMPTY` | нигде: хватает манифеста |
| меньше `default-chunk-size` (16 КиБ) | `SMALL` | целиком одной записью в `small_*.sob` (append-only журнал, CRC32C на запись) |
| не меньше `default-chunk-size` | `CHUNKED` | чанки в кукушкиных таблицах блобов `blob_*.raw` пула |

Крупный файл режется на чанки фиксированного размера. Каждый чанк хэшируется (XXH64). Если такой чанк уже есть в бакете
(индекс чанков `chunks`), байты сравниваются и чанк не пишется второй раз (дедупликация по всему бакету, счётчик ссылок
`refcount`). Новый чанк кладётся в один из блобов бакета: блобы ранжируются взвешенным rendezvous-хэшированием (вес — свободное
место, у почти полного блоба вес падает), первый принявший получает чанк; когда бакет заполняется, добавляется новый блоб. Манифест
хранит только упорядоченный список ключей чанков: где чанк лежит, говорит индекс `(бакет, ключ чанка) → блоб, длина, CRC, счётчик ссылок`.
Благодаря этому `Range`-запросы читают лишь нужные чанки, а видео можно перематывать. Малый объект не режется и не участвует в кукушкином хэшировании:
манифест хранит лишь «где лежит» (`smallBlobId`, `smallOffset`, `smallLength`, `smallCrc32c`). Подробности:
[`docs/architecture/04-small-objects.md`](docs/architecture/04-small-objects.md).

Раскладка на диске:

```
sectoriadb-meta/
  sectoria.db        пулы, блобы, манифесты, индексы (бакет, ключ) → манифест, индекс чанков (chunks, chunks_by_blob),
                     очереди для сборки мусора (deleted_manifests, chunk_gc, chunk_orphans)
  credentials.json   ключи доступа
  oplogs.jsonl       журнал операций
sectoriadb-data/<бакет>/   несколько blob_*.raw (кукушкины таблицы чанков) и small_*.sob (журналы малых объектов)
```

Загрузка объекта — одна транзакция метаданных (ссылки на чанки, новый манифест, переключение указателя, освобождение ссылок
старой версии и её постановка в очередь), листинг — диапазонный проход по индексу. Подробности: [`docs/architecture/07-metastore-integration.md`](docs/architecture/07-metastore-integration.md),
несколько блобов, HRW и индекс чанков: [`docs/architecture/09-multi-blob-pool.md`](docs/architecture/09-multi-blob-pool.md).

Проект состоит из двух Maven-модулей:

| Модуль | Что внутри |
|---|---|
| `sectoriadb-core` | движок хранилища: кукушкина хэш-таблица, чанкинг, блоб-файлы, транзакционное хранилище метаданных и репозитории поверх него |
| `sectoriadb-server` | Spring Boot приложение: S3 API, проверка подписи SigV4, консоль администратора, планировщик |

Пакеты (`org.example.sectoriadb`):

| Модуль | Пакет | Назначение |
|---|---|---|
| core | `model` | сущности и значения: манифесты, пулы, блобы, ключи доступа, журнал операций |
| core | `metastore` | встроенное транзакционное хранилище: B+-деревья, снимки, транзакции |
| core | `repository`, `repository.metastore` | репозитории пулов, блобов и манифестов поверх хранилища, индексы, листинг |
| core | `service`, `service.impl`, `service.gc` | бизнес-логика, запись и чтение чанков, кукушкина таблица, файлы малых объектов, сборка мусора |
| core | `format` | форматы файлов на диске: блоб-таблица и файл малых объектов |
| core | `checksum` | алгоритмы S3-контрольных сумм (CRC32/CRC32C/CRC64NVME/SHA-1/SHA-256), однопроходный расчёт нескольких digest |
| core | `config`, `tools` | настройки `sectoriadb.*`, хэширование |
| server | `s3`, `s3.xml` | контроллеры S3 API, XML-ответы, обработка ошибок |
| server | `s3.auth` | проверка SigV4, декодирование `aws-chunked` |
| server | `s3.access` | ACL и политики доступа |
| server | `shell` | команды консоли администратора |
| server | `scheduler` | автоматический рост пулов, сборка мусора |

## Сборка мусора

Удаление и перезапись объекта сразу освобождают только ссылки на его чанки; место возвращает сборщик мусора
(`sectoriadb.gc.enabled=true`, по умолчанию включён): чанк без ссылок через период ожидания `sectoriadb.gc.grace` (15 минут)
освобождает свой слот в блобе (и слот снова доступен вставкам и весам размещения), надгробия манифестов удаляются, записи
малых объектов помечаются удалёнными, а `small_*.sob`, где мёртвых байтов больше половины, переписываются в новый файл.
Раз в 6 часов обход блобов находит копии чанков, оставшиеся от оборванных загрузок. Загрузка, которая успела найти чанк в
индексе, но не уложилась в период ожидания, получает `503` и повторяется клиентом. Команды консоли: `gc status`, `gc run [--pool P] [--grace 0s]`,
`gc sweep --pool P`, `gc compact --pool P`. Подробности: [`docs/architecture/10-gc-and-resize.md`](docs/architecture/10-gc-and-resize.md).

## Целостность данных

Объект проверяется на каждом участке пути; подробности и поведение при несовпадениях —
[`docs/architecture/05-object-checksums.md`](docs/architecture/05-object-checksums.md).

| Слой | Что проверяется | При несовпадении |
|---|---|---|
| Транспорт (SigV4) | `x-amz-content-sha256`, подписи фрагментов и trailer `aws-chunked` | `400 XAmzContentSHA256Mismatch` / `403 SignatureDoesNotMatch`, объект не сохраняется |
| S3-суммы загрузки | `x-amz-checksum-*` (заголовок или trailer), `Content-MD5` | `400 BadDigest`, объект не сохраняется (до записи в блоб и манифест) |
| CRC32C чанка / записи | каждое чтение чанка кукушки или записи `.sob`, в том числе `Range` | ошибка чтения (`500`, либо обрыв ответа, если заголовки уже отправлены) |
| CRC32C всего объекта | хранится в манифесте всегда, сверяется на каждом полном `GET`, `CopyObject`, `restore` | `GET` обрывается (соединение закрывается, последний чанк не отдаётся), в логе `ERROR`; копирование — `500` без фиксации |
| Консоль | `verify --id ID`, `verify-all [--pool NAME]` — полный обход со строкой `RESULT: OK` / `RESULT: FAILED` | |

`Range`-запросы опираются только на CRC32C чанков/записей. Контрольную сумму можно получить обратно:
`aws s3api head-object --bucket B --key K --checksum-mode ENABLED`. Для загрузки с проверкой:
`aws s3 cp file s3://B/K --checksum-algorithm SHA256` (CLI сам считает сумму).

## Мониторинг

Метрики в формате Prometheus отдаются на **отдельном порту** `9464` (свойство `management.server.port`), а не на S3-порту:

```bash
curl -s localhost:9464/actuator/prometheus | grep ^sectoriadb_s3_requests_seconds_count
curl -s localhost:9464/actuator/health
```

* Доступны только `health` и `prometheus`. Порт не защищён подписью SigV4, поэтому закройте его сетевыми правилами или
  привяжите к внутреннему интерфейсу (`management.server.address=127.0.0.1`). `docker-compose.yml` публикует его только
  на `127.0.0.1` хоста. Через порт S3 `/actuator/*` недоступен (`403`/`404`).
* Для каждой S3-операции (`PutObject`, `GetObject`, `ListObjectsV2`, `UploadPart`, ...) измеряются rate, ошибки (по классу
  статуса и по коду S3) и задержка (гистограмма `sectoriadb_s3_requests_seconds`); отдельно считаются отказы
  аутентификации по причинам, `fsync`, чтение и запись диска, блокировки метахранилища, заполнение кукушки,
  малые объекты, ёмкость и свободное место диска, JVM, Tomcat. Все метки низкокардинальные: имён бакетов и ключей
  в метриках нет.
* Каждый ответ получает `x-amz-request-id` и `x-amz-id-2`; идентификатор и операция попадают в лог (MDC), запросы дольше
  `sectoriadb.observability.slow-request-ms` пишутся предупреждением (без ключей).
* Перцентили считает Prometheus: `histogram_quantile(0.99, sum by (operation, le) (rate(sectoriadb_s3_requests_seconds_bucket[5m])))`.

Полный каталог метрик, границы гистограмм, правила кардинальности и примеры PromQL:
[docs/architecture/08-observability-bench.md](docs/architecture/08-observability-bench.md).

## Безопасность

- **Не публикуйте `.env`.** В нём лежат реальные ключи. Файл исключён из git; в репозиторий входит только `.env.example`.
- **Не отключайте авторизацию на открытом сервере.** Параметр `sectoriadb.s3.auth.enabled=false` предназначен
  только для разработки.
- **Нет ключей — нет доступа.** Если авторизация включена, но ни одного ключа ещё нет, сервер отвечает `403` на все
  запросы. Создайте ключ командой оболочки `mk-key` или задайте `SECTORIADB_S3_ACCESS_KEY` и
  `SECTORIADB_S3_SECRET_KEY`. Старое поведение («открытый режим настройки») включается явно:
  `sectoriadb.s3.auth.allow-open-setup=true` (`SECTORIADB_S3_AUTH_ALLOW_OPEN_SETUP=true`); не оставляйте его на
  сервере, доступном из сети.
- **Целостность загрузки.** Хэш тела (`x-amz-content-sha256`) и подписи aws-chunked-фрагментов проверяются; при
  несовпадении объект не сохраняется (`XAmzContentSHA256Mismatch`, 400). `UNSIGNED-PAYLOAD` по умолчанию разрешён
  (так делают AWS SDK по HTTPS); чтобы требовать подписанное тело, задайте
  `sectoriadb.s3.auth.allow-unsigned-payload=false`. Подробности: `docs/architecture/02-security.md`.
- **Политики бакета.** Явный `Deny` сильнее любого `Allow` и ACL. Условия (`Condition`) не вычисляются: `Allow` с
  условием не действует, `Deny` с условием действует всегда. Политики применяются только к анонимным запросам;
  подписанные запросы с любым действующим ключом имеют полный доступ.
- **Порты в Docker.** По умолчанию `8080` и `8081` открыты на всех сетевых интерфейсах. s3manager работает с
  полными правами и умеет удалять файлы. Если сервер доступен из сети, не публикуйте порт `8081` наружу или
  ограничьте его адресом `127.0.0.1`.
- **HTTP без шифрования.** Сервер не терминирует TLS. Для доступа из интернета поставьте перед ним обратный прокси
  с HTTPS.
- **Публичный доступ.** `public-read` на бакете открывает только список файлов, но не их содержимое (как в AWS S3);
  чтение объекта даёт ACL самого объекта или политика бакета с `s3:GetObject`. Не открывайте бакет с приватными
  файлами как `public-read`: его содержимое смогут перечислить все. Режим `public-read-write` позволяет любому загружать и затирать файлы.
- Если ключ засветился, удалите его (`rm-key`) и создайте новый.

## Ограничения

- Место после удаления и перезаписи возвращается не сразу, а сборщиком мусора по истечении периода ожидания
  (`sectoriadb.gc.grace`, 15 минут): читатель, который держит старую версию объекта дольше этого срока, может получить ошибку
  чтения. Таблицы блобов не уменьшаются: освободившиеся слоты переиспользуются, но файл `blob_*.raw` остаётся того же размера.
- `resize` одного блоба не останавливает запись, но на время переноса блоб замораживается, и пул может превысить `pool.max-blobs`
  на число замороженных блобов; старый файл удаляется сборщиком после `sectoriadb.gc.grace`, а при перезапуске в середине расширения
  оставшийся файл удаляется при старте. Таблицы блобов вытесняются из памяти по LRU (`sectoriadb.cache.*`): холодный блоб
  читается с задержкой загрузки таблицы.
- Загружаемый файл сначала записывается во временный каталог, поэтому там нужно свободное место не меньше размера
  самого большого файла.
- Нет версионирования, шифрования на стороне сервера и репликации. Соответствующие запросы S3 возвращают заглушки.
- Метаданные лежат в одном файле `sectoriadb-meta/sectoria.db` (CRC32C страниц, атомарные коммиты). Файл открывает
  один процесс: второй сервер на том же каталоге не стартует. Метаданные старого формата (`pools.json`, `blobs.json`,
  `manifests/*.json`) не переносятся. Данные блобов пишутся до коммита метаданных (новые чанки кукушки без `fsync` под
  блокировкой таблицы, но с барьером долговечности перед коммитом), поэтому сбой может оставить неучтённые данные (их находит
  обход блобов сборщика мусора), но не объект без данных. Сбой коммита метаданных (диск полон или не отвечает) не требует
  перезапуска: чтение продолжается, запись возобновляется сама, когда диск снова работает. Перед важными операциями делайте
  копию томов `sectoriadb-meta` и `sectoriadb-data`.
