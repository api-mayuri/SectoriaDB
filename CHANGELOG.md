## 19-security-audit — аудит безопасности (2026-10-21)

### Метахранилище и GC

- **Рост `sectoria.db` на длительной нагрузке и деградация p99 `PutObject` (soak этапа 18: 1,2 ГБ за 54 минуты при постоянном числе объектов, p99 51 → 85 мс).** Причина: сборщик освобождал не больше `max-chunks-per-run` (10 000) надгробий за проход раз в минуту при около 300 удалениях в секунду;
  очередь `deleted_manifests`, манифесты за ней и мёртвые записи малых объектов росли без предела (в soak наблюдалась только очередь чанков). Читатели страницы не удерживали, freelist не раздувался, заполнение деревьев стабильно — проверено счётчиками и `treeStats()`.
  Исправление: все просроченные надгробия собираются за проход (префиксный просмотр очереди, срезы), пометки `DELETED` малых записей — один `fsync` на файл на пачку вместо одного на запись, проход, упёршийся в предел чанков, повторяется планировщиком сразу.
  Тест: `GcKeepsUpTest` (падает на старом коде).
- **Диагностика:** `sectoriadb_metastore_oldest_reader_seconds`, `WARN` о читателе, державшем снимок дольше пяти секунд, `MetaStore.treeStats()`; `soak.csv` получил столбцы `tombstones` и `oldest_reader_s`.
- **Сборка не голодает при непрерывных загрузках:** вместо осушения пула пачка чанков занимает свои ключи на затворе; ждутся только загрузки, тронувшие эти ключи (`hold.touch`). Документ `garbage-collection.md` приведён в соответствие с кодом (чанки из `chunk_gc` затвор используют).
- **Ограниченные транзакции:** `DeleteBucket` — короткая транзакция «пул и блобы исчезли» и затем срезы по тысяче строк (запись `pool_purges`, оборванное удаление заканчивает сборщик); надгробия найдены по новому индексу `deleted_manifests_by_pool` вместо чтения всей очереди;
  обмен при компакции `.sob` и удаление блоба не читают очередь надгробий. Мультизагрузки бакета берутся по индексу открытых, а не просмотром всех.
- **Метрика открытых multipart-загрузок** читает размер индекса открытых за O(1) (раньше разбирала каждую запись при каждом скрейпе).
- **Журнал:** построчные события хранилища (`Storing file`, `Stored`, `Object deleted`, multipart, чтение/восстановление, загрузка таблиц) переведены на `DEBUG`; на `INFO` остались события жизненного цикла.
- Формат файла не менялся; добавлены деревья `deleted_manifests_by_pool` и `pool_purges` (создаются при первой записи; надгробия старых версий в индексе отсутствуют и снимаются обычным проходом).

## 18-ops-hardening — один том, копии, шифрование, soak, фаззинг (2026-10-18)

- **Один том для всего.** `docker-compose.yml` и `Dockerfile` держат метаданные (`/data/meta`), блобы и спул загрузок (`/data/storage`, спул `/data/storage/.tmp`) в одном томе `sectoriadb-store`, смонтированном в `/data`; `VOLUME ["/data"]`. Снимок одного тома атомарен для метаданных и блобов.
  **Меняется для пользователей compose:** прежние тома `sectoriadb-meta` и `sectoriadb-data` больше не используются; перенос — одноразовый контейнер, копирующий оба тома в новый ([guide/operations.md](docs/guide/operations.md#переход-со-старой-раскладки-на-два-тома)). Кода миграции нет, формат данных не менялся.
- **Резервное копирование без кода в сервере.** Хранилище переживает потерю питания по построению, поэтому горячая копия — атомарный снимок тома (LVM, ZFS, Btrfs, облачный диск), восстановление — запуск на снимке. Для малых установок: `deploy/backup/cold-backup.sh` (остановка, GNU tar с сохранением разрежённости, запуск, `.sha256`),
  `restore.sh` (только в новый том), `verify-backup.sh` (копия во временный том, `verify-all`, код возврата ≠ 0 при сбое; годится для cron).
- **Шифрование на диске — слой хранения, кода нет:** рецепты LUKS (с монтированием в Docker-том через `driver_opts`) и шифрованных дисков AWS/GCP/Azure, что они защищают и что нет, обращение с ключами ([guide/operations.md](docs/guide/operations.md#шифрование-на-диске)). Рецепты с `cryptsetup` и облачные в песочнице не проверялись (отмечено в документе).
- **Проверка горячей копии:** `bench/faults/snapshot-backup.sh` копирует том работающего сервера, пока идут записи (заморозка процесса `docker pause` как мгновение снимка), и проверяет `verify-all` и содержимое каждой подтверждённой записи на копии; контрольный прогон с копированием каталогов «по очереди» показывает несогласованную копию.
- **Длительный прогон:** `bench/warp/soak.sh` (по умолчанию 4 ч, рекомендуется ≥ 8 ч) снимает метрики сервера каждые N минут в `soak.csv` рядом с результатами warp (RSS, куча, дескрипторы, потоки, размер и свободные страницы метахранилища, очередь GC, диск, p99, доля 5xx) и печатает дрейф: первое окно против последнего и предупреждения о монотонном росте.
- **Фаззинг парсеров** (JUnit, фиксированное зерно, около 20 с): `Range`, `x-amz-copy-source(-range)`, `aws-chunked`, SigV4-заголовки и presigned-параметры, XML `DeleteObjects`/`CompleteMultipartUpload`/ACL. Исправлено: `Range: bytes=` давал `500` (`ArrayIndexOutOfBoundsException`), теперь игнорируется; разбор неверного XML писал `[Fatal Error]` в stderr мимо журнала.
- Формат данных не менялся.

## 17-iam — IAM-политики ключей (2026-10-18)

- Права ключа задаёт стандартная **IAM-политика** AWS (`Version`, `Statement` с `Effect`, `Action`, `Resource`, `Condition`), вычисляемая вместе с политикой бакета по правилам AWS для одного аккаунта: явный `Deny` в любой из двух запрещает;
  иначе `Allow` в любой разрешает; иначе ключ с политикой получает `403 AccessDenied`, а **ключ без политики сохраняет полный доступ** (существующие установки работают как раньше). Анонимные запросы не изменились.
- Политика хранится в `credentials.json` (необязательное поле `policy`) и подхватывается сервером со следующего запроса, без перезапуска. Новая онлайн-команда консоли `key-policy --id ID (--file F | --show | --remove)` проверяет документ до записи; `keys` показывает колонку `Policy`.
  Готовые примеры — `deploy/iam/` (`read-only.json`, `read-write.json`, `backup-writer.json`).
- Одно соответствие «операция → действие + ARN» для всех операций (`IamAuthorizer` на основе `OperationClassifier`): `CopyObject`/`UploadPartCopy` требуют `s3:GetObject` на источнике и `s3:PutObject` на приёмнике, `DeleteObjects` отдаёт `AccessDenied` по каждому запрещённому ключу (как AWS),
  `ListBuckets` требует `s3:ListAllMyBuckets`. Неоднозначные запросы (закодированное имя подресурса, смесь подресурсов) ключу с политикой отказывают.
- Принципал в политике бакета может называть ключ: `arn:aws:iam::sectoriadb:user/<accessKeyId>` или просто `<accessKeyId>`. **Меняется поведение для всех ключей:** явный `Deny` в политике бакета теперь действует и на подписанные запросы, `Allow` для `"*"` распространяется на ключи.
- Условия: добавлены `StringEquals`/`StringLike` на `s3:prefix` и `s3:delimiter` (листинг «только своего префикса»); `Bool` на `aws:SecureTransport` вычисляется и в политике ключа. Остальные условия по-прежнему fail closed (в политике ключа `key-policy` их отвергает).
- Новая причина отказа `policy_denied` в `sectoriadb_s3_auth_failures_total`.
- Нет пользователей, групп, ролей, STS, OIDC, владельца бакета: арендаторов разделяют ключи с политиками на их бакеты ([guide/recommendations.md](docs/guide/recommendations.md#один-ключ-на-приложение-или-арендатора)).
- Формат данных не менялся (в `credentials.json` добавлено необязательное поле).

## 16-tls-proxy — TLS через nginx (2026-10-18)

- TLS не реализуется в Java: перед сервером стоит nginx (`deploy/nginx/sectoriadb.conf`, сервис `nginx` в compose, образ `nginx:1.27.5-alpine`). TLS 1.2/1.3, HSTS, редирект `80` → `443`, `Host` и путь без изменений (подпись SigV4 сходится на ключах с пробелами, `+`, `%`, `//`, юникодом и эмодзи),
  без буферизации, тело до 5 ГиБ, `aws-chunked` и `Expect: 100-continue` проходят. Проверено `aws cli`, `rclone`, `s3cmd`, `curl` и `warp` через `https://localhost` ([guide/recommendations.md](docs/guide/recommendations.md#обратный-прокси-nginx)).
- Для пользователей: **порт `8080` больше не публикуется на хост** — клиенты ходят на `https://localhost` (`443`; `80` — редирект). Сертификат кладётся в `deploy/certs/` (в git не попадает); для проверки — `deploy/gen-self-signed.sh`.
  Прежний вариант без TLS и s3manager вынесены в `docker-compose.dev.yml` (`-f docker-compose.yml -f docker-compose.dev.yml`, S3-порт на `127.0.0.1:8080`). Новые переменные `HTTPS_PORT`, `HTTP_PORT`, `SECTORIADB_S3_REQUIRE_SECURE_TRANSPORT`.
- Новое свойство `sectoriadb.s3.require-secure-transport` (по умолчанию `false`, в compose `true`): запрос не по HTTPS получает `403 InsecureTransport`. Схему сервер берёт из `X-Forwarded-Proto` (`server.forward-headers-strategy=native`) только от доверенных прокси (`server.tomcat.remoteip.internal-proxies`, по умолчанию частные сети).
- Условие `Bool` на `aws:SecureTransport` в политиках бакета вычисляется (раньше `Allow` с любым условием не действовал, а `Deny` с условием запрещал всегда); остальные условия — как прежде.
- В compose сервер доверяет `X-Forwarded-*` только адресу nginx (фиксированная подсеть `172.31.250.0/24`, nginx `172.31.250.10`), а не всем частным сетям: подделать схему из соседнего контейнера нельзя.
- Исправлено: ключи из окружения (`SECTORIADB_S3_ACCESS_KEY`/`SECRET_KEY`, `SECTORIADB_S3_CREDENTIALS`) **не заводились**, когда включена интерактивная консоль (по умолчанию в compose): сидирование было `ApplicationRunner`, а консоль — тоже раннер, который блокирует поток.
  Теперь сидирование и очистка каталога временных файлов выполняются до открытия порта и до любых раннеров (`StartupSeedingTest`). Заодно очистка больше не может удалить временный файл загрузки, начавшейся сразу после старта.
- Формат данных не менялся.

## 13-multipart-metastore — multipart в метахранилище (2026-10-12)

- Состояние multipart — деревья `mpu_uploads`, `mpu_by_bucket`, `mpu_parts`; части — скрытые манифесты; `CompleteMultipartUpload` — одна транзакция без чтения и записи данных (раскладка `MULTIPART`, склейка CRC32/CRC32C/CRC64NVME без чтения данных).
- Для пользователей: `GET`/`HEAD ?partNumber=N` отдают часть (`206`); `Complete` идемпотентен (24 ч); минимальный размер части 5 МиБ (`sectoriadb.multipart.min-part-size`, `400 EntityTooSmall` при `Complete`);
  `ListMultipartUploads` с `delimiter` и маркерами, `ListParts` с корректным `NextPartNumberMarker`; `CreateMultipartUpload` запоминает `x-amz-acl`; `DeleteBucket` отбрасывает незавершённые загрузки; метрика `sectoriadb_multipart_uploads_open`.
- Миграция: формат метахранилища расширен (новые деревья, кодек манифеста v2; старые файлы читаются). Каталог `<data-dir>/.multipart` не читается и удаляется при старте — незавершённые загрузки на момент обновления теряются.
- Сервер больше не импортирует модуль `metastore`.

## 10-gc-and-resize — сборка мусора и безопасное расширение (2026-10-07)

- Сборщик мусора возвращает место удалённых и перезаписанных объектов (период ожидания 15 минут, затвор загрузок, обход блобов, компакция `small_*.sob`), команды `gc status|run|sweep|compact`, метрики `sectoriadb_gc_*`.
- `resize` блоба под записью без потери чанков; восстановление записи метахранилища на месте после сбоя коммита (чтение идёт, запись `503`/`507` и возобновляется сама); вытеснение таблиц блобов из памяти по LRU
  (`sectoriadb.cache.*`); барьер долговечности кукушки (без `fsync` под блокировкой таблицы).
- Для пользователей: загрузка, не уложившаяся в период ожидания, может получить `503` и должна повториться; место возвращается не сразу; `blob_*.raw` не уменьшаются. Новые свойства `sectoriadb.gc.*`, `sectoriadb.cache.*`, `sectoriadb.metastore.recovery-backoff`, `sectoriadb.reconcile-on-start`.
- Миграция: форматы не менялись; метки `DELETED` малых записей ставит теперь сборщик, а не коммит.

## 05-object-checksums — контрольные суммы объекта (2026-10-06)

- `x-amz-checksum-*` (заголовок и trailer), `Content-MD5`, составные и полнообъёмные суммы multipart, `x-amz-checksum-mode`; CRC32C всего объекта в манифесте и проверка при каждом полном чтении; команды `verify`, `verify-all`.
- Для пользователей: несовпадение суммы — `400 BadDigest`, объект не сохраняется. Манифесты без новых полей читаются (проверка пропускается).

## 04-small-objects — малые объекты (2026-10-06)

- Объекты меньше размера чанка хранятся целиком в append-only журнале `small_*.sob` (CRC32C на запись, восстановление хвоста); пустые объекты — только манифест.
- **Миграция:** новый вид блоба и поля манифеста; старые JSON читались с значениями по умолчанию.

## 03-chunk-integrity — целостность чанков (2026-10-06)

- Формат блоба v1 с заголовком, CRC32C и длиной в 32-байтной записи слота, XXH64-ключи, размер чанка 16 КиБ, проверка на чтении, побайтное сравнение при дедупликации, пересчёт ключа при коллизии, карантин слотов; `scrub`.
- **Миграция:** legacy-формат блобов (9-байтные записи) удалён, старые блобы не открываются (`bad magic`).

## 02-security — безопасность S3-слоя (2026-10-06)

- `public-read` на бакете открывает только листинг (раньше и чтение объектов — **изменение поведения**: анонимный `GET` объектов теперь `403`); явный `Deny` в политиках; проверка `x-amz-content-sha256` и подписей фрагментов;
  отказ всем запросам, пока нет ключей (`allow-open-setup` для старого поведения); XXE закрыт; строгий `uploadId`.
- Новые свойства: `sectoriadb.s3.auth.allow-open-setup`, `sectoriadb.s3.auth.allow-unsigned-payload`.

## 01-engine-safety — безопасность движка (2026-10-06)

- Атомарная вставка в кукушку (путь вытеснений ищется в памяти, перенос с конца), блокировка таблицы, `floorMod` вместо `abs` (формат не менялся), полные чтение/запись в цикле, постоянный канал и `fsync` по схеме «данные → force → метаданные → force»
  (`sectoriadb.fsync`).
